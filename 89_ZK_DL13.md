# From World Models to Smarter Pre-Training: Four Frontiers in Modern AI Systems

Modern AI is no longer advancing through scale alone. Larger models, bigger datasets, and more GPUs still matter, but they do not explain the most interesting shifts now happening across the field. The frontier is moving toward systems that learn more useful internal representations, compress sequence history more intelligently, train across hardware more deliberately, and extract more value from finite data.

Four ideas capture this shift. **JEPA-style world models** replace pixel reconstruction with latent prediction, giving agents a way to model action-conditioned futures. **State-space models** challenge the assumption that every past token must be stored in a growing attention cache. **Distributed training systems** turn model growth into a hardware topology problem, combining data, tensor, pipeline, context, and expert parallelism. **Smarter pre-training algorithms** change the learning process itself through curricula, front-loaded reasoning data, and reinforcement-style objectives during pre-training.

Taken together, these ideas point toward a more precise view of progress: the next generation of AI systems will be defined not only by how much they compute, but by what they choose to remember, predict, compress, and practice.

## 1. JEPA World Models: From Latent Prediction to Causal Object Dynamics

World models aim to give an agent an internal simulator: given the current state and an action, the model predicts what the world will look like next. Joint-Embedding Predictive Architecture (JEPA) changes how this simulator is trained. Instead of reconstructing future pixels, JEPA predicts future representations in latent space, allowing the model to focus on predictable structure rather than every visual detail.

This explains that idea through two recent directions. **Causal-JEPA** asks how a world model can learn object interactions rather than patch-level correlations. **LeWorldModel** asks how far JEPA can be simplified while still avoiding representational collapse. Together, they show why latent predictive models matter for robotics, planning, and physical AI.

### Why World Models Need Actions

An autoregressive model predicts the next state from the current or previous states:

$$
s_{t+1} = f_\theta(s_t)
$$

This is useful for temporal prediction, but it is incomplete as a model of an interactive world. The future is not determined only by what is currently visible. It also depends on what the agent or other actors do. A world model therefore introduces an action variable:

$$
s_{t+1} = f_\theta(s_t, a_t)
$$

Here, $s_t$ is the current state and $a_t$ is the action taken. This formulation makes the model a simulator: it can answer "what would happen if this action were applied now?"

A useful world model depends on three design choices:

- **State representation:** the model should encode the world faithfully, not merely store raw pixels.
- **Transition model:** it should capture the rules of the environment, such as gravity and collision.
- **Dynamics model:** it should respond correctly to interventions and actions.

JEPA mainly changes the first of these. It argues that the right prediction target is not the next image itself, but the latent representation of the next state.

### JEPA as Latent-Space Prediction

Generative world models predict in pixel space. They encode the current observation $x$, run a predictor, and reconstruct a future observation $y$. JEPA instead encodes both $x$ and $y$, then compares prediction and target in representation space. In other words, JEPA asks whether the predicted latent future matches the encoded true future.

This matters because not all future pixel details are predictable or important. A world model should preserve the structure needed for planning, not waste capacity on noise, texture, or arbitrary visual variation. JEPA can therefore be understood as an energy-based model.

An energy-based model defines a scalar compatibility score: low energy means that $(x,y)$ is a plausible pair, while high energy means the pair is incompatible.

Rather than computing a normalized likelihood $p(y|x)$, the model scores whether $y$ is a plausible continuation of $x$. In JEPA, this energy can be implemented as a latent prediction error. If $\hat{z}_y = \text{Predictor}(\text{Enc}(x), \text{mask})$ and $z_y = \text{Enc}(y)$, then:

$$
\mathcal{L}_{\text{JEPA}} = \|  \hat{z}_y - \text{sg}(z_y) \|^2
$$

where $\text{sg}(\cdot)$ denotes stop-gradient through the target encoder.

The difficulty is collapse. If the encoder maps every input to the same vector, latent prediction becomes trivial. V-JEPA avoids this with a target encoder updated by exponential moving average:

$$
\theta_{\text{target}} \leftarrow \lambda \cdot \theta_{\text{target}} + (1 - \lambda) \cdot \theta_{\text{online}}
$$

Together with stop-gradient and spatiotemporal masking, this prevents the target representation from becoming a degenerate constant. V-JEPA 2 then moves closer to a true world model by conditioning prediction on robot actions and poses.

DINO World Model takes a different route. It freezes a pretrained DINOv2 encoder and trains a predictor over the resulting patch features. This avoids collapse by construction, but it also changes the problem: the encoder is no longer learned as part of the world model.

### The Problem With Patch-Level World Models

Patch-level prediction is computationally heavy and cognitively awkward. A model that predicts 196 image patches may learn useful dynamics, but humans usually reason about objects: blocks, cups, bars, grippers, goals, and their interactions.

Causal-JEPA starts from this observation. It replaces patch tokens with object-centric slots. Object-centric learning decomposes a scene into a small set of slot vectors, ideally one per object. A canonical mechanism is Slot Attention. Given input patch embeddings $X = \{x_1, \ldots, x_N\}$ and $K$ slot vectors $\{s_1, \ldots, s_K\}$, slots query the input features and are refined iteratively:

$$
\text{Attn}(Q, K, V) = \text{softmax}\!\left(\frac{QK^\top}{\sqrt{d}}\right) V
$$

with slots as queries and input features as keys and values. Slots are then refined iteratively:

$$
s_k^{(t+1)} = \text{GRU}(s_k^{(t)}, \text{Attn}_k(X))
$$

Some slot-attention implementations normalize over slots rather than patches so that each patch is primarily assigned to one slot.

These slots are more compact than patches and better aligned with physical interaction. However, simply replacing DINO World Model's patches with object slots is not enough. The model can still learn shortcuts.

### Object Masking as an Intervention

Causal-JEPA's central idea is object masking. If the model sees every object's recent trajectory, it can often predict the next state of each object from that object's own smooth motion. That produces low loss without requiring inter-object reasoning.

Masking breaks this shortcut. The model hides entire object slots at selected time steps and forces the predictor to infer them from other objects. The intuition is simple: if a monkey is hidden but a banana is shrinking, a model that understands interaction should infer the hidden cause.

There is a subtle problem. Slots are permutation-equivariant: slot 2 in one video does not necessarily represent the same object type as slot 2 in another. Causal-JEPA handles this by never masking the first time step. The first-frame slot acts as an identity anchor. A masked token is constructed as:

$$
\hat{m}_{k,t} = \text{Identity}_k^{(t_0)} + \text{Learnable Mask Token} + \text{PositionalEncoding}(t)
$$

The training target is the true slot representation produced by the encoder. The C-JEPA loss is:

$$
\mathcal{L}_{\text{C-JEPA}} = \sum_{k \in \mathcal{M}} \sum_{t \in \mathcal{T}} \left\| \hat{s}_{k,t} - \text{sg}(s_{k,t}^*) \right\|^2
$$

The predictor receives object slots and action tokens together. This action design is important. DINO World Model concatenates action embeddings to patch features. Causal-JEPA treats the action as a separate graph node, allowing the transformer to learn which objects the action influences.

### What "Causal" Means Here

Causal-JEPA does not claim to recover a Pearl-style structural causal model. Its use of "causal" is closer to temporally directed predictive dependence: which past objects help predict which future objects?

The relevant conceptual primitive is an influence neighborhood. For a masked object $k$ at time $t$, the influence neighborhood $\mathcal{N}(k,t)$ is the minimal set of other observable slot histories needed to predict that object:

$$
\hat{s}_{k,t} = g(\{s_{j,t'}\ |\ j \in \mathcal{N}(k,t),\ t' < t\})
$$

Once the influence neighborhood is known, the rest of the history should add little conditional information about the target slot. Attention probing can then be used as an imperfect but useful diagnostic: if a masked token attends heavily to another object, that object may be part of the target's influence neighborhood.

Causal-JEPA also relaxes the first-order Markov assumption. A single frame often lacks velocity and acceleration information. For object slots, the next state usually depends on a finite history window:

$$
p(s_{t+1} \mid s_{t}, s_{t-1}, \ldots, s_{t-L+1}) \approx p(s_{t+1} \mid s_{t}, s_{t-1}, \ldots, s_1)
$$

The theory depends on four assumptions:

**A1 (No Instantaneous Causality):** object interactions are modeled through past states, not same-time effects.

**A2 (Shared Mechanism):** the transition mechanism is assumed to be shared across the training videos.

**A3 (Object-Aligned Representation):** each slot should track the same object through a video.

**A4 (History Sufficiency):** the finite history window should contain enough information to predict the target slot.

Confounders can exist, so the model is not guaranteed to recover the true causal graph. The more modest claim is that masking encourages the transformer to learn predictively sufficient inter-object dependencies.

A simple confounder pattern is that a hidden cause can drive both $X$ and $Y$, making them appear directly related even when neither causes the other.

### Experimental Lessons From Causal-JEPA

Causal-JEPA is evaluated on three kinds of tasks:

- **CLEVRER:** video question answering with predictive, explanatory, and counterfactual questions.
- **Push-T:** control and planning, where a ball pushes a T-shaped block to a goal pose.
- **PHYRE:** physical plausibility with gravity, collisions, and multi-object interaction.

The strongest gains appear where inter-object reasoning matters. On CLEVRER, C-JEPA improves counterfactual accuracy, especially compared with the ablation that uses object-centric representations without masking.

Planning can be written as latent-space goal optimization:

```math
a_1^*, a_2^*, \ldots, a_T^* = \arg\min_{\{a_t\}} \sum_{t=1}^{T} \left\| z_t - z_{\text{goal}} \right\|^2
```

with rollout:

$$
z_{t+1} = \text{Predictor}(z_t, a_t)
$$

Here, $z_t$ is the full latent scene state, while $s_{k,t}$ is an individual object slot. Equivalently, $z_t = \{s_{1,t}, \ldots, s_{K,t}\}$.

### LeWorldModel: Can JEPA Be Simpler?

LeWorldModel attacks a different problem: JEPA systems often require many anti-collapse tricks. V-JEPA uses EMA, stop-gradient, and masking. Causal-JEPA adds object-centric encoders, identity-preserving masking, and action nodes. DINO World Model avoids collapse by freezing a pretrained encoder. PLDM uses a multi-term VICReg-style objective.

LeWorldModel asks whether end-to-end JEPA can work with one regularizer and one hyperparameter.

The collapse problem is:

$$
\text{Enc}(o_t) = \mathbf{c} \quad \forall\ o_t
$$

If $\mathbf{c}$ is constant, prediction loss becomes trivial and the representation contains no useful information.

VICReg prevents collapse with variance, invariance, and covariance terms:

$$
\mathcal{L}_{\text{VICReg}} = \lambda_I \cdot \mathcal{L}_I + \lambda_V \cdot \mathcal{L}_V + \lambda_C \cdot \mathcal{L}_C
$$

The variance and covariance pieces encourage unit-scale, decorrelated dimensions, while the invariance piece keeps paired views close. PLDM applies this kind of regularization spatially and temporally, producing six loss terms. LeWorldModel instead uses SIGReg, the Sketched Isotropic Gaussian Regularizer.

The target distribution is an isotropic Gaussian:

$$
\mathcal{N}(\mathbf{0}, \sigma^2 I_D)
$$

The key theorem is Cramér-Wold:

> A multivariate distribution $P$ on $\mathbb{R}^D$ is uniquely determined by the collection of all its 1D marginals $\{P_{u^\top z}\ |\ \mathbf{u} \in S^{D-1}\}$ where $S^{D-1}$ is the unit sphere.

So SIGReg does not directly fit a full high-dimensional Gaussian. It samples random directions, projects embeddings onto each direction, and makes those one-dimensional projections look Gaussian.

### The LeWorldModel Training Step

LeWorldModel is deliberately minimal:

- No EMA.
- No masking.
- No stop-gradient.
- No pretrained encoder.
- A shared encoder processes current and next observations.
- A predictor maps $(z_t, a_t)$ to $\hat{z}_{t+1}$.
- The CLS token serves as the latent state.
- SIGReg is the only anti-collapse regularizer.

<details><summary>The concise training loop is:</summary>

```python
z_t   = encoder(o_t)       # encode current observation
z_t1  = encoder(o_t1)      # encode next observation (shared encoder)
z_hat = predictor(z_t, a_t)  # predict next latent state
loss_pred = MSE(z_hat, z_t1)  # prediction loss
loss_reg  = SIGReg(z_t)       # anti-collapse regularization
return loss_pred + lambda * loss_reg
```

</details>

The prediction loss is:

$$
\mathcal{L}_{\text{pred}} = \frac{1}{B} \sum_{i=1}^{B} \left\| \hat{z}_{t+1}^{(i)} - z_{t+1}^{(i)} \right\|^2
$$

SIGReg begins by sampling projection directions:

$$
p_{m,i} = \mathbf{u}_m^\top z_i, \quad \mathbf{u}_m \sim \text{Uniform}(S^{D-1})
$$

For each projection direction $m$, with sorted projected values $p_{m,(1)} \leq p_{m,(2)} \leq \ldots \leq p_{m,(B)}$:

$$
\mathcal{L}_{\text{SIGReg}, m} = \frac{1}{B} \sum_{i=1}^{B} \left( p_{m,(i)} - \Phi^{-1}\!\left(\frac{i}{B+1}\right) \right)^2
$$

This is a differentiable approximation to the 1D Wasserstein-2 distance between the empirical projection and a standard Gaussian.

The full SIGReg loss averages across directions:

$$
\mathcal{L}_{\text{SIGReg}} = \frac{1}{M} \sum_{m=1}^{M} \mathcal{L}_{\text{SIGReg}, m}
$$

and the total objective is:

$$
\mathcal{L}_{\text{total}} = \mathcal{L}_{\text{pred}} + \lambda \cdot \mathcal{L}_{\text{SIGReg}}
$$

The result is a one-hyperparameter trade-off. With only $\lambda$, tuning becomes a one-dimensional search problem rather than a high-dimensional grid over many loss weights.

### Planning With LeWorldModel

LeWorldModel uses a compact CLS-token latent state, which makes planning much faster than patch-token models. Given an initial observation $o_1$ and goal observation $o_g$, the planner encodes:

1. $z_1 = \text{Enc}(o_1)$
2. $z_g = \text{Enc}(o_g)$
3. A candidate action sequence $\{a_1, \ldots, a_T\}$
4. A rollout $z_{t+1} = \text{Predictor}(z_t, a_t)$
5. A latent goal loss $\mathcal{L} = \sum_t \|z_t - z_g\|^2$

The formal planning objective is:

$$
\mathcal{L}_{\text{plan}}(\{a_t\}_{t=1}^T) = \sum_{t=1}^{T} \left\| z_t - z_g \right\|^2
$$

subject to:

$$
z_{t+1} = \text{Predictor}(z_t, a_t), \quad z_1 = \text{Enc}(o_1)
$$

Because the predictor is differentiable, the action sequence can be optimized by backpropagation through the rollout. This is model predictive control in latent space, although the evaluation discussed here uses open-loop rollouts.

LeWorldModel's speed advantage comes from the latent representation. DINO World Model predicts over many patch tokens, while LeWorldModel predicts over a single vector. The reported result is that LeWorldModel plans in under one second, while DINO World Model's best setting takes 47 seconds, roughly a 50x speedup. At equal compute, LeWorldModel can outperform DINO even on tasks where DINO performs better with its full planning budget.

### Representation Quality and Surprise

A world model's prediction error can act as a surprise signal:

$$
e_t = \| \hat{z}_{t+1} - z_{t+1} \|^2
$$

where:

- $\hat{z}_{t+1} = \text{Predictor}(z_t, a_t)$ — what the model _expected_
- $z_{t+1} = \text{Enc}(o_{t+1})$ — what _actually happened_

If an object teleports, prediction error should spike. If an irrelevant color changes, the spike should be much smaller. This gives the world model a way to detect physical violations without being explicitly trained as an anomaly detector.

LeWorldModel's latent space is also probed for physical state variables. A linear probe predicts a target variable $y$ from frozen latent state $z$:

$$
\hat{y} = W z + b, \quad W \in \mathbb{R}^{d_y \times D},\ b \in \mathbb{R}^{d_y}
$$

$$
\mathcal{L}_{\text{probe}} = \frac{1}{N} \sum_i \| \hat{y}_i - y_i \|^2
$$

Low linear-probe error suggests the representation makes physical variables linearly accessible. This does not prove full disentanglement, but it is consistent with SIGReg's pressure toward decorrelated dimensions.

t-SNE is used as a visual diagnostic:

$$
\{z_i\} \xrightarrow{\text{t-SNE}} \{w_i\} \subset \mathbb{R}^2
$$

The desired geometry is that nearby physical states remain nearby in latent space.

### Limitations of LeWorldModel

LeWorldModel's simplicity is also its main risk. SIGReg forces embeddings toward an isotropic Gaussian in $D$ dimensions. If the true environment has intrinsic dimensionality $d \ll D$, such as a 2D navigation task where position is almost sufficient, the model may need to fill extra dimensions with artificial variation. This can harm learning.

Using a single CLS token also sacrifices spatial detail. That trade-off is exactly what makes planning fast, but it can become a limitation in tasks requiring fine-grained spatial relations. The OG-Bench Cube results show the other side of this trade-off: DINO's pretrained visual representation gives it an advantage in 3D object understanding when compute is not normalized.

Finally, LeWorldModel applies `SIGReg(z_t)` to the current embedding. Because the same encoder processes $o_t$ and $o_{t+1}$, this indirectly regularizes both current and next states, but applying regularization only to $z_t$ is still a design choice worth testing.

### World Models Versus VLAs and LLM Agents

Vision-Language-Action models map observations and instructions directly to actions:

$$
a_t = \pi_{\text{VLA}}(o_t, \text{instruction})
$$

A world-model planning policy instead optimizes actions through a learned simulator:

$$
a_t^* = \arg\min_{\{a_\tau\}_{\tau=t}^{t+T}} \sum_{\tau=t}^{t+T} \mathcal{C}(z_\tau, z_g), \quad z_{\tau+1} = f(z_\tau, a_\tau)
$$

The distinction is not that VLAs can never encode dynamics implicitly. The sharper point is that they are not explicitly trained to model action consequences. JEPA world models are. They learn transitions of the form $p(s_{t+1} | s_t, a_t)$ and can be used for planning immediately after training.

This also separates JEPA from LLM agents. JEPA is not an architecture; it is a training framework. A JEPA model may use transformers internally, but its objective is latent predictive consistency under actions, not next-token likelihood.

World-model hallucination is also different from LLM hallucination. An LLM may state a false fact. A world model may predict an out-of-distribution future or allow an optimizer to exploit invalid action bounds, such as suggesting $a = -2$ when $a \in [-1, 1]$.

### From Slow Planning to Fast Policies

World-model planning can be slow. A practical path is to use a world model as a System 2 planner during training, then distill its behavior into a fast System 1 policy.

Dreamer expresses this idea as a model-based reinforcement learning loop. First, train the world model:

$$
\min_{\phi} \mathbb{E}_{(o_t, a_t, o_{t+1}) \sim \mathcal{D}} \left[ \mathcal{L}_{\text{world}}(o_t, a_t, o_{t+1}; \phi) \right]
$$

Then train a policy inside imagined rollouts:

$$
\min_{\psi} \mathbb{E}_{z_0 \sim \mathcal{D},\ a_t \sim \pi_\psi(z_t)} \left[ -\sum_{t=0}^{H} \gamma^t R(z_t, a_t) \right], \quad z_{t+1} = f_\phi(z_t, a_t)
$$

Then collect more real data from the trained policy and add it back into the dataset.

A more direct distillation version uses MPC as a teacher and trains a fast policy:

$$
\min_\psi \mathbb{E}_{(z_t, z_g) \sim \mathcal{D}} \left[ \| \pi_\psi(z_t, z_g) - a_t^{\text{S2}} \|^2 \right]
$$

This combines the careful reasoning of model-based planning with the inference speed of direct policies.

### Why Masking Matters

Prediction loss alone can learn a world model, but it may not learn interaction dynamics. Without masking, the model can minimize loss by learning self-dynamics:

$$
\hat{s}_{k,t} = g(s_{k,t-1}, s_{k,t-2}, \ldots, s_{k,t-L})
$$

That is enough when each object's motion is smooth and mostly predictable from its own history. With masking, the self-dynamics shortcut is blocked:

$$
\hat{s}_{k,t} = g(\{s_{j, t'}\ |\ j \neq k,\ t' < t\})
$$

Now the model must use other objects' histories. This is the core reason Causal-JEPA's object masking improves counterfactual and physical-reasoning benchmarks.

## 2. State-Space Models, Transformers, and the Future of Learned Tokenization

Modern state-space models are often introduced as efficient alternatives to transformers. That description is not wrong, but it is incomplete. The more important point is that state-space models, or SSMs, impose a different inductive bias on sequence modeling. They do not store every past token and retrieve from it later. Instead, they continuously compress the past into a fixed-size state.

That difference changes what the model is good at. Transformers are excellent when the input has already been divided into meaningful tokens. SSMs are stronger when the data must be compressed, summarized, tracked, or reorganized over time. The central question is therefore not whether SSMs are "cheaper transformers." It is when a model should behave like a database, when it should behave like a recurrent state, and how future architectures can combine both.

### Why Modern SSMs Work

State-space models come from control theory. In sequence modeling, the core recurrence can be written as:

$$
h_t = \bar{A}_t h_{t-1} + \bar{B}_t x_t
$$

$$
y_t = C_t h_t
$$

Here, $h_t$ is the hidden state at step $t$, $x_t$ is the current input, and $y_t$ is the output. The matrices or vectors $\bar{A}_t$, $\bar{B}_t$, and $C_t$ determine how the previous state is retained, how the new input is incorporated, and how the output is read from the state.

The modern SSM family includes Mamba, Mamba 2, Mamba 3, xLSTM, DeltaNet, Gated DeltaNet, TTT, and hybrid architectures such as Jamba, Zamba, Samba, Hunyuan, Qwen variants, Kimi-Linear, Olmo, and Nemotron. Among these, Mamba 2 and Gated DeltaNet are useful reference points because they have more practical validation than newer variants.

Modern SSMs became competitive through three ingredients.

First, they use much larger state sizes than classical recurrent models. Traditional LSTMs usually had a hidden state roughly comparable to the model output dimension. Modern SSMs expand each channel into a larger state, often with $N \approx 64$ or $128$. Since the state is the model's only persistent memory during generation, this expansion is essential.

Second, they use input-dependent parameters. In Mamba, the SSM parameters are projections of the input:

$$
\bar{B}_t = \text{Linear}_B(x_t), \quad C_t = \text{Linear}_C(x_t), \quad \Delta_t = \text{Softplus}(\text{Linear}_\Delta(x_t))
$$

$$
\bar{A}_t = e^{\Delta_t \cdot A}
$$

This selectivity lets the model decide, at each step, whether to preserve the previous state, overwrite it, or partially mix in the new input. Without selectivity, the recurrence treats all inputs too uniformly. With selectivity, an SSM gets something closer to attention's ability to decide what matters, but it does so through state updates rather than explicit retrieval.

Third, modern SSMs are designed around hardware-efficient computation. A naive recurrence is sequential, which would make training slow on long sequences. Mamba 1 used associative scan to parallelize the recurrence. Mamba 2 reformulated the computation as chunked matrix multiplication, mapping the work more directly to GPU tensor cores.

For a chunk of length $L$, the SSM computation can be written as:

$$
Y_{\text{chunk}} = M_{\text{chunk}} \cdot X_{\text{chunk}} + \text{(cross-chunk term)}
$$

where $M_{\text{chunk}}$ is lower-triangular, so each position depends only on the current and previous positions in the chunk.

This makes the relationship between SSMs and attention more concrete. Within a local chunk, the computation resembles a lower-triangular attention-like matrix. The difference is what happens after the chunk: an SSM carries forward a compressed state instead of storing every token in a growing cache.

### Autoregressive State: Database vs. Brain

The most useful way to compare transformers and SSMs is through their autoregressive state: the information a model keeps between generation steps.

A transformer stores a KV cache:

$$
\text{Transformer}: \quad \mathcal{S}_t^{\text{attn}} = \{(k_s, v_s)\}_{s=1}^t \quad \Rightarrow \quad |\mathcal{S}_t^{\text{attn}}| \propto t
$$

An SSM stores a fixed hidden state:

$$
\text{SSM}: \quad \mathcal{S}_t^{\text{SSM}} = h_t \in \mathbb{R}^{d \times N} \quad \Rightarrow \quad |\mathcal{S}_t^{\text{SSM}}| = \text{const}
$$

The transformer's state grows with context length. The SSM's state does not.

This gives transformers a database-like character. They retain a representation of every past token, and each new token can query that database. This is powerful for fine-grained retrieval, copying, coreference, and tasks where the correct answer depends on locating a specific past item.

SSMs have a brain-like character in the limited sense that they maintain a compressed, evolving internal state. They are good at tracking aggregate state, updating representations over time, and processing streams at constant memory cost. But compression is lossy. A fixed state cannot guarantee exact recall of an arbitrary token from an arbitrarily long context.

The practical memory difference is direct:

$$
\text{Memory}_{\text{KV}}(T) = 2 \cdot T \cdot d_k \cdot n_h \cdot L \cdot \text{bytes}
$$

$$
\text{Memory}_{\text{SSM}} = d \cdot N \cdot \text{bytes} \quad (\text{constant in } T)
$$

This explains why SSMs are attractive for streaming, long-context processing, and online inference. It also explains why pure SSMs struggle on tasks like "Needle in a Haystack," where the model must retrieve an exact detail from a long context. The weakness is not accidental. It follows from the fixed-size state.

Hybrid models try to combine both regimes. They interleave many SSM layers with occasional attention layers. Empirically, several groups have found strong results with more SSM layers than attention layers. Earlier work suggested a ratio near 10:1; more recent practice often uses about 3:1 or 4:1. The interpretation is simple: most layers can perform efficient stateful compression, while a smaller number of attention layers provide precise retrieval when needed.

For a model with $L_{\text{total}}$ total layers, the hybrid allocation is:

$$
L_{\text{SSM}} : L_{\text{attn}} = r : 1
$$

The total computation ratio, ignoring KV cache, is:

$$
\frac{\text{Compute}_{\text{SSM}}}{\text{Compute}_{\text{attn}}} \approx \frac{L_{\text{SSM}} \cdot O(T \cdot N \cdot d)}{L_{\text{attn}} \cdot O(T \cdot d^2)} = \frac{r \cdot N}{d}
$$

For $r=4$, $N=128$, and $d=4096$, the ratio is approximately $0.125$. That means the SSM layers use about 12.5 percent of the compute per token that attention layers do. But the deeper point is not just compute. The ratio suggests that compressive state updates are doing useful modeling work, not merely replacing attention with a cheaper substitute.

### Why Tokenization Matters So Much for Transformers

Transformers work best when tokens are meaningful units. This is easy to miss because modern language models almost always use BPE, WordPiece, or similar tokenization schemes. Those tokenizers turn raw characters into subwords, common words, prefixes, suffixes, and other units that attention can usefully store and retrieve.

In standard attention, every token is stored in the KV cache. That is sensible when each token is worth remembering. It is less sensible when the unit is a byte, a single character, a DNA base pair, or a pixel. A single byte usually has little standalone semantic content. Caching it as if it were a meaningful memory item wastes capacity and compute.

The sequence-length penalty is also severe. For the same text corpus with character count $C$:

$$
T_{\text{BPE}} \approx \frac{C}{r_{\text{BPE}}}, \quad r_{\text{BPE}} \approx 4 \text{ (for English)}
$$

Attention compute at byte level vs. token level is:

$$
\text{Compute}_{\text{byte}} = O(C^2) = O\!\left((r_{\text{BPE}} \cdot T)^2\right) = r_{\text{BPE}}^2 \cdot O(T^2) \approx 16 \times \text{Compute}_{\text{token}}
$$

So byte-level transformers face two problems at once. They see longer sequences, and the individual sequence elements are less meaningful.

This helps explain the empirical results from byte-level modeling. In MambaByte experiments, Mamba outperformed sliding-window transformers at the same model size on raw bytes. Global attention used more compute and still only roughly closed the gap. In DNA modeling, where there is no obvious analogue of English BPE tokens, Mamba-like models were reported to be about three times more data-efficient than transformers.

The claim is not that tokenization is bad. It is that tokenization is doing important modeling work for transformers. Attention is powerful partly because humans or offline algorithms have already chosen a useful resolution for the sequence.

### H-Net and Learned Chunking

H-Net pushes this argument further. Instead of using a fixed tokenizer, it learns a hierarchy of chunks end to end. The architecture replaces static BPE rules with a learned, data-dependent boundary predictor.

At a high level, H-Net looks like this:

```text
Raw bytes/chars -> [Encoder (SSM)] -> [Boundary Predictor] -> Chunk boundaries
                                                              |
                                              [Pooling] -> Chunk embeddings
                                                              |
                                              [Main Model (Transformer or H-Net)]
                                                              |
                                              [Expand back to original resolution]
                                                              |
                              [Decoder (SSM)] -> Per-byte prediction logits
```

The outer stages operate at the byte or character level, where SSMs are useful because they compress and aggregate local information. The inner model operates on chunk embeddings, which are more semantically meaningful and therefore better suited to attention.

If a byte sequence has length $C$ and average chunk size $\bar{s}$, the chunk sequence length is:

$$
T_{\text{chunks}} = \frac{C}{\bar{s}}
$$

For two-level H-Net:

$$
T_{\text{level-2}} = \frac{T_{\text{chunks}}}{\bar{s}_2} = \frac{C}{\bar{s}_1 \cdot \bar{s}_2}
$$

The boundary predictor computes a soft probability for each position:

$$
\hat{b}_t = \sigma\!\left(w^\top h_t + c\right) \in (0, 1)
$$

It then forms a hard boundary decision by thresholding or otherwise discretizing the probability. Once boundaries are chosen, the model pools the encoder states inside each chunk. The main model then processes these chunk embeddings, and the decoder expands the representation back to byte resolution.

The important point is that H-Net does not look up chunk embeddings from a fixed vocabulary. It computes them dynamically from the encoder outputs. That allows variable chunk sizes and arbitrary real-valued chunk representations.

One especially important H-Net experiment applies the architecture to data that is already BPE-tokenized. Even there, outer SSM layers outperform pure transformer outer stages. That matters because it removes the simple explanation that "SSMs only help because the data is byte-level." In that experiment, both architectures see the same BPE tokens. The advantage appears to come from the compression task itself.

This supports the broader thesis: SSMs are not merely useful at low data resolutions. They are useful whenever the architecture must learn how to compress information into better abstractions.

### What H-Net Suggests About Scaling

DNA modeling gives another test case for H-Net. Fixed human-designed tokenization is much less obvious than in natural language. A base pair is too small to be semantically rich, but there is no universal equivalent of a word or subword vocabulary.

A simple scaling-law form is:

$$
\mathcal{L}(C_{\text{compute}}) = a \cdot C_{\text{compute}}^{-\alpha}
$$

where $\mathcal{L}$ is bits per byte and $C_{\text{compute}}$ is total training FLOPs.

For H-Net on DNA:

$$
\alpha_{\text{H-Net}} > \alpha_{\text{Transformer}} \quad \Rightarrow \quad \text{H-Net scales better with compute}
$$

This is stronger than a fixed performance offset. If two architectures have parallel scaling curves, one may be consistently better by a constant margin. But if one architecture has a steeper slope, it improves faster as compute increases. The result suggests that learned hierarchy plus SSM-based compression may be fundamentally better suited to certain non-tokenized domains.

The caveat is important: H-Net has not yet been validated at very large model scales. Boundary prediction is also a difficult discrete routing problem, and training can be unstable. The result is promising, not settled.

### Efficiency Is Not the Whole Story

The final reframing is that efficiency alone is the wrong lens. The real question is how well an architecture turns compute into useful modeling capability.

From this perspective, a FLOP is not valuable just because it was spent. It is valuable if it reduces loss or improves capability. If a transformer spends compute storing and comparing semantically empty byte tokens, some of that compute may be poorly matched to the data. If an SSM compresses low-level tokens into a useful evolving state, it may extract more modeling value from less compute.

This is why "quadratic attention is inefficient" is not always the right criticism. If a task requires exact retrieval from many past items, the transformer's growing cache is the right tool. The cost is not wasteful; it is buying precise recall. The weakness appears when attention is forced to operate at an inappropriate token resolution.

Likewise, "SSMs cannot retrieve exactly" is not always the right criticism. If a task rewards state tracking, summarization, streaming, or abstraction-building, the fixed state is a strength. The weakness appears when the task requires exact recall of arbitrary details.

### Open Problems

Several open problems fall out of this framing.

The first is training true recurrence. Current SSMs rely on linear structure to enable efficient parallel training. For a linear recurrence, gradients involve products of transition matrices:

$$
\prod_{s=k}^{t} \frac{\partial h_s}{\partial h_{s-1}} = \prod_{s=k}^{t} \bar{A}_s
$$

Associative scan makes this tractable. More expressive nonlinear recurrence would require backpropagation through time, creating a severe memory constraint:

$$
\text{Memory}_{\text{BPTT}} = T \cdot d \cdot N \cdot \text{bytes}
$$

For very long sequences, storing the entire activation history becomes infeasible. This may be one reason current architectures sit in a local optimum shaped by GPU efficiency and backpropagation.

The second open problem is learned chunking. H-Net suggests that chunking is a critical primitive, but its current boundary prediction mechanism is only an early step. A better chunking mechanism could become as important to future architectures as tokenization is to current transformers.

The third open problem is interpretability. SSMs do not have literal attention maps, but their outputs can still be analyzed as input-weighted contributions from past positions. These virtual maps tend to be diffuse rather than sharp, matching the idea that SSMs compress broadly while transformers retrieve specifically. But they are not normalized attention weights, and they can behave differently from softmax attention maps. They are useful, but they require caution.

## 3. Scaling LLM Training: From One GPU to 5D Parallelism

Training a trillion-parameter language model is not just a bigger version of ordinary deep learning. The basic training loop still has the same ingredients: forward pass, backward pass, gradient synchronization, optimizer step, and checkpointing. But at modern scale, every one of those ingredients becomes a distributed systems problem.

The core challenge is simple: a single GPU cannot hold the model, and a single GPU cannot process enough data fast enough. Modern LLM training therefore combines several orthogonal forms of parallelism. Data Parallelism splits the batch. Tensor Parallelism splits tensor operations. Pipeline Parallelism splits layers. Context Parallelism splits long sequences. Expert Parallelism splits Mixture-of-Experts modules.

The hard part is not knowing these names. The hard part is knowing what each one buys, what it costs, and where it fits in the hardware topology.

### Why the Single-GPU Baseline Breaks

<details><summary>The baseline training loop is familiar:</summary>

```python
for batch in dataloader:
    y_pred = model.forward(batch)     # Forward pass
    loss = loss_fn(y_pred, batch.labels)
    loss.backward()                    # Backward pass: compute gradients
    optimizer.step()                   # Update parameters
    optimizer.zero_grad()              # Clear gradients
```

</details>

This loop assumes that the model parameters, gradients, optimizer state, and activations fit in one device's memory. That assumption fails quickly.

For a model with $N$ parameters, with Adam optimizer in mixed precision (BF16 compute, FP32 optimizer):

$$
M_{\text{total}} = \underbrace{2N}_{\text{params (BF16)}} + \underbrace{2N}_{\text{grads (BF16)}} + \underbrace{4N}_{\text{master weights (FP32)}} + \underbrace{4N}_{\text{momentum (FP32)}} + \underbrace{4N}_{\text{variance (FP32)}} + M_{\text{act}}
$$

$$
M_{\text{total}} = 16N + M_{\text{act}} \text{ bytes}
$$

The $16N$ term is already enormous before activations are counted. A 1T-parameter model requires about 16 TB for parameters, gradients, and optimizer state under this accounting. An H100 has 80 GB of VRAM, so the model must be split.

Gradient accumulation helps with batch memory, but not with model memory. If the global batch is too large to process in one pass, it can be divided into $k$ micro-batches:

$$
\nabla \mathcal{L}_{\text{accum}} = \frac{1}{k} \sum_{i=1}^{k} \nabla_\theta \mathcal{L}(x_i)
$$

<details><summary>In code:</summary>

```python
optimizer.zero_grad()
for i, micro_batch in enumerate(micro_batches):
    y_pred = model(micro_batch)
    loss = loss_fn(y_pred, micro_batch.labels) / k  # normalize by accumulation steps
    loss.backward()  # accumulates gradients in .grad

optimizer.step()   # single optimizer step after k micro-batches
optimizer.zero_grad()
```

</details>

The global batch size is:

$$
B_{\text{global}} = B_{\text{micro}} \times k_{\text{accum}} \times N_{\text{DP}}
$$

Accumulation decouples the optimizer batch size from the micro-batch size that fits in memory. But it is still sequential, and it still assumes the model itself fits. Distributed parallelism starts where this trick stops.

### Data Parallelism: Split the Batch

Data Parallelism (DP) is the most direct way to use multiple GPUs. Each GPU holds a full copy of the model and processes a different slice of the batch. During the backward pass, gradients are averaged so every replica performs the same optimizer update.

For parameter $\theta_i$, the synchronized gradient $\bar{g}_i$ across $D$ GPUs is:

$$
\bar{g}_i = \frac{1}{D} \sum_{d=1}^{D} g_{i, d}
$$

This is implemented with `AllReduce`. The benefit is simplicity: DP is model agnostic, easy to implement with `torch.nn.parallel.DistributedDataParallel`, and highly effective when the model fits on each GPU.

The first performance issue is communication overlap. A naive implementation waits until the full backward pass finishes before synchronizing gradients. Optimized DDP buckets gradients. As soon as a bucket is ready, the `AllReduce` for that bucket begins while earlier layers are still computing their backward pass. The goal is to keep GPU compute engines busy while communication engines move gradients.

The deeper issue is memory redundancy. Vanilla DP duplicates model parameters, gradients, and optimizer states on every GPU. That motivates ZeRO.

### ZeRO and FSDP: Remove Redundant State

ZeRO starts from a key collective identity:

$$
\text{AllReduce}(X_1, X_2, \ldots, X_D) = \text{AllGather}\left(\text{ReduceScatter}(X_1, X_2, \ldots, X_D)\right)
$$

Where $X_d$ is the full gradient tensor on GPU $d$.

`ReduceScatter` sums tensors across GPUs but returns only one shard of the summed result to each GPU. `AllGather` then collects all shards back onto every GPU. ZeRO inserts useful work between these two operations.

The stages are:

- **ZeRO-1:** shard optimizer states. Each GPU updates only its parameter shard, then parameters are gathered.
- **ZeRO-2:** shard optimizer states and gradients. Unneeded gradient shards are discarded.
- **ZeRO-3 / FSDP:** shard optimizer states, gradients, and parameters.

For a model with $N$ parameters, trained on $D$ GPUs with Adam in mixed precision:

$$
\text{Vanilla DP:} \quad M = \underbrace{2N}_{\text{param}} + \underbrace{2N}_{\text{grad}} + \underbrace{12N}_{\text{opt}}
$$

$$
\text{ZeRO-1:} \quad M = 2N + 2N + \frac{12N}{D}
$$

$$
\text{ZeRO-2:} \quad M = 2N + \frac{2N}{D} + \frac{12N}{D}
$$

$$
\text{ZeRO-3 (FSDP):} \quad M = \frac{2N}{D} + \frac{2N}{D} + \frac{12N}{D} = \frac{16N}{D}
$$

ZeRO-3 is the most aggressive. Since parameters are sharded, a GPU does not hold the full layer weights by default. Before a layer runs, FSDP performs an `AllGather` to materialize that layer's parameters, executes the layer, then frees the gathered copy and keeps only the local shard. The same idea applies during backward.

This sounds expensive, but FSDP relies on prefetching. While the current layer computes, the next layer's parameters are gathered in the background. In practice, only one or two FSDP units need to be materialized at once.

The trade-off is clear: ZeRO-3 converts memory pressure into communication pressure. If ZeRO-1 fits, it is usually faster than ZeRO-3 because it avoids continuous parameter gathering during forward and backward. The practical rule is to use the lowest ZeRO stage that fits in VRAM.

FSDP implementation details also matter. FSDP1 flattens parameters into 1D buffers before sharding. That can break optimizers such as Muon, which need full 2D tensor structure. FSDP2 uses `DTensor` to preserve tensor shapes while still distributing them, making it more compatible with modern optimizer designs.

### Tensor Parallelism: Split the Operations

Data Parallelism increases the global batch size. But global batch size cannot grow forever without hurting optimization. When batch size has reached its useful limit and the model still needs more GPUs, Tensor Parallelism (TP) becomes necessary.

TP splits individual tensor operations across GPUs. All TP GPUs process the same data, but each GPU owns only part of a weight matrix and computes part of the output.

For an MLP: $Y = \text{GeLU}(X \times A) \times B$

Split $A$ by columns: $A = [A_1 \mid A_2]$. Split $B$ by rows:

$$
B = \begin{bmatrix} B_1 \\ B_2 \end{bmatrix}
$$

On GPU 1: $Y_1 = \text{GeLU}(X \times A_1) \times B_1$
On GPU 2: $Y_2 = \text{GeLU}(X \times A_2) \times B_2$

$$
Y = Y_1 + Y_2 \quad \xrightarrow{\text{AllReduce}} \quad Y \text{ on all GPUs}
$$

This is the core Megatron-LM trick. The first projection is column parallel, the nonlinearity can be applied independently, and the second projection is row parallel. Only the final partial outputs need to be summed.

Attention uses a similar idea, but the split must preserve mathematical correctness. The useful debugging question is: would each GPU compute the same activations as the non-TP model? Splitting attention along hidden dimensions can break softmax because each GPU sees only part of what softmax should normalize over. Splitting by attention heads works because heads are independent before the output projection.

TP is sample efficient because it does not require additional data batches. It also reduces parameter, gradient, optimizer, and activation memory inside the sharded operations. The cost is communication: every transformer block needs synchronization in forward and backward. For that reason, TP is usually restricted to GPUs connected by very fast intra-node interconnects such as NVLink.

### Sequence Parallelism: Save Activation Memory Around TP

TP has a subtle activation problem. Between tensor-parallel regions, such as around LayerNorm or dropout, activations may be duplicated across the TP group. Sequence Parallelism (SP) reduces that memory by sharding the sequence dimension outside TP regions.

In vanilla TP, the forward pass at the end of a block gathers or reduces partial activations so every GPU holds the full tensor again. With Sequence Parallelism, that synchronization is reshaped into sequence-wise `ReduceScatter` and `AllGather` operations around layers such as LayerNorm. Instead of every GPU holding the full activation tensor $[S, B, H]$, each GPU holds only $[S/D, B, H]$ in the sequence-sharded region. The communication volume is equivalent to the original `AllReduce`, but the activation memory is lower.

The backward pass lines up naturally because `AllGather` and `ReduceScatter` are adjoint collectives. This also synchronizes gradients for non-TP parameters like LayerNorm without an extra explicit `AllReduce`.

### Pipeline Parallelism: Split the Layers

Pipeline Parallelism (PP) splits the model by depth. One GPU or group owns early layers, another owns middle layers, and another owns later layers. Activations are passed from stage to stage in the forward pass; gradients pass backward in reverse.

The advantage is cheap communication. PP mostly sends boundary activations between neighboring stages rather than performing heavy global collectives. That makes it suitable for crossing node boundaries where bandwidth is lower.

The drawback is the pipeline bubble. If stage 2 waits for stage 1, and stage 3 waits for stage 2, much of the cluster can sit idle unless the batch is divided into many micro-batches and scheduled carefully.

The fraction of idle time for a simple 1F1B schedule is approximately:

$$
\text{Bubble Fraction} \approx \frac{P - 1}{m}
$$

Here $P$ is the number of pipeline stages and $m$ is the number of micro-batches. To keep efficiency high, $m$ must be much larger than $P$. That increases the effective global batch size, so PP is constrained by both scheduling and optimization.

Common schedulers include:

- **AFAB:** all forwards, then all backwards. Simple, but leaves large bubbles.
- **1F1B:** one forward and one backward interleaved. Better steady-state utilization, but still has warmup and cooldown bubbles.
- **DualPipe:** a bidirectional schedule popularized by DeepSeek, designed to reduce bubbles through more aggressive overlap.

PP is powerful, but software complexity is high. It interacts with activation checkpointing, micro-batch scheduling, inter-stage communication, and memory planning.

### Context Parallelism: Split Long Sequences

Context Parallelism (CP) is specialized for extremely long contexts. When sequence length reaches hundreds of thousands or millions of tokens, attention's KV cache and attention computation can exceed memory even with other forms of parallelism.

CP shards the sequence dimension across GPUs. The difficulty is that attention needs every query to compare against every key and value. Ring Attention solves this by passing KV blocks around a ring. Each GPU keeps local queries, receives remote key-value blocks in sequence, and updates its local attention result using the online softmax trick from FlashAttention.

Conceptually, attention over sequence blocks $k_1, k_2, \ldots, k_N$ is computed iteratively, with each received KV block updating the local attention result. A running maximum of the dot products is tracked to ensure numerical stability of the exponential function.

CP is valuable when sequence length is the bottleneck. It is not a general-purpose scaling knob for ordinary short-context training, because it is communication heavy.

### Expert Parallelism: Split the Experts

Expert Parallelism (EP) applies to Mixture-of-Experts models. In an MoE layer, a router sends each token to one or more expert feed-forward networks. Since the experts can be large and numerous, they are placed on different GPUs.

The routing flow is:

1. The router computes assignment scores.
2. Tokens are dispatched to the GPUs that host their assigned experts with `All-to-All`.
3. Experts compute token outputs.
4. Outputs are returned to the original token order with another `All-to-All`.

`All-to-All` is one of the most difficult collectives at scale because every GPU sends different data to every other GPU. MoE also introduces load balancing problems. If most tokens route to one expert, the GPU holding that expert becomes the bottleneck while others idle.

A common auxiliary load balancing loss is:

$$
\mathcal{L}_{\text{balance}} = \alpha \cdot E \cdot \sum_{i=1}^E f_i \cdot P_i
$$

Here $E$ is the number of experts, $f_i$ is the fraction of tokens routed to expert $i$, $P_i$ is the average router probability for expert $i$, and $\alpha$ controls the strength of the penalty. Newer methods can avoid adding an auxiliary loss by dynamically biasing router logits to encourage balanced routing.

The hardware bottleneck is severe. Routing decisions are computed on GPU, but communication buffers historically needed CPU-visible sizes. That CPU-GPU synchronization can stall the pipeline. Libraries such as DeepEP use advanced InfiniBand and RDMA features to reduce this bottleneck. Without strong networking, MoE training can be far slower than the theoretical FLOP count suggests.

### Combining Parallelisms Into a Mesh

The important synthesis is that these parallelisms are mostly orthogonal:

- DP shards the batch.
- TP shards tensor dimensions inside layers.
- PP shards model depth.
- CP shards sequence length.
- EP shards experts.

The total GPU count is the product of their degrees:

$$
N_{\text{total}} = d \times t \times p \times c \times e
$$

Where $N_{\text{total}}$ is the total number of GPUs, and $d, t, p, c, e$ are the degrees of Data, Tensor, Pipeline, Context, and Expert parallelism respectively.

Modern frameworks represent this as a communication mesh. Each GPU has coordinates along multiple axes, and collectives operate only along the relevant axis. A TP `AllReduce` should talk only to the TP group. A DP gradient synchronization should talk only to the DP group. An EP `All-to-All` should talk only to the expert group.

<details><summary>The setup looks like this in pseudocode:</summary>

```python
# Pseudocode for Mesh initialization
mesh = init_device_mesh("cuda", (DP_SIZE, PP_SIZE, TP_SIZE))
dp_group = mesh.get_group(0)
pp_group = mesh.get_group(1)
tp_group = mesh.get_group(2)
```

</details>

The exact mesh shape is dictated by hardware:

- TP belongs inside the fastest interconnect domain, usually one NVLink node.
- SP usually comes with TP to reduce activation memory.
- PP can cross node boundaries because it uses point-to-point activation transfers.
- DP scales until the global batch size limit is reached.
- HSDP uses FSDP inside a fast group and DP across slower groups.
- CP is added when context length is the bottleneck.
- EP is added when the model uses many MoE experts.

This means there is no universal best parallelism configuration. The same model can require different meshes on an 8-GPU workstation, an NVSwitch pod, and a multi-rack InfiniBand cluster.

### A Practical Decision Order

A useful engineering heuristic is:

1. Start with the target global batch size and convergence constraints.
2. Use DP while the model fits and the batch size can grow.
3. Add ZeRO/FSDP only to the degree needed for memory.
4. Use TP when the model or activations need intra-layer sharding, keeping TP inside fast interconnects.
5. Add SP with TP to reduce activation memory.
6. Use PP to scale across nodes when TP cannot stretch farther.
7. Add CP only for very long contexts.
8. Add EP only for MoE models, and expect the network to dominate performance.

The general principle is to trade memory for the cheapest available communication. FSDP trades parameter memory for repeated `AllGather`s. TP trades layer memory for frequent `AllReduce`s. PP trades depth memory for scheduling complexity and bubbles. CP trades sequence memory for ring communication. EP trades expert capacity for `All-to-All` routing.

## 4. Smarter Pre-Training: Curricula, Front-Loaded Reasoning, and RLP

Large language model pre-training is entering a different regime. For years, scaling progress came from more parameters, more compute, and more human-generated text. But the supply of useful human text is finite. If projections that most available human-generated data will be consumed by frontier training runs are directionally correct, the key question changes from "How do we get more data?" to "How do we make the model learn more from the data it already has?"

The answer is a shift toward smarter pre-training algorithms. Instead of sampling data randomly according to raw dataset size, a stronger training run should estimate data quality, control repetition, order the curriculum, inject reasoning data early, and eventually make reasoning part of the pre-training objective itself.

The full story can be understood through four training personas:

- **Pascal:** reads randomly, ignores high-quality reasoning data, and does not think before predicting.
- **Volta:** uses a better data blend and a curriculum, but still does not use reasoning data during pre-training.
- **Ampere:** uses curriculum learning and front-loads reasoning data into pre-training.
- **Hopper:** combines curriculum learning, front-loaded reasoning, and reinforcement-style thinking during pre-training.

The progression from Pascal to Hopper captures a larger claim: future pre-training gains will come not only from more tokens, but from changing how models interact with those tokens.

### The Data Wall Changes the Training Problem

State-of-the-art LLM development depends on four broad ingredients:

- **Smart data:** high-quality, diverse, filtered, and deduplicated corpora.
- **Smart architecture:** model designs beyond standard transformers, including hybrid architectures such as Mamba2-based systems.
- **Smart algorithms:** training recipes that go beyond plain next-token prediction.
- **Smart collaboration:** tight coordination between pre-training, post-training, research, and engineering.

This focuses on the third pillar: smart algorithms.

The historical baseline for pre-training is a natural distribution strategy. If a web crawl dataset contains most of the tokens, the model sees most of its training examples from web crawl. If a smaller dataset contains high-quality math, code, or textbook-style material, it receives far less attention simply because it is smaller.

That is not an optimal learning strategy. A model trained this way can spend too much compute on massive low-quality sources while underusing compact, high-value domains. As human-generated data becomes a limiting resource, the training process must become more deliberate.

### From Natural Sampling to Optimal Data Blending

Natural sampling chooses data according to raw token count. If dataset $i$ contains $N_i$ tokens, its sampling probability is:

$$
P(i) = \frac{N_i}{\sum N_j}
$$

An optimal blend should instead account for quality and useful repetition. High-quality data should be weighted more heavily, but it should not be repeated indefinitely. Each domain has a point where additional epochs stop improving downstream performance.

That idea can be summarized as:

$$
W_i = f(\text{Quality}_i, \text{MaxEpochs}_i, N_i)
$$

- $W_i$ (Sampling weight for dataset $i$ ): Determines Phase 1 vs Phase 2 mixtures
- $\text{Quality}_i$ (Estimated quality score): Derived via classifiers (e.g., FineWeb-Edu)
- $\text{MaxEpochs}_i$ (Optimal repetition limit): Derived via ablation studies

The important change is that data is no longer treated as interchangeable. A dataset's role in pre-training should depend on what it teaches, how reliably it teaches it, and how many times the model can benefit from seeing it.

Quality estimation can be automated with classifiers. For general web crawl, tools such as FineWeb-Edu score text by educational value, often on a scale from 1 to 5. For reasoning data, quality depends on correctness, filtering strictness, and the structure of the reasoning trace.

Epoch estimation is more expensive. Researchers train proxy models while varying how many times a domain appears in the mix. If math improves performance up to four repeats but plateaus after that, the training recipe can use that repeat count instead of blindly sampling math forever.

<details><summary>Conceptually, that ablation process looks like this:</summary>

```python
# Conceptual Epoch Estimation Ablation
def test_dataset_repeats(base_mixture, target_dataset, max_repeats=5):
    results = {}
    for epochs in range(1, max_repeats + 1):
        # Increase target dataset weight, decrease web_crawl weight
        test_mixture = adjust_weights(base_mixture, target_dataset, epochs)

        # Train small proxy model
        model = train_model(test_mixture, compute_budget)

        # Evaluate on downstream tasks
        score = evaluate(model, benchmark="MMLU")
        results[epochs] = score

        # Stop if diminishing returns hit
        if epochs > 1 and results[epochs] < results[epochs-1] + threshold:
            return epochs - 1 # Optimal epochs

    return max_repeats
```

</details>

This is compute intensive, but it gives pre-training a more principled foundation. The goal is not just to find good data. The goal is to discover how much of each kind of data the model can productively absorb.

### Why Curriculum Order Matters

Even a good data blend is incomplete if the model sees the mixture in a random order. The analysis proposes a two-phase pre-training curriculum.

**Phase 1 emphasizes diversity.** The model sees broad, varied data, including large web crawls and medium-quality sources. This phase helps the model acquire general language structure, vocabulary, factual breadth, and broad world knowledge.

**Phase 2 emphasizes quality and focus.** The mixture shifts heavily toward high-value domains such as math, code, Wikipedia, STEM material, and other filtered sources. This phase uses the quality and epoch estimates from the earlier data analysis to repeat valuable datasets enough to deepen capability without wasting compute.

This ordering matters. Prioritizing quality before diversity performed worse. Broad exploration needs to come first, followed by focused exploitation. The curriculum resembles a human learning sequence: first build general language and world knowledge, then concentrate on harder domains.

Empirically, the curriculum-based Volta setup outperformed the naive Pascal baseline by about 17% on average. The raw data can be the same, but the order and weighting of that data materially change the final model.

### Front-Loading Reasoning Into Pre-Training

The standard LLM training pipeline separates reasoning from pre-training:

1. **Pre-training:** learn from massive unannotated text through next-token prediction.
2. **Supervised Fine-Tuning (SFT):** learn response formats, instruction-following behavior, and reasoning traces from prompt-response examples.
3. **Reinforcement Learning (RLHF/RLVR):** improve alignment or task performance using rewards.

The weakness of this pipeline is that it treats reasoning as a post-training add-on. The base model learns language and facts first, then SFT and RL try to install reasoning behavior later.

Front-loading reasoning challenges that separation. The idea is to move high-quality reasoning traces into the pre-training phase, when the learning rate is high and the model's core representations are still being shaped. Instead of waiting until SFT to show the model step-by-step math, code, logic, and problem-solving traces, the model sees some of that material while forming its foundation.

Reasoning data can be categorized along three axes:

- **Quantity:** how many reasoning tokens are available.
- **Quality:** how correct, clear, and well-filtered the traces are.
- **Diversity:** how many domains are represented, such as math, code, logic, STEM, or legal reasoning.

The study described three dataset categories:

- **SHQ:** small quantity, low diversity, high quality.
- **LDQ:** large quantity, large diversity, low quality.
- **LMQ:** a combined mixture of SHQ and LDQ.

The controlled comparison is between Volta and Ampere. Volta uses the curriculum but no reasoning data during pre-training. Ampere uses the same curriculum strategy while injecting reasoning data early.

The results are the central argument for front-loading:

- Before any fine-tuning, the reasoning-pretrained Ampere model outperforms the no-reasoning Volta model by 16% on reasoning benchmarks.
- After both models receive identical SFT, Ampere still keeps a 9.3% lead.
- Mixing high-quality reasoning data with lower-quality diverse reasoning data may not show immediate gains at the base-model stage, but after SFT the mixed LMQ setup shows a 4.25% boost.
- Doubling SFT compute for the no-reasoning base does not close the gap. The reasoning-pretrained model with normal SFT still wins by 3%.
- Under a fixed reasoning-token budget, splitting the data between pre-training and SFT beats saving all reasoning data for SFT by 12%.

The last point is especially important. If a team has a limited supply of reasoning traces, the best use is not necessarily to reserve all of them for supervised fine-tuning. Some of that data should shape the base model itself.

In plain terms, reasoning data has more leverage when it participates in the formation of the base model. SFT can teach a model to imitate reasoning formats, but it cannot fully compensate for a foundation that never learned the structure of reasoning during pre-training.

Across the full pipeline of pre-training, SFT, and RL, the front-loaded Ampere model maintains a 19% average advantage over Volta, including a 39% advantage on AIME-style difficult math benchmarks.

### RLP: Reinforcement Learning as a Pre-Training Objective

Front-loaded reasoning still depends on annotated reasoning traces. RLP, or Reinforcement Learning for Pre-training, goes further. It asks whether the model can learn to reason during pre-training without requiring a curated reasoning dataset or an external verifier.

The contrast is between two learning styles:

- **Bolt:** learns by observing text and predicting the next token.
- **Leo:** learns by doing, generating internal thoughts and receiving feedback on whether those thoughts helped.

Standard next-token prediction is imitation learning. Given context $C$, the model predicts the next token $x$ and receives a cross-entropy penalty if it assigns too little probability to the true token. It learns to mimic the observed corpus.

RLP modifies this loop. Before predicting the next token, the model generates an internal thought or reasoning trace. It then predicts the next token using both the original context and that thought. The training signal asks a simple question: did the thought make the model better at predicting the actual next token?

The RLP pipeline has six steps:

1. **Input context:** sample a chunk of ordinary pre-training text.
2. **Thought generation:** prompt the active model to generate a reasoning trace focused on the next step.
3. **Prediction with thought:** predict the next token using the context plus the generated thought.
4. **Baseline prediction:** use a no-think baseline model to predict the same token from context alone.
5. **Reward calculation:** reward the active model according to the information gain from thinking.
6. **Model update:** update the thought policy with an RL algorithm, while updating the baseline through an exponential moving average.

The reward is:

$$
R = \log(p_\theta) - \log(p_\phi)
$$

- $R$ (Reward): Dense, continuous scalar value
- $p_\theta$ : ( $P(\text{next token} \mid \text{context}, \text{thought})$ ) : Probability from the active Thought Policy
- $p_\phi$ : ( $P(\text{next token} \mid \text{context})$ ): Probability from the lagged No-Think Baseline

If $p_\theta > p_\phi$, the generated thought helped. If $p_\theta < p_\phi$, the thought made the prediction worse. This makes the reward dense and self-supervised: it can be computed for ordinary pre-training text because the next token is already known.

This is the key advantage over sparse RL setups. A sparse reward might only tell a model whether a final answer was correct. RLP gives a continuous signal at token level, measuring how much the thought improved prediction.

The no-think baseline must stay close to the active model. If it is static, the active model eventually beats it too easily and the reward becomes less meaningful. If it updates instantly, the reward collapses toward zero. RLP therefore updates the baseline through an exponential moving average:

$$
\phi_t = \beta \cdot \phi_{t-1} + (1 - \beta) \cdot \theta_t
$$

- $\phi_t$ ( Parameters of No-Think Baseline at step $t$ ): Used to compute $p_\phi$
- $\theta_t$ ( Parameters of Thought Policy at step $t$ ): The actively training model
- $\beta$ ( Decay rate e.g., 0.999): Controls how fast the baseline tracks the policy

<details><summary>In code, the reward computation can be represented as:</summary>

```python
# RLP Information Gain Reward
with torch.no_grad():
    # 1. Baseline predicts next token probabilities without thought
    logits_no_think = baseline_model(context)
    p_phi = get_probs(logits_no_think, target_token)

# 2. Active policy generates a thought
thought = active_model.generate(context, prompt="Think step by step:")

# 3. Active policy predicts next token with the thought
logits_think = active_model(context + thought)
p_theta = get_probs(logits_think, target_token)

# 4. Calculate Information Gain Reward
reward = torch.log(p_theta) - torch.log(p_phi)

# 5. Apply standard RL algorithm (e.g., PPO or GRPO) using this reward
loss = rl_algorithm(active_model, context, thought, reward)
loss.backward()

# 6. Update baseline via EMA
update_ema(baseline_model, active_model, beta=0.99)
```

</details>

The underlying RL optimizer is GRPO, the same broad family of methods associated with reasoning-oriented systems such as DeepSeek R1. The difference is the reward. Standard GRPO for reasoning often uses a binary correctness reward. RLP replaces that with dense information gain. That makes RLP verifier-free. It does not need a human preference model, a math answer checker, or an external LLM judge. It can train on any document where the next token is available.

### What RLP Achieves

RLP produced several notable empirical results:

- On a Qwen 1.7B model trained for 1 billion RLP tokens, RLP beat standard next-token pre-training on the same number of tokens by 17%.
- Because RL is more computationally expensive per token, the study also compared 170 million RLP tokens against 6 billion standard next-token tokens under equal FLOPs. RLP still won by 14%.
- On a 12B parameter hybrid Mamba2 model, applying RLP to just 250 million tokens near the end of a 20 trillion token run improved performance by 35% compared with the 20T-token baseline.
- Compared with other early-reasoning methods such as RPT or Quiet-STaR-style approaches, RLP outperformed by about 4% while avoiding external verifiers and sparse binary rewards.

One of the most striking details is that RLP also helps on unannotated web crawl. The reported gains of 7-9% on ordinary web text imply that the model is not merely memorizing math-solution formats. It is learning when internal reasoning helps predict normal human text.

RLP token selection is random. The method does not only target the hardest words. It samples tokens uniformly across documents. This sounds inefficient, but the dense reward handles the difference. If a token such as "the" does not benefit from reasoning, the information gain should be near zero. If a token requires understanding the causal or logical structure of a sentence, the thought can earn a positive reward.

RLP also works before the end of training. Although one headline experiment applied it near 19.8 trillion tokens, experiments at about 20% of the training run, around 4 trillion tokens, still showed significant gains. That matters because it frames RLP as a true pre-training method, not only a final polishing step.

### Practical Lessons

**Quality is measurable, but not trivial.** For web crawl, quality can be estimated with classifiers such as FineWeb-Edu. For reasoning data, quality usually means correctness, structure, and filtering strictness. A dataset such as OpenThoughts represents heavily filtered reasoning traces, while broader STEM-oriented SFT data may be larger and more diverse but less clean.

**Reasoning data has a recognizable format.** The examples typically contain a question, a long step-by-step reasoning trace, and a final solution. This format makes reasoning explicit enough to shape model behavior during pre-training.

**Epoch estimation requires domain-level ablations.** The mixture is not fully hand-tuned, but it is also not free. Quality scoring can be automated, while repetition limits require experiments. Researchers increase repeats for a domain such as math, train proxy models, and stop when downstream metrics plateau.

**GRPO is a training algorithm, not the core novelty.** RLP uses GRPO under the hood, but its distinctive contribution is the reward signal. Replacing sparse correctness rewards with dense information gain makes reinforcement learning usable inside pre-training.

**RLHF and RLP solve different problems.** RLP teaches a model to reason and deduce. RLHF or RLVR still matters later for preference alignment, helpfulness, safety, and task-specific behavior. RLP does not remove the need for post-training.

**RLHF has known failure modes.** RLAIF, or reinforcement learning from AI feedback, is one research direction for reducing some human-feedback biases, but final-stage RL remains important across the industry.

### The Larger Training Recipe

The complete Hopper methodology combines four ideas:

1. Build an optimal data blend using quality estimation and epoch estimation.
2. Train with a two-phase curriculum: diversity first, quality second.
3. Front-load reasoning data into pre-training instead of reserving it all for SFT.
4. Use RLP so the model learns to generate useful internal thoughts while predicting ordinary text.

Together, these strategies can yield up to a 60% relative improvement over a naive Pascal-style baseline trained on the same raw data. That result is important because it reframes scaling. The next major gains may not require discovering entirely new text sources. They may come from training models to use existing tokens more intelligently.

Several broader lessons follow.

First, the "one pass over data" intuition is too simple. High-quality domains such as math and code can be profitably repeated, as long as repetition is measured and bounded.

Second, base-model evaluation can understate future potential. High-quality reasoning data may create latent capabilities that only appear after SFT. If researchers only evaluate immediately after pre-training, they may miss important downstream gains.

Third, SFT cannot repair every weakness in the foundation model. Extra SFT compute and extra SFT data did not erase the advantage of front-loaded reasoning. The base model's weights impose a real ceiling.

Fourth, RLP turns reasoning into a pre-training behavior rather than a post-training style. By rewarding thoughts according to information gain, the model learns when thinking improves prediction and when it does not.
