# How Modern AI Models Are Built: Data, Alignment, Multimodality, and Efficient Inference

Modern AI is often described through parameter counts, benchmark scores, and increasingly capable product demonstrations. Those measures capture the visible result, but they conceal the larger system that makes the result possible. A model's behavior begins with decisions about which data to collect and preserve, continues through post-training and reinforcement learning, expands through architectures that connect language with images and video, and finally depends on inference software that can serve every token efficiently.

Viewed together, these stages reveal a consistent pattern: progress comes from choosing the right representation, objective, and constraint at each layer of the stack. Data filters define what the model learns. Alignment data turns latent capabilities into useful behavior. Verifiers and environments determine which reasoning strategies reinforcement learning rewards. Multimodal encoders decide what visual information survives. Serving systems and recurrent architectures determine how economically those capabilities can run.

The development of a modern AI system is best understood as a sequence of transformations. Raw documents become filtered and deduplicated tokens; broad pre-trained capabilities become an assistant interface; preference data and verifiable environments shape behavior; continuous media becomes a representation a language model can use; and trained weights become a service through careful control of computation and memory.

Each transformation introduces its own bottleneck and its own definition of quality. A larger crawl is not automatically a better corpus. A stronger reward signal is not useful if the policy can exploit it. A unified multimodal vocabulary is not necessarily better if it destroys visual detail. More GPU throughput does not help if decode remains constrained by memory movement. Improvements at one stage also change the requirements of the next, which is why isolated optimization increasingly gives way to full-stack co-design.

The durable lesson is that capable AI depends on far more than scale. It depends on provenance, filtering, representation, incentives, verification, memory, and execution—all aligned around the behavior the system is meant to produce. The frontier will continue to move, but these engineering questions will remain central to building models that are not only more capable, but also more reliable, efficient, and understandable.

## 1. Data Is the Moat: How Training Corpora Shape Large Language Models

The architecture of a modern large language model attracts most of the attention, but the data pipeline often determines what the model can actually do. Leading laboratories publish model sizes, optimization strategies, and benchmark results while revealing far less about the corpora behind them. That imbalance is not accidental. Data is both a competitive advantage and a source of legal exposure.

Building a training corpus is also much harder than collecting “the internet.” Teams must acquire content, extract usable text, verify access rights, remove duplicates and sensitive information, score quality, balance domains, and defend against adversarial manipulation. Each decision changes the distribution from which the model learns.

### The Training Pipeline Narrows as Quality Rises

Language-model development usually divides data into three broad stages:

| Stage         | Typical data                                                                   | Quality                     | Scale                           |
| :------------ | :----------------------------------------------------------------------------- | :-------------------------- | :------------------------------ |
| Pre-training  | Raw web documents, papers, books, code                                         | Low to medium               | Trillions of tokens             |
| Mid-training  | Curated web data, long-context documents, domain data, synthetic data          | High                        | Billions to trillions of tokens |
| Post-training | Conversations, preference data, math, coding, safety examples, RL environments | Very high and task-specific | Millions to billions of tokens  |

Pre-training produces a broadly capable base model. Mid-training strengthens selected capabilities without restarting the process, while post-training turns the model into a useful assistant through instruction tuning, preference optimization, and task-specific reinforcement learning.

The boundaries are increasingly blurry. Some frontier developers publish only a finished chat model, without checkpoints that cleanly separate pre-training, mid-training, and post-training. Fully open projects such as OLMo are therefore unusually valuable: they expose the data and intermediate stages needed to study how each phase affects model behavior.

### Why “The Internet” Is Not a Dataset

The web is a collection of live services, not a static corpus. A conventional pre-training run cannot interact with those services continuously, so developers train on snapshots created by crawlers or bulk downloads.

A basic crawler treats the hyperlink network as a directed graph. It begins with seed URLs, downloads pages, extracts links, and adds those links to a traversal queue:

Production crawling is substantially more difficult. Crawlers must canonicalize URLs, avoid mirrors and duplicate pages, prioritize frequently changing sites, distribute requests across machines, respect per-domain rate limits, and decide when old pages should be fetched again.

Common Crawl has archived billions of pages per crawl since 2007. It distributes raw HTTP records in WARC files and extracted plaintext in WET files. WARC preserves the response, headers, and HTML; WET is convenient but lossy.

That distinction matters. Reprocessing WARC HTML with specialized extraction tools such as `trafilatura` or `resiliparse` can produce better training text than relying on the corresponding WET output. Boilerplate removal, navigation handling, and main-content extraction are not merely storage details—they measurably affect downstream model quality.

Responsible collection also requires operational restraint. A crawler that sends excessive traffic can degrade a service even when no copyright issue is involved. Politeness delays, rate limits, and official bulk-download channels are therefore part of the data design, not optional courtesy.

Most online text is copyrighted automatically when it is created and fixed in a tangible form. Public availability does not mean public-domain status, and ideas being free to use does not make a particular expression of those ideas unprotected.

Fair use in the United States is a balancing test based on purpose, the nature of the original work, the amount used, and the effect on the work’s market.

No factor decides the outcome alone. Training has a potentially transformative character because a model extracts statistical structure rather than simply distributing a copy. At the same time, using entire works and producing outputs that substitute for the originals may weigh against fair use. Copyright analysis also goes beyond literal n-gram overlap: protected expression can be reproduced semantically through plots, characters, or other distinctive elements.

The legal snapshot summarized in the source material draws a critical distinction between training and acquisition. Recent litigation has supported the view that model training can be transformative, while obtaining books through unauthorized shadow libraries remains a separate infringement risk. Buying and scanning a book is not legally equivalent to downloading a pirated copy, even if both copies later enter the same training process.

Terms of service must be checked independently. A fair-use argument about training does not necessarily authorize scraping a service whose contract prohibits bots. A responsible pipeline must therefore record, separately, the work's copyright status, the license or legal basis for reuse, how the copy was obtained, and whether automated access complied with the service's terms.

This is a conceptual framework, not legal advice. Its value is in showing that the right to train, the right to obtain a copy, and the right to automate access are related but distinct questions.

### How Pre-Training Datasets Evolved

Public dataset design changed rapidly between 2018 and 2026. The field moved from small curated collections to rule-filtered web crawls, then to learned quality classifiers and LLM-assisted scoring.

#### From curated corpora to web-scale filtering

BERT used Wikipedia and BooksCorpus, amounting to roughly 16 GB. Its document-level context was important, but BooksCorpus later became a warning about terms-of-service compliance.

GPT-2’s WebText used Reddit engagement as a human quality proxy: pages linked from posts with at least a small amount of positive karma were treated as more promising than arbitrary web pages. The proprietary dataset was never released, prompting the open OpenWebText replication.

CCNET introduced multilingual Common Crawl processing with language identification and a Wikipedia-trained language model as a quality signal:

$$
\text{quality}(d) = -\log P_{\text{Wikipedia-LM}}(d)
$$

The more probable a document appears under a Wikipedia-trained model, the more Wikipedia-like—and, by this proxy, the higher quality—it is.

C4 took a transparent rule-based route. It retained sufficiently long, well-punctuated English text while removing short pages, boilerplate, blocked words, and code-like content. Its success showed that Common Crawl could become a usable corpus when processed aggressively.

GPT-3 combined Common Crawl with WebText, books, and Wikipedia. It used a learned classifier to distinguish higher-quality WebText-like documents from ordinary crawl data and added fuzzy deduplication. The approach established quality classification as a scalable alternative to handwritten rules.

#### Source diversity and its legal cost

The Pile combined web pages with PubMed, arXiv, GitHub, Wikipedia, Stack Exchange, public-domain books, emails, and other specialized sources. Its diversity influenced many later open datasets, but Books3—derived from a shadow library—became a major legal liability inherited by downstream projects.

DeepMind’s MassiveWeb/Gopher pipeline preferred manual rules to learned filters, emphasizing transparency and concern about classifier bias. Llama 1 combined several established sources and used Wikipedia citations as a quality signal, keeping pages referenced by Wikipedia rather than merely pages that resembled it.

RefinedWeb advanced the argument that careful extraction and deduplication could make Common Crawl alone sufficient. FineWeb expanded that philosophy across many crawl snapshots while improving deduplication and personally identifiable information removal. Dolma returned to a mixed-source approach, combining web, code, social, and scholarly data with language, quality, and toxicity filters.

#### Classifiers, LLM scoring, and synthetic augmentation

DCLM began with an unfiltered pool of roughly 240 trillion tokens and retained about 3.8 trillion. Its fastText classifier learned from instruction-style positive examples and ordinary web negatives:

$$
\text{DCLM filtered} = \{d \in \text{DCLM-pool} \mid f_{\text{fastText}}(d) > \theta\}
$$

The 98.6% rejection rate makes the importance of the threshold concrete. A quality classifier does not simply clean a dataset; it defines the distribution that the eventual model will see.

Nemotron combined the DCLM signal with an educational-value classifier trained from LLM-generated labels. It also used synthetic augmentation: lower-quality documents could be rewritten in a more informative style, while higher-quality documents could produce summaries, questions, answers, or extraction tasks.

This development creates a new tension. Synthetic data can increase density and structure, but repeated training on model-generated text may reduce diversity or reinforce the scorer’s preferences. DCLM’s use of GPT-4-derived instruction data as a positive quality signal is similarly circular: one model’s style helps define what counts as good data for the next.

#### Three filtering philosophies

| Method             | Strength                        | Weakness                       | Representative datasets         |
| :----------------- | :------------------------------ | :----------------------------- | :------------------------------ |
| Manual rules       | Transparent, fast, controllable | Rigid and labor-intensive      | C4, Gopher, RefinedWeb, FineWeb |
| Learned classifier | Adaptive and efficient at scale | Inherits labels and biases     | GPT-3, DCLM                     |
| LLM scoring        | Rich semantic quality signal    | Slow, costly, scorer-dependent | Nemotron label generation       |

There is no universally best method. Rules preserve representativeness but miss subtle defects. Classifiers recognize patterns that rules cannot express but encode the definition of quality found in their training examples. LLM scores are more expressive still, yet amplify cost and dependence on the scoring model.

### Code Data Requires Its Own Architecture

The Stack project demonstrates why collecting source files is not enough. High-quality code data needs licensing checks, near-deduplication, secret and PII removal, malware filtering, bot filtering, language balancing, and representations of the development process.

The Stack V1 filtered a very large set of public repositories down to permissively licensed, near-deduplicated code. The Stack V2 used Software Heritage for stable repository content and added issues, pull requests, comments, and documentation. These records teach a model why code changes, how defects are discussed, and how reviewers evaluate a patch.

#### LLVM IR as a cross-language bridge

Low-resource languages contain too little code for a model to learn robust semantics directly. LLVM intermediate representation offers a shared target for languages such as C, C++, Rust, Swift, and some lower-resource languages:

```text
Nim source code
     ↓ (Nim compiler → LLVM backend)
LLVM IR
     ↑ (also from C, Rust, C++, Swift, ...)
```

Training on source-and-IR pairs lets the model connect scarce syntax to semantics learned from higher-resource languages.

Several research directions follow directly from this view of data:

- **Principled quality metrics:** Existing filters often rely on handwritten intuitions, proxy labels, or the preferences of another model.
- **Provenance tracking:** Dataset lineage must survive aggregation, redistribution, and synthetic transformation if legal and scientific claims are to remain auditable.
- **Scalable near-deduplication:** Detecting mirrors, forks, templates, and lightly edited copies across hundreds of terabytes remains expensive.
- **Optimal source mixing:** The best proportions of web, code, books, science, dialogue, and synthetic data depend on the capabilities being targeted.
- **Adversarial robustness:** Predictable snapshots and open contribution systems create poisoning opportunities even in trusted sources.
- **Synthetic-data dynamics:** Researchers still need to establish when generated data increases useful structure and when it narrows diversity or leads to model collapse.
- **Permissive-data discovery:** Better indexing of public-domain, government, educational, and genuinely open material could reduce dependence on legally ambiguous corpora.

## 2. From Raw Web Pages to Reasoning Traces: Engineering Data for Large Language Models

The performance of a large language model depends on far more than how much data it sees. Before a single training token reaches the model, raw web pages must be converted into text, low-value documents must be filtered out, duplicate material must be removed, and heterogeneous sources must be combined without repeatedly exhausting the smallest datasets. After pre-training, a second pipeline must create task-specific examples that teach reasoning, coding, and tool use.

These stages form a connected system. Text extraction determines what information survives. Filtering defines what the pipeline calls “quality.” Deduplication determines how much genuinely distinct information remains. Mixing controls how often each source appears during training. Synthetic generation then turns curated tasks and environments into post-training trajectories.

### Turning Raw Documents into Trainable Text

Training begins with raw bytes rather than clean prose. Most web data arrives as HTML, while a smaller but often valuable fraction appears as PDFs. Code data introduces still other structures, including repository trees, commit histories, issues, and pull requests. Every format must eventually become a one-dimensional token sequence.

That conversion is inherently lossy:

$$
\text{HTML/PDF} \xrightarrow{\text{extraction}} \text{Text} \xrightarrow{\text{tokenization}} \text{Token sequence}
$$

HTML at least contains semantic hints. Tags such as `<h1>`, `<p>`, `<nav>`, and `<table>` distinguish headings, paragraphs, navigation, and tabular material. An extractor can use those hints to remove boilerplate and identify the main content. Even so, “content” has no perfectly clean boundary. Navigation may be irrelevant to an article but useful for learning the structure of a website. A table may convert neatly to Markdown, or it may contain nested relationships that cannot be flattened without destroying meaning.

<details><summary>A rule-based extractor looks like this:</summary>

```python
def html_to_text(html_bytes):
    dom = parse_html(html_bytes)

    # Step 1: Remove boilerplate elements
    for tag in ["nav", "header", "footer", "aside", "script", "style", "ads"]:
        dom.remove_all(tag)

    # Step 2: Extract main content body
    main_content = dom.find_main_content()  # heuristic: largest text block

    # Step 3: Linearize remaining structure
    text = ""
    for node in main_content.traverse():
        if node.is_table():
            text += render_as_markdown_table(node)  # may fail for nested
        elif node.is_text():
            text += node.text + "\n"

    return text.strip()
```

</details>

Production pipelines usually favor fast rule-based libraries because extraction must run across enormous crawls. Tools such as `trafilatura` and `resiliparse` make different heuristic choices, and those choices measurably affect downstream model quality. In comparisons reported around DataComp-LM, Common Crawl’s pre-extracted WET text formed a weaker baseline than reprocessing the underlying HTML, with Resiliparse performing particularly well on extended evaluations. A small, sufficiently fast model could eventually resolve layouts that defeat fixed rules, but only if its quality gain justifies its web-scale inference cost.

PDF extraction is harder because PDF is a layout format rather than a semantic document format. It records where characters appear on a page, not which characters form a heading, paragraph, footnote, or table. Multi-column layouts, mathematical notation, and figures must therefore be reconstructed from position. Scanned PDFs contain no machine-readable text at all and require OCR, potentially through a vision-language model at much greater cost.

Common Crawl may also truncate large PDFs, forcing a pipeline to identify and recrawl the original files. Projects such as FinePDFs address these problems by separating ordinary text extraction from expensive OCR and by cleaning the result after conversion. The payoff can be worthwhile: PDFs are a small share of the web, but many are deliberate, high-effort documents such as papers, reports, and manuals. That is a useful quality prior, though not a guarantee—spam, forms, and autogenerated PDFs remain part of the distribution.

The broader point is that extraction is not neutral preprocessing. It is the first learned-distribution decision. Whatever the extractor discards can never be recovered by later stages.

### Filtering Defines What “Quality” Means

Once documents have been converted to text, the pipeline must decide which ones deserve training compute. A useful general formulation begins with a small target set $T$ that represents the desired material and a much larger raw pool $R$:

$$
\text{Target } T \text{ (small, high-quality)} + \text{Raw } R \text{ (huge, mixed)} \longrightarrow \text{Filter } \longrightarrow S \subseteq R
$$

The objective is not to rediscover $T$. It is to learn enough from $T$ to identify new documents in $R$ that share its useful properties. The resulting filter must generalize, produce a scalar score, and remain cheap enough to evaluate across tens or hundreds of trillions of tokens.

Two families of models fit this requirement:

| Approach               | Mechanism                                                                     | Typical tool        |
| :--------------------- | :---------------------------------------------------------------------------- | :------------------ |
| Generative scoring     | Train a language model on $T$ and measure how surprising each raw document is | KenLM 5-gram model  |
| Discriminative scoring | Treat $T$ as positive data and sampled raw documents as negatives             | fastText classifier |

A KenLM-style score can be written as per-token cross-entropy:

$$
\text{score}_{\text{KenLM}}(d) = -\frac{1}{|d|} \sum_{t=1}^{|d|} \log P_{\text{KenLM}}(w_t \mid w_{t-4}, \ldots, w_{t-1})
$$

Here, lower values mean that the document resembles the target distribution. A fastText classifier instead learns a linear boundary over n-gram features:

$$
\hat{y}(d) = \sigma\left(\mathbf{w}^\top \phi(d) + b\right), \quad \text{keep } d \text{ if } \hat{y}(d) > \theta
$$

Because both models are simple, they can score web-scale collections far more cheaply than a neural language model. The target can encode general quality, language, educational value, mathematical content, toxicity, or almost any other property for which examples can be assembled.

#### Language, domain, and quality filters

Language identification is one of the most mature applications. Meta’s fastText language-identification model supports 176 languages and performs well for ordinary documents, although short text, dialects, and code-switching remain difficult edge cases.

Toxicity filtering can likewise use word lists or learned classifiers. The Jigsaw Toxic Comments dataset, built from Wikipedia talk-page discussions, is a common source of labels. Its domain is also a warning: toxicity expressed in forums, social media, or code communities may look different from Wikipedia conversation. A classifier can be fast and accurate on its benchmark while still defining the wrong boundary for a broader crawl.

Domain filters use the same framework. OpenMathText, for example, progressively narrows Common Crawl through explicit LaTeX signals, a ProofPile-trained KenLM, and a fastText math classifier:

```text
All of Common Crawl
    → Rule filter: contains LaTeX commands?
    → KenLM filter: perplexity < θ under ProofPile 5-gram model
    → fastText filter: P(math) > τ_1 (with LaTeX) or P(math) > τ_2 (without LaTeX)
    → 15 billion math tokens
```

The pipeline uses a lower classifier threshold when LaTeX is already present and a higher threshold when it is not. This combines learned scoring with domain knowledge rather than asking a single classifier to do everything. Models trained on the resulting 15 billion filtered tokens outperformed counterparts trained on 300 billion generic tokens in the reported math evaluations—a striking example of quality beating raw volume within a fixed task.

General-quality filters differ mainly in how they define $T$. GPT-3 used Wikipedia, WebText, and books as positives against Common Crawl negatives. Llama 1 used pages cited by Wikipedia, capturing sources that Wikipedia editors considered worth referencing without forcing every retained page to resemble Wikipedia’s own encyclopedic style.

```python
import fasttext

# Step 1: Prepare training data
# T = target (high quality), R = raw (negative examples)
with open("train.txt", "w") as f:
    for doc in target_set_T:
        f.write(f"__label__quality {doc}\n")
    for doc in sample(raw_set_R, len(target_set_T)):  # balance classes
        f.write(f"__label__raw {doc}\n")

# Step 2: Train fastText classifier
model = fasttext.train_supervised("train.txt", lr=0.1, epoch=5, wordNgrams=2)

# Step 3: Score and filter raw dataset
theta = 0.7  # tunable — higher = stricter quality, smaller dataset
filtered = []
for doc in raw_set_R:
    label, prob = model.predict(doc)
    if label[0] == "__label__quality" and prob[0] > theta:
        filtered.append(doc)

# Result: filtered ⊂ R, approximately distributed like T
```

#### The optimal threshold depends on the training budget

A quality threshold is not universally good or bad. Raising $\theta$ produces a smaller and cleaner dataset; lowering it retains more diversity. The correct setting depends on how many tokens the eventual model will consume:

$$
\theta^* = \arg\min_\theta \mathcal{L}(\text{train}(f_\theta(R), N_{\text{train}}))
$$

where $f_\theta(R) = \{d \in R : \text{score}(d) > \theta\}$ and $\mathcal{L}$ is the downstream loss after training on $N_{\text{train}}$ tokens.

Strictly filtered data often wins early because every token carries more useful signal. If training continues for many epochs, however, the finite clean set may be exhausted and overfit. A larger, noisier set can continue supplying new information. Experiments with a 157-million-parameter model illustrated this crossover: DCLM-filtered data achieved lower early loss, while a larger Resiliparse-extracted set eventually caught up after extended training.

This explains why published filtering thresholds cannot be interpreted without their token budgets. Quality is relative to the intended capability, and the quality–quantity balance is relative to the length of the run.

### Deduplication Protects Compute and Evaluation

Filtering scores one document at a time. Deduplication asks whether two documents contain the same information, making it an inherently relational problem.

Duplicates waste GPU time, increase memorization, and distort the effective training distribution. They can also elevate copyright risk by presenting the same passage many times. A particularly important special case is decontamination: removing overlap between training material and evaluation benchmarks. General deduplication improves efficiency, but decontamination protects the scientific validity of reported results.

Real corpora contain both exact and near duplicates. License text may appear across millions of repositories. News articles are syndicated with small edits. Templates change only an entity name. One product description was reportedly repeated 61,000 times in C4. Even a small duplication rate becomes enormous at web scale.

#### Exact duplicates are the easy case

Exact deduplication hashes every document and retains one representative from each hash bucket. The operation is linear in the number of documents and maps naturally onto distributed processing.

The method misses minor changes in whitespace, punctuation, or wording. Span-level deduplication can catch repeated fragments, but it creates a different problem. C4 removed repeated three-sentence spans from otherwise retained documents; doing so reduces repetition but can leave incoherent gaps in the surrounding text.

#### Near duplicates require a similarity measure

To compare documents approximately, represent each document as a set of overlapping word or character n-grams called shingles. Jaccard similarity measures their overlap:

$$
J(A, B) = \frac{|A \cap B|}{|A \cup B|}
$$

For example:

$$
J(\{1,2,3,4\}, \{1,2,3,5\}) = \frac{|\{1,2,3\}|}{|\{1,2,3,4,5\}|} = \frac{3}{5} = 0.6
$$

A pipeline might declare $A$ and $B$ near duplicates when $J(A,B) \geq 0.9$ or $0.99$. Computing Jaccard similarity for every pair is impossible, however: $n$ documents create $\binom{n}{2}=O(n^2)$ comparisons.

MinHash replaces direct comparisons with probabilistic signatures. For a suitable random hash family, the probability that two sets have the same minimum hash equals their Jaccard similarity:

$$
\Pr_{h \sim \mathcal{H}_{\min}}\left[\min_{a \in A} h(a) = \min_{b \in B} h(b)\right] = J(A, B)
$$

The intuition comes from random permutations. Consider the first element of $A \cup B$ under a random ordering. The two sets share the same minimum exactly when that first element belongs to $A \cap B$, which occurs with probability $|A \cap B|/|A \cup B|$.

For text, repeating this estimate across many hash functions turns each document into a compact vector of minimum hash values. This compresses a potentially large shingle set into a fixed-length signature. It makes pairwise comparison cheaper, but comparing every signature with every other signature would still be quadratic. Locality-Sensitive Hashing supplies the final scaling step.

### Locality-Sensitive Hashing Creates a Similarity Threshold

A single MinHash collision has probability $s=J(A,B)$. That relationship is useful but too noisy for a clean deduplication decision. A pair with $s=0.95$ still fails to collide 5% of the time, while a pair with much lower similarity may collide by chance.

MinHash LSH combines many hashes using an AND–OR structure. Divide $n$ hashes into $b$ bands of $r$ rows, so $n=b\times r$. Two documents become a candidate pair if every hash matches within at least one band:

$$
\text{collision}(A, B) = \bigvee_{i=1}^{b} \bigwedge_{j=1}^{r} [h_{i,j}(A) = h_{i,j}(B)]
$$

If the documents have Jaccard similarity $s$, all $r$ hashes in one band match with probability:

$$
\Pr[\text{band } i \text{ matches}] = s^r
$$

No band matches with probability:

$$
\Pr[\text{no band matches}] = (1 - s^r)^b
$$

Therefore:

$$
P_{\text{collide}}(s; b, r) = 1 - (1 - s^r)^b
$$

This function has an S-shaped transition. Increasing $r$ makes each band harder to trigger, moves the transition toward higher similarity, and suppresses false positives. Increasing $b$ creates more chances for a match, moves the transition toward lower similarity, and suppresses false negatives.

For $b=5$, $r=10$, and $s=0.8$:

$$
P_{\text{collide}}(0.8) = 1 - (1 - 0.8^{10})^5 = 1 - (1 - 0.107)^5 \approx 0.40
$$

An approximate center for the transition is:

$$
\tau \approx \left(\frac{1}{b}\right)^{1/r}
$$

At this point, each band matches with probability $1/b$, giving:

$$
P_{\text{collide}}(\tau) \approx 1 - (1 - 1/b)^b \approx 1 - e^{-1} \approx 0.632
$$

With the large parameters $b=20$ and $r=450$:

$$
\tau \approx (1/20)^{1/450} \approx e^{-\ln(20)/450} \approx 0.993
$$

The resulting detector is extremely strict: only documents sharing roughly 99.3% of their shingle vocabulary are likely to fall above the transition. Large $b$ and $r$ make the curve sharper, but pairs exactly at the approximate threshold still collide only about 63.2% of the time. For that reason, $b$ and $r$ should be selected against acceptable false-positive and false-negative rates rather than treated as a universal recipe.

A full pipeline constructs signatures, assigns their bands to buckets, generates candidate pairs from shared buckets, and optionally verifies those pairs with exact Jaccard similarity. LSH does not prove that a pair is duplicated; it reduces an impossible all-pairs search to a manageable set of candidates. Exact verification then removes accidental collisions at a cost proportional to the candidate set rather than $n^2$.

Cross-source deduplication is especially important. The same paragraph can appear independently in Wikipedia, Common Crawl, books, and specialized corpora. Deduplicating each source in isolation leaves that redundancy intact.

### Data Mixing Is an Epoch-Budget Problem

After extraction, filtering, and deduplication, the corpus contains multiple sources with different sizes and strengths: filtered web pages, Wikipedia, books, code, and scientific papers. A mixture assigns a probability $p_k$ to each source $k$, subject to $\sum_k p_k=1$.

Neither of the obvious rules is satisfactory. Uniform mixing gives every source the same weight regardless of its size, potentially repeating small datasets many times. Proportional mixing sets $p_k\propto N_k$, preventing that repetition but allowing the largest, often noisier source to dominate higher-quality material.

#### The silent epoch problem

The hidden variable is the number of times the model will traverse each source:

$$
\text{Epochs}_k = \frac{p_k \cdot N_T}{N_k}
$$

The audit must cover every source, where $N_T$ is the total training-token budget and $N_k$ is the number of unique tokens in source $k$.

Suppose a low-quality source contains $10^{13}$ tokens, a high-quality source contains $10^{10}$, and a one-trillion-token run samples each with probability 0.5:

$$
\text{Epochs}_L = \frac{p_L \cdot N_T}{N_L} = \frac{0.5 \times 10^{12}}{10^{13}} = 0.05 \quad \text{(5% of data seen once)}
$$

$$
\text{Epochs}_H = \frac{p_H \cdot N_T}{N_H} = \frac{0.5 \times 10^{12}}{10^{10}} = \mathbf{50} \quad \text{(!)}
$$

The data loader silently wraps around the smaller source, causing every high-quality token to be seen 50 times. What appears to be a balanced mixture is actually a severe repetition and memorization risk.

<details><summary>An epoch audit should therefore happen before training:</summary>

```python
def check_epoch_budget(mixture_weights, source_sizes, total_tokens, max_epochs=10):
    """Audit epoch counts for all sources before starting training."""
    print(f"{'Source':<20} {'Weight':>8} {'Size (B)':>10} {'Epochs':>10} {'Warning':>10}")
    print("-" * 65)
    for source, weight in mixture_weights.items():
        size = source_sizes[source]
        epochs = (weight * total_tokens) / size
        warning = "⚠️ OVERFIT RISK" if epochs > max_epochs else "OK"
        print(f"{source:<20} {weight:>8.3f} {size/1e9:>10.1f}B {epochs:>10.1f} {warning:>10}")

# Example
mixture_weights = {"wikipedia": 0.1, "commoncrawl": 0.8, "arxiv": 0.1}
source_sizes = {"wikipedia": 4e9, "commoncrawl": 1e13, "arxiv": 3e9}
total_tokens = 1e12

check_epoch_budget(mixture_weights, source_sizes, total_tokens)
# Output:
# wikipedia: weight=0.1, epochs = 0.1 * 1e12 / 4e9 = 25 ⚠️ OVERFIT RISK
# commoncrawl: weight=0.8, epochs = 0.8 * 1e12 / 1e13 = 0.08  OK
# arxiv: weight=0.1, epochs = 0.1 * 1e12 / 3e9 = 33 ⚠️ OVERFIT RISK
```

#### UniMax caps source repetition

UniMax turns repetition into an explicit constraint. If no source may be traversed more than $C$ times, then the budget applies to every source:

$$
p_k \cdot N_T \leq C \cdot N_k \quad \forall k
$$

Equivalently, each source's sampling weight is capped at $C N_k/N_T$.

A practical weight begins with uniform sampling and caps sources that would exceed the budget:

$$
p_k = \min\left(\frac{1}{K}, \frac{C \cdot N_k}{N_T}\right), \quad \text{normalized to sum to 1}
$$

When a source reaches its cap, the sampler redistributes its probability mass across the remaining sources. The method supplies an important safety rail, although $C$ is itself a tunable choice: a cap that is too low underuses rare, valuable material, while a high cap reintroduces overfitting.

#### RegMix and OLMix learn mixture weights from proxy runs

Regression-based mixing treats the mixture as a hyperparameter that can be optimized empirically:

1. Define K sources and their token counts
2. Sample M random mixtures p^(1), ..., p^(M) from Dir(α)
3. For each mixture p^(i):
   a. Train a small proxy model (e.g., 300M params) for a short run
   b. Evaluate proxy model on target metric L(p^(i))
4. Fit regression: L̂(p) = f_θ(p) using the M data points
5. Optimize: p\* = argmin\_{p ∈ Δ^K} L̂(p)
6. Train large model using mixture p\*

Mixtures are commonly sampled from a Dirichlet distribution so that the experiments cover the probability simplex. A simple log-linear surrogate is:

$$
\hat{L}(\mathbf{p}) = \mathbf{w}^\top \log(\mathbf{p}) + b \quad \text{(log-linear model)}
$$

The predicted optimum is:

$$
\mathbf{p}^* = \arg\min_{\mathbf{p} \in \Delta^K} \hat{L}(\mathbf{p})
$$

subject to $p_k\geq0$ and $\sum_kp_k=1$.

This method rests on two transfer assumptions: the regression must remain accurate near mixtures favored by the optimizer, and the best mixture for a small model must remain good for a large one. It can also optimize the wrong goal. If the target metric contains only coding evaluations, the optimizer may correctly choose a nearly all-code mixture—correctly for the metric, but incorrectly for a general-purpose model. A richer design can treat each domain–quality combination as its own source, turning a one-dimensional source mixture into a two-dimensional domain-by-quality grid.

#### Simulated epoching makes proxy runs structurally comparable

Small proxy runs may never exhaust a valuable source even when the full run would repeat it heavily. OLMix addresses this mismatch by shrinking each source according to the ratio between proxy and full training budgets:

$$
N_k^{\text{proxy}} = \gamma \cdot N_k^{\text{large}}, \quad \gamma = \frac{N_T^{\text{small}}}{N_T^{\text{large}}}
$$

Then the epoch count transfers exactly:

$$
\text{Epochs}_H^{\text{proxy}} = \frac{p_H \cdot N_T^{\text{small}}}{N_H^{\text{proxy}}} = \frac{p_H \cdot N_T^{\text{small}}}{\gamma \cdot N_H} = \frac{p_H \cdot N_T^{\text{large}}}{N_H} = \text{Epochs}_H^{\text{large}}
$$

Mixtures that would overuse a source at full scale now exhibit the same failure in the proxy experiment. This “make small look like large” principle is what makes the regression informative rather than merely inexpensive.

### Synthetic Data Extends the Pipeline Beyond Pre-Training

Pre-training data is broad, document-shaped, and mostly collected. Post-training data is task-specific, structured as prompts and responses, and increasingly generated by strong teacher models. A general recipe is:

1. Define environment E (code repos, math problems, science datasets)
2. Define tasks/prompts P (questions, bug descriptions, coding exercises)
3. Collect responses from teacher model M (expensive model or human)
4. Filter responses (correctness, quality, format)
5. Use (P, M(P)) pairs as supervised fine-tuning data

The environment anchors the task, the teacher creates candidate behavior, and filtering determines which behavior becomes supervision. This is distillation at dataset scale.

#### OpenThoughts uses diversity and multi-sampling

OpenThoughts assembled about 1.2 million reasoning examples across mathematics, science, and code. Its questions came from multiple sources, including NuminaMath, Stack Exchange, competitive programming, code review, and CodeGolf. Several teacher models generated reasoning traces.

The core pipeline sampled 16 responses per question and retained strong candidates. If a teacher independently answers a question correctly with probability $p_{\text{correct}}$, the probability that at least one of $N$ attempts succeeds is:

$$
P(\text{at least one correct in } N) = 1 - (1 - p_{\text{correct}})^N
$$

At 50% per-sample accuracy, 16 attempts give $1-0.5^{16}\approx99.998\%$ probability of at least one correct answer. That coverage only becomes useful when a filter can distinguish sound reasoning from a lucky final answer. OpenThoughts found that basic answer checking alone was insufficient; trace quality and diversity mattered.

Several findings complicate the usual “stronger teacher is always better” assumption. A well-chosen subset of question sources outperformed indiscriminate use of every available source, and QwQ-32B reportedly produced more useful traces for this setting than the larger DeepSeek-R1. A smaller teacher may generate reasoning that is more diverse, concise, or learnable for the student.

#### SWE-Zero trades execution feedback for scale

SWE-Zero starts from an empirical observation: strong code models can solve many repository tasks through static inspection alone. In the cited comparison, success fell from roughly 80% with execution feedback to roughly 70% without it. The performance cost was meaningful but small enough to unlock a much larger corpus.

The agent is restricted to file operations such as `grep`, `sed`, `find`, `cat`, and `diff`. It cannot run tests or execute code, so repositories no longer need working environments. Filtering is essential because some teacher models ignore the restriction and attempt to execute commands anyway. Removing those trajectories ensures that the student is trained on behavior available in the intended environment. Preventing execution also removes one avenue for agent hacking, such as hard-coding expected test outputs instead of solving the underlying defect.

SWE-rebench pushed the same approach much further. The 12 million trajectories are roughly 240 times SWE-smith's 50,000 execution-based tasks. The datasets occupy different points on a quantity–grounding spectrum:

| Dataset                   | Generation strategy                                |       Approximate scale |
| :------------------------ | :------------------------------------------------- | ----------------------: |
| OpenThoughts              | Multi-source, multi-teacher reasoning              |    1.2 million examples |
| SWE-smith                 | Execution-required synthetic bugs and solutions    |            50,000 tasks |
| SWE-Zero                  | Execution-free work on real pull requests          |    300,000 trajectories |
| SWE-rebench with SWE-Zero | Execution-free generation across many repositories | 12 million trajectories |

Execution-based data offers stronger verification, while execution-free data makes far more environments usable. A two-stage curriculum combines their strengths: first learn repository navigation and editing from abundant static trajectories, then refine those skills on the smaller set of executable tasks.

### A Unified View of the Data Pipeline

The stages of the pipeline solve different problems, but they share a common design principle: spend expensive computation only after cheap operations have reduced the search space.

| Stage                    | Core question                                        | Scalable mechanism                                               |
| :----------------------- | :--------------------------------------------------- | :--------------------------------------------------------------- |
| Extraction               | What textual information survives the source format? | Rule-based HTML/PDF conversion, selective OCR                    |
| Filtering                | Which documents resemble the desired target?         | KenLM, fastText, LLM-labeled proxy classifiers                   |
| Deduplication            | Which documents repeat the same information?         | Exact hashes, MinHash, LSH candidate generation                  |
| Mixing                   | How often should each source appear?                 | Epoch audits, caps, regression-based proxy runs                  |
| Post-training generation | Which behaviors should the model learn?              | Teacher sampling, environment construction, trajectory filtering |

Each stage also exposes a version of the same quality–quantity trade-off. Strict extraction rules lose unusual layouts. Strict filtering runs out of unique tokens sooner. Strict deduplication may collapse legitimately related documents. High weights on rare sources cause repeated epochs. Execution requirements improve verification but sharply reduce the number of repositories that can contribute agent trajectories.

The right operating point is therefore conditional, not universal. It depends on the target capabilities, total training budget, acceptable memorization risk, evaluation suite, and available infrastructure. Even a theoretically elegant method can fail if these surrounding constraints are ignored.

## 3. From Base Model to Assistant: The Evolution of LLM Post-Training

A pre-trained language model can absorb vast amounts of knowledge and learn remarkably general patterns from text, yet still be frustratingly difficult to use. Early base models such as GPT-3 often required carefully designed prompts and several examples before they would perform a task reliably. They could continue text, but they did not naturally behave like assistants.

Post-training closes that gap. It turns a broad next-token predictor into a model that can follow instructions, hold a conversation, use tools, refuse unsafe requests, and optimize its answers for human preferences. The transformation depends on two main techniques: supervised fine-tuning (SFT), which demonstrates desired behavior, and reinforcement learning from human feedback (RLHF), which teaches the model to prefer some outputs over others.

The history of post-training is also a history of changing data. The field moved from repurposed NLP benchmarks to distilled conversations, expert-written answers, synthetic examples, safety demonstrations, and structured agent trajectories. At the same time, preference optimization evolved from complex reinforcement-learning systems such as PPO to simpler objectives such as Direct Preference Optimization (DPO). These advances made language models easier to control, but they also exposed persistent problems: stylistic improvements can masquerade as intelligence, fine-tuning can amplify hallucinations, annotator biases can become model policies, and reward optimization can collapse diverse behavior into repetitive formulas.

Understanding post-training therefore requires more than knowing a training algorithm. It requires understanding what each stage can change, what its data actually teaches, and where apparent progress may be misleading.

### Pre-Training Creates Capability; Post-Training Creates an Interface

Pre-training and supervised fine-tuning use essentially the same learning objective: predict the next token. The difference lies in the data distribution.

During pre-training, a model consumes an enormous and heterogeneous collection of text. This process gives it broad knowledge, linguistic ability, and latent competence across many tasks. The result is something like a “primordial soup” of capabilities. Those capabilities exist, but they are not organized into a reliable user interface.

SFT applies the same next-token objective to a much smaller, carefully curated collection of input-output pairs. Each example shows the model how it should respond to a particular kind of request. The model is not merely shown more text; it is shown a behavioral pattern:

- A user gives a direct instruction.
- The assistant interprets the instruction as a task.
- The assistant produces an answer in a consistent, useful format.

This distinction explains why relatively little SFT data can produce a large behavioral shift. A few hundred or thousand examples may be sufficient to surface capabilities that pre-training has already created. The examples act less like a new knowledge base and more like pointers to latent behavior. They teach the model how to expose what it knows.

That observation also complicates the meaning of a “base model.” Modern models marketed as base models may already include extensive data curation or even chat-like data during the final stages of pre-training. The clean historical division—web text first, instruction data later—has become increasingly difficult to maintain.

### The Evolution of Supervised Fine-Tuning Data

The development of SFT data followed a clear progression. Each generation addressed a limitation of the one before it, while introducing new tradeoffs.

#### FLAN: turning NLP benchmarks into instructions

Early instruction-tuning projects such as FLAN reused existing NLP datasets. A summarization dataset could be converted into an instruction such as “Summarize this article,” while an email dataset might produce an artificial task such as “Write a subject for this Enron email.” Combining many transformed datasets taught models to recognize a broad range of task descriptions.

This approach demonstrated that instruction tuning could improve zero-shot task performance, but its data often felt unlike real conversation. Benchmark datasets were built for narrow research tasks rather than natural interaction. Their prompts could sound mechanical, and noisy target answers could teach the model unsupported or hallucinated summaries. The model learned to follow instructions, but the resulting interface was not yet a natural chatbot.

#### Alpaca: distilling the behavior of a chatbot

Stanford’s Alpaca project changed the data source. Instead of converting legacy benchmarks, it used ChatGPT to generate 52,000 instruction-response demonstrations for LLaMA. The key insight was direct: if the goal is a chatbot, the training data should look like conversations with a chatbot.

Alpaca showed that chat-style demonstrations could unlock a surprisingly capable assistant interface in an open model. Tasks that previously required prompt engineering and few-shot examples could be requested through ordinary language. It also established model distillation as a practical way for open projects to reproduce the behavioral style of a stronger proprietary system.

Distillation has a ceiling, however. A student can learn the teacher’s formatting, tone, and common response patterns, but it cannot reliably become more capable than the teacher simply by imitating its outputs. It also inherits the teacher’s quirks, including repeated disclaimers and formulaic phrases such as “As an AI language model.” Distillation is an effective way to catch up to an interface, not a guaranteed way to surpass the underlying intelligence that produced it.

#### Open Assistant: crowdsourcing human quality

Open Assistant pursued a different strategy: build a high-quality instruction dataset from human-written conversations. This approach sought to avoid dependence on proprietary model outputs and to capture answers that reflected genuine human judgment.

Human expertise brought its own risk. Expert annotators could write detailed responses containing precise claims and citations that a student model had never encountered during pre-training. SFT then asked the model to learn two things at once: the desired form—provide a confident answer with citations—and the specific facts contained in that demonstration.

If those facts were not already represented in the model, the generalizable lesson might be the format rather than the knowledge. At inference time, the model could reproduce the pattern of authoritative citation without knowing which citation was correct. The result would be structurally convincing but factually invented references.

This is the tail-knowledge problem. SFT can teach a model how to express knowledge more reliably, but it is a poor mechanism for forcing large amounts of obscure new world knowledge into the model. When demonstrations demand facts that the base model does not possess, fine-tuning may teach the appearance of knowledge more successfully than the knowledge itself.

#### Synthetic and agentic data

Modern SFT pipelines increasingly depend on synthetic data. Projects such as WizardLM and Tulu 3 use model-generated instructions, answers, or refinements to create data at a scale that would be prohibitively expensive for human annotators. Even projects initially committed to human data have adopted AI-generated annotation because it is cheaper, faster, and often comparable to average crowd-worker output.

The target behavior has also expanded beyond text-only conversation. Agentic SFT data may include:

- Structured calls to tools and APIs
- Decisions about which tool to use
- Parallel execution branches
- Intermediate reasoning or action traces
- Observations returned by external environments
- Final answers grounded in tool results

This data does more than make a model conversational. It teaches the model to operate as one component in a larger system.

Human annotation remains especially valuable at the frontier, where subtle errors require domain expertise. Doctors, lawyers, developers, and other specialists can evaluate outputs that general crowd workers cannot reliably verify. Their judgments are costly, but synthetic scale cannot fully replace the tacit knowledge needed to distinguish a polished answer from a correct one.

The best frontier datasets are difficult to study from the outside because major labs treat their post-training data as a closely guarded trade secret. Public research consequently depends heavily on older disclosures, open crowdsourcing projects, and attempts to distill proprietary assistants. Those sources reveal the broad direction of the field, but they are not necessarily representative of the human-data pipelines behind the strongest closed models.

### Style Is Not the Same as Capability

One of SFT’s most deceptive effects is that it can make a model appear much more intelligent without materially improving its underlying problem-solving ability.

Chat-style tuning often produces longer answers, clearer organization, Markdown headings, bullet points, and a confident explanatory tone. These changes are useful. They make a system easier to understand and more pleasant to use. They can also produce large gains on evaluations where another model or a human chooses which answer looks better.

The problem is that evaluators often reward visible structure more readily than invisible correctness. A non-expert can quickly recognize formatting, detail, and fluency, but may be unable to verify a mathematical derivation, legal interpretation, or factual claim. A model trained to produce longer, better-formatted answers can therefore achieve a much higher win rate on preference-based leaderboards such as AlpacaEval while showing little or no corresponding gain on stricter capability benchmarks such as MMLU or mathematics tests.

This creates an illusion of progress. The assistant sounds better, and evaluators prefer it, but the model may not know more or reason more accurately. Formatting should therefore be treated as one dimension of quality rather than evidence of a general capability increase.

### Safety Fine-Tuning Is a Boundary-Setting Problem

Safety SFT teaches a model how to respond to harmful, malicious, or dangerous requests. Its objective is not simply to maximize refusals. A useful safety policy must balance two competing error rates:

1. **Violation rate:** how often the model complies with a genuinely harmful request.
2. **False-refusal rate:** how often the model rejects a benign request because it superficially resembles something harmful.

A model that answers every request may have an unacceptable violation rate. A model that refuses whenever it sees a word such as “kill” may reject harmless questions like “How do I kill a Python process?” Reducing one error by indiscriminately increasing the other does not create a well-aligned assistant. Safety training must find a workable point on this tradeoff.

Real user interactions are valuable because they expose attacks and ambiguities that a laboratory might not anticipate. Open datasets such as WildChat contain real chatbot conversations, including jailbreak attempts that can be mined and converted into safety demonstrations. Annotators can then write preferred responses: sometimes a direct refusal, sometimes a safe alternative, and sometimes a normal answer when the query is benign despite suspicious wording.

Surprisingly little data can alter this behavior. Roughly 500 well-chosen refusal examples may sharply reduce violations across many categories. As with general SFT, this suggests that the base model already represents concepts of harm and safety. Fine-tuning mainly selects the behavioral boundary at which those concepts should trigger a refusal.

The post-training team is therefore the last line of defense before deployment, but its task is closer to policy calibration than to teaching the model the concept of danger from scratch.

### Annotators Become Part of the Model

Human feedback is not a neutral measurement. Every annotation reflects a person’s knowledge, values, incentives, and interpretation of the task. When those judgments become training targets, characteristics of the annotator pool can become characteristics of the model.

Demographic effects offer a direct example. A study of annotation effects found that post-trained models shifted toward the political views of the specific populations represented among InstructGPT annotators, including West Coast Americans and Southeast Asians. The important point is not that one worldview is correct. It is that the composition of a rater pool can silently define the model’s policy for millions of users.

Expertise creates another systematic effect. Non-experts tend to reward features they can verify, such as length, confidence, bullet points, and polished formatting. Experts are more likely to detect factual inconsistency or a subtly invalid argument. Two annotation pools can therefore prefer different models even when they receive the same evaluation instructions.

There are also practical quality-control problems. If annotators use a chatbot to perform the work they were hired to judge, an ostensibly human dataset may become an undisclosed form of synthetic distillation. Labs must distinguish genuine independent evaluation from model-assisted rating.

Bias can even travel through data that appears unrelated to the bias itself. In emergent misalignment, a model with a hidden behavioral tendency generates apparently innocuous training examples, and a student trained on those examples acquires part of the underlying tendency. Data does not transmit only its explicit propositions; it can transmit the statistical signature of the system or population that produced it.

The lesson is unavoidable: choosing annotators is part of designing the model. Their expertise, demographics, guidelines, and tools all shape the policy learned during post-training.

### Mid-Training Blurs the Boundary

The classical pipeline places general web-scale learning in pre-training and chat or instruction learning in post-training. Modern training increasingly mixes the two.

During the final learning-rate decay phase—often the last 5–10 percent of a pre-training run—labs may reduce the share of raw web data and introduce high-quality sources such as StackExchange or UltraChat. This phase is sometimes called mid-training, although it occurs near the end of pre-training.

Injecting instruction-style data at this point has several advantages. It begins shaping assistant behavior before the dedicated post-training stage, scales instruction exposure across a large token budget, and makes the final pre-trained model a stronger starting point for later alignment. It also creates an economical environment for data experiments. A complete pre-training run is too expensive to repeat for every mixture, but the shorter decay phase allows teams to test alternative data blends, compare their effects, and apply those lessons to the next full run.

This practice explains why apparently base models may already exhibit chat-like behavior. It also shows that pre-training and post-training are not fundamentally separate kinds of learning. Both shape a model through the data distribution; the boundary is increasingly an engineering convention rather than a clean scientific division.

### Why Preference Learning Goes Beyond SFT

SFT teaches by presenting a target answer. That requirement creates a bottleneck: a human must be able to write the desired output. In many domains, however, evaluation is easier than generation.

A person may recognize the better of two summaries without being able to write an equally strong summary from scratch. In one example from the development of InstructGPT, freelance writers preferred the model’s summaries to summaries they had written themselves. A developer can run two programs and identify which one passes the tests more easily than writing the correct implementation. A mathematical solution may be hard to discover but straightforward to verify.

RLHF exploits this generator-evaluator gap. Instead of asking a person to produce the perfect answer, it asks them to compare candidates. A standard InstructGPT-style pipeline proceeds as follows:

1. Give a prompt to an SFT model.
2. Sample several responses.
3. Ask a human rater to rank or compare them.
4. Train a reward model to predict those preferences.
5. Optimize the language model to generate responses that receive higher predicted rewards.

This changes the learning objective. Pre-training and SFT fit a distribution over text: they try to reproduce the kinds of sequences found in their data. RLHF maximizes a scalar reward. In principle, a reward-maximizing policy has no obligation to preserve the diversity of the original text distribution. If one response pattern always receives the highest score, the policy may use that pattern repeatedly.

### PPO and the Role of the KL Penalty

Early RLHF systems commonly used Proximal Policy Optimization (PPO). The central objective can be written as:

$$
\max_{\pi_\theta} \mathbb{E}_{x \sim \mathcal{D}, y \sim \pi_\theta(\cdot|x)} \left[ r(x, y) - \beta \mathbb{D}_{\text{KL}} \left( \pi_\theta(\cdot|x) \,\|\, \pi_{\text{ref}}(\cdot|x) \right) \right]
$$

Here, $\pi_\theta$ is the policy being trained, $r(x,y)$ is the reward model's score for response $y$ to prompt $x$, $\beta$ controls the strength of the divergence penalty, and $\pi_{\text{ref}}$ is usually the original SFT model.

The first term rewards outputs that the preference model considers good. The second penalizes the trained policy for moving too far from the reference model. This Kullback–Leibler divergence penalty is essential because a learned reward model is only an imperfect proxy for human judgment. If optimization proceeds without restraint, the policy may discover adversarial strings that exploit weaknesses in the reward model. Such strings can score extremely well while becoming repetitive, nonsensical, or otherwise undesirable.

PPO also clips overly large policy updates so that a single optimization step cannot move the model too far from its previous state. Its practical difficulty comes from the machinery needed to perform this optimization. Training may require an active policy, a frozen reference policy, a reward model, and a value function in memory at the same time. It must also generate fresh samples during training, which is slower and less stable than ordinary supervised learning. The system is powerful, but it is expensive and notoriously sensitive to implementation details.

### DPO Turns Preference Optimization into Classification

Direct Preference Optimization asks whether the reward model and the reinforcement-learning loop can be removed. Its derivation begins with the closed-form optimal policy for the KL-constrained RLHF objective:

$$
\pi^*(y|x) = \frac{1}{Z(x)} \pi_{\text{ref}}(y|x) \exp\left(\frac{1}{\beta} r(x, y)\right)
$$

Here, $\pi^*$ is the theoretical optimal policy, $Z(x)$ is a normalizing partition function, and the exponential term increases or decreases the reference probability according to the reward. In words, the optimal policy is the reference SFT model with each response reweighted exponentially by its reward.

This expression provides a mathematical bridge between reward and policy. By rearranging it, the reward can be written in terms of the probability ratio between the optimal policy and the reference policy. Substituting that expression into a pairwise preference loss eliminates the explicit neural reward model.

DPO can then train directly on triples containing a prompt $x$, a preferred response $y_w$, and a rejected response $y_l$. Conceptually, its update has the form:

$$
\nabla_\theta \mathcal{L}_{\text{DPO}} = \text{weight} \cdot \left( \nabla_\theta \log \pi_\theta(y_w|x) - \nabla_\theta \log \pi_\theta(y_l|x) \right)
$$

The update raises the likelihood of the chosen response and lowers the likelihood of the rejected response. Its dynamic weight depends on the model’s current relative confidence. If the model already strongly prefers the winner, the necessary correction is small. If it assigns greater probability to the loser, the update is larger.

Operationally, DPO resembles supervised fine-tuning: it uses ordinary gradient descent over a fixed preference dataset and does not need online sampling, a value network, or a separately trained reward model. That simplicity helped it become a standard technique in open post-training pipelines, including work associated with Llama 3.

The derivation contains an important assumption. It treats the policy as non-parametric—as though it could take the exact shape of any desired probability distribution. A finite neural network cannot satisfy that assumption perfectly. DPO works well empirically despite the mismatch, but its mathematical elegance should not be mistaken for a proof that it is always superior.

### Reward Optimization Has Its Own Failure Modes

Preference optimization does not eliminate the biases present in its reward signal. It can intensify them.

If raters favor long, confident, highly structured answers, a reward model learns that preference. Continued optimization may produce increasingly verbose or sycophantic responses without improving factuality. This is reward hacking: the policy learns how to obtain a high score rather than how to satisfy the deeper intention behind the score.

The same pressure can cause mode collapse. SFT attempts to reproduce a distribution containing many legitimate styles and answers. Reward maximization pushes probability toward whichever outputs receive the highest score. If the reward function consistently favors one phrase, structure, or tone, the model can lose creative variance and answer unrelated questions in an increasingly uniform voice.

DPO is not immune. Its results can be highly sensitive to preference-pair formatting and step size. Although it simplifies the infrastructure, PPO and related methods such as GRPO can still outperform it at the frontier. The choice is not between an obsolete algorithm and a universally better replacement; it is a tradeoff between simplicity, stability, data sensitivity, and the ability to optimize against interactive rewards.

More fundamentally, thumbs-up and thumbs-down data eventually reaches a limit. Collecting more subjective preferences cannot guarantee indefinite capability improvement. Once the model learns the easiest visible signals associated with approval, stronger optimization may amplify those signals rather than solve harder problems.

This limitation motivates reinforcement learning with verifiable rewards (RLVR). In mathematics and code, correctness can often be checked objectively through a proof condition, exact answer, compiler, or test suite. Verifiable rewards reduce dependence on stylistic human preference and allow optimization to target whether a solution actually works.

## 4. Beyond Reward Models: How RLVR Is Reshaping Reasoning and Agent Training

Reinforcement learning from human feedback helped turn pretrained language models into useful assistants, but its core reward signal creates a hard scaling limit. Human judgments are expensive and subjective, so developers usually train a neural reward model to approximate them. Continued optimization against that proxy eventually teaches the policy to exploit its weaknesses instead of producing genuinely better answers.

Reinforcement Learning from Verifiable Rewards (RLVR) offers a different path. In mathematics, code, formal proofs, games, and some agent environments, an external system can determine whether an answer is correct. That makes it possible to train directly against outcomes rather than a learned approximation of human preference. The result is a reward signal that appears more objective and scalable.

Yet RLVR does not eliminate the difficult parts of reinforcement learning. It changes them. The field has had to simplify fragile algorithms, control pathological incentives, construct difficult training tasks, and harden environments against agents that discover shortcuts no human designer anticipated. The development of PPO, GRPO, DeepSeek R1, Kimi K1.5, and Qwen's agent-training pipeline reveals both the promise and the limits of this approach.

### Why RLHF Eventually Hits a Ceiling

RLHF normally begins with human preference data. People compare model outputs, and those comparisons train a reward model that can score new responses at much greater scale. A reinforcement-learning algorithm then adjusts the language model to maximize that score.

The reward model is only a proxy for human judgment, however. It has limited capacity, reflects noise in the original labels, and cannot anticipate every output the policy might generate. If optimization continues for long enough, the policy searches beyond the distribution on which the reward model was trained and finds outputs that receive high scores without satisfying the underlying human objective. This is reward hacking, or overoptimization.

That failure mode means more RLHF compute does not necessarily produce a better model. Past some point, additional optimization may simply make the policy better at exploiting the evaluator.

RLVR replaces the learned evaluator with a test whose outcome can be checked directly. A mathematical response can be compared with a known answer, code can be compiled and run against tests, and a formal proof can be submitted to a verifier. In these settings, the reward often reduces to a scalar such as 1 for success and 0 for failure.

The contrast is straightforward:

| Training approach | Source of reward                               | Central risk                                                        |
| :---------------- | :--------------------------------------------- | :------------------------------------------------------------------ |
| RLHF              | A neural model trained from human preferences  | The policy exploits errors in the learned reward model              |
| RLVR              | An objective checker or executable environment | The policy exploits errors or shortcuts in the task and environment |

RLVR therefore moves the boundary of the problem. It reduces dependence on a subjective neural reward model, but its reliability is only as strong as the verifier and the environment surrounding it.

### The Policy-Gradient Foundation

At the center of both approaches is a simple idea: actions that lead to higher reward should become more likely. The REINFORCE policy gradient expresses that idea as:

$$
\nabla_\theta J(\theta) = \mathbb{E}_{\pi_\theta} \left[ \nabla_\theta \log \pi_\theta(a|s) \cdot R \right]
$$

Here, $\nabla_\theta J(\theta)$ gives the parameter-update direction, $\nabla_\theta \log \pi_\theta(a|s)$ describes how to make action $a$ more or less likely in state $s$, and $R$ scales that update according to the reward.

If a generated trajectory receives a positive reward, training increases the probability of its actions. A negative reward pushes in the opposite direction. For a language model, those actions are tokens, and a trajectory may be an entire chain of thought followed by a final answer.

The equation is simple; obtaining useful, stable gradient estimates is not. Rewards may be sparse, many rollouts may fail, and two responses to the same prompt can vary dramatically in both quality and length. Practical algorithms introduce baselines and constraints to control that variance.

Language-model RL also sits between a bandit problem and conventional multi-step reinforcement learning. A response often receives one reward only after the complete sequence has been generated, yet the algorithm must assign that outcome across many token-level actions. This delayed, sequence-wide feedback makes credit assignment and variance control especially important.

### Why PPO Made Language-Model RL So Difficult

Proximal Policy Optimization (PPO) became the standard reinforcement-learning algorithm for early reasoning systems. It limits the size of each policy update so that training does not move too far from the model that generated the data. PPO also estimates an advantage: how much better or worse an action performed than expected.

That expectation usually comes from a value function. In language-model training, the value model may be another network comparable in size to the policy itself. It predicts future reward from the current state and supplies a baseline that reduces gradient variance.

This design imposes several costs:

- **Memory overhead:** Training may need the policy, a reference policy, a reward component, and a value model in memory at the same time. The value model alone can resemble a second LLM.
- **Algorithmic brittleness:** Details such as policy clipping, KL control, and generalized advantage estimation can determine whether training remains stable or collapses.
- **Infrastructure complexity:** Rollout generation and gradient computation have different hardware and scheduling requirements.
- **Straggler effects:** One long reasoning trajectory may take minutes while another finishes in seconds, leaving batched inference resources idle.

Direct Preference Optimization (DPO) avoids much of this online RL machinery when the data naturally consists of a preferred and a rejected response. Verifiable problems do not always have that shape. An agent explores a task and receives a scalar success or failure signal; there may be no pre-existing response pair. RLVR needs an algorithm that can sample, explore, and optimize those scalar outcomes directly.

### GRPO Removes the Value Model

Group Relative Policy Optimization (GRPO) simplified this pipeline by replacing the learned value baseline with comparisons among multiple responses to the same prompt. For each problem, the model generates a group of $G$ rollouts. Their rewards are summarized by a mean and standard deviation, and each rollout receives a relative advantage:

$$
A_i = \frac{r_i - \text{mean}(\mathbf{r})}{\text{std}(\mathbf{r})}
$$

Here, $r_i$ is rollout $i$'s raw reward, often 1 for success and 0 for failure. The group mean replaces the learned value-model baseline, while the group standard deviation normalizes the update; the resulting $A_i$ determines whether and how strongly the rollout is reinforced.

A response that performs above its group mean receives a positive advantage; one below the mean receives a negative advantage. Because all rollouts address the same prompt, their relative performance provides a prompt-specific signal without asking a neural network to predict expected reward.

Removing the value model sharply reduces memory requirements and implementation complexity. This practical simplification made large-scale RLVR more accessible and supported open reasoning-model efforts such as DeepSeek R1.

DeepSeek R1 also emphasized outcome supervision over process supervision. A process reward model attempts to grade intermediate reasoning steps, which requires detailed labels or a reliable step-level evaluator. An outcome reward model asks only whether the final answer is correct. Outcome checks are much easier to scale, and R1 showed that they can be sufficient to train strong reasoning behavior.

R1-Zero pushed the idea further by applying RL directly to a base model without first relying on long-chain-of-thought supervised fine-tuning. The experiment suggested that a capable base model already contains reasoning and self-correction behaviors that reinforcement learning can amplify.

### Theoretical Imperfections Create Practical Side Effects

GRPO's success does not make every part of its update theoretically clean. A policy-gradient baseline can reduce variance without changing the expected gradient, but dividing rewards by a group standard deviation changes how different prompts are weighted. Sequence-length normalization can introduce another distortion.

#### Standard-deviation normalization

Dividing by $\text{std}(\mathbf{r})$ gives larger normalized updates to groups with little reward variation. That can overemphasize prompts that are too easy or too hard, even though problems near the model's capability frontier often provide the most useful learning signal. If every rollout receives the same reward, the group supplies no relative ranking at all and must be handled carefully to avoid an undefined or unstable update.

#### Length normalization

When a negative update is divided across the tokens in a response, a failed trajectory can reduce its per-token penalty by becoming longer. The model may therefore learn to ramble when it is wrong. Extra reasoning tokens are not necessarily evidence of deeper reasoning; they can be an artifact of the training objective.

This matters because long chains of thought increase inference cost. An algorithm that improves benchmark accuracy while teaching failed attempts to expand indefinitely transfers part of its training pathology directly into production serving costs.

#### “Aha moments” require careful interpretation

Reasoning models sometimes recognize an error mid-generation, reconsider the problem, and recover. RLVR can make these episodes more visible and frequent, but that does not prove the behavior originated during RL. Base models can already contain self-correction patterns learned during pre-training. Reinforcement learning may select and strengthen an existing capability rather than create it from nothing.

#### Even answer checking can be ambiguous

Mathematical verification is not always equivalent to string matching. For example, $\frac{1}{\sqrt{2}}$ and $\frac{\sqrt{2}}{2}$ denote the same value but have different surface forms. A checker must normalize expressions, use symbolic tools, or call another model to judge equivalence. The last option reintroduces a learned evaluator into a supposedly verifiable pipeline.

Kimi's pipeline, for example, used a dedicated neural reward model to judge answer equivalence. The verifier was still narrower and more objective than a general preference model, but its presence demonstrates how quickly real-world RLVR becomes a hybrid system.

These examples do not invalidate GRPO. They show why empirical success and theoretical correctness must be evaluated separately. A useful heuristic can unlock strong models while still carrying incentives that need explicit correction.

### Kimi K1.5 Takes an Alternative Route

Kimi K1.5 reached a similar group-relative training strategy from a DPO-inspired derivation rather than a PPO-inspired one. Its design highlights two practical issues that become increasingly important as reasoning models move into production: controlling output length and allocating training compute to the right problems.

First, Kimi explicitly penalizes long chains of thought. A useful length penalty cannot simply force every incorrect response toward zero tokens, because that would prevent exploration and reasoning. Instead, the training signal encourages failed answers to become modestly shorter relative to the group, reducing unproductive rambling without eliminating thought altogether.

Second, Kimi uses Best-of-N filtering as a difficulty curriculum. If the current model can solve a problem in any of several attempts, that problem may already be too easy to justify further RL compute. Filtering out such examples concentrates training on tasks that remain beyond the model's reliable reach.

This leads to a broader rule for RLVR data selection: a useful training task is verifiable, solvable through exploration, and currently difficult.

A task that is impossible supplies only repeated failure. A task that is already easy supplies little new information. The most valuable prompts sit near the moving boundary of the model's competence, so the data curriculum must evolve as the policy improves.

### From Reasoning Models to Agentic RLVR

Single-turn mathematics and coding problems are only the beginning. An agent must navigate a repository, inspect files, select tools, edit code, and react to environment feedback across a long trajectory. Qwen's work on reasoning models and Qwen 3.5 Coder-Next illustrates how RLVR expands into this setting.

#### Combining thinking and non-thinking behavior

Qwen 3 experimented with a single model that could switch between an immediate-response mode and a deeper reasoning mode through prompt tags. Mixing both behaviors during training created a flexible model whose chain of thought could be truncated early while still retaining some benefit from partial reasoning.

The experiment also exposed a trade-off. A unified model is convenient, but mixing modes can slightly reduce peak performance on demanding mathematics and coding tasks. Later versions could therefore favor more separation when specialization matters more than behavioral flexibility.

#### Agent behavior begins before post-training

An agent cannot acquire all of its foundational capabilities during the final RL stage. It needs prior exposure to the structures and trajectories it will encounter. Agentic mid-training can include:

1. Concatenated files from complete code repositories.
2. GitHub pull requests augmented with retrieved repository context.
3. Web documents transformed into useful long-context examples.
4. Execution traces produced by existing coding agents.

This data teaches the model how repositories are organized, how changes relate across files, how issues map to patches, and how tool-driven work unfolds over time. Reinforcement learning then refines behavior within environments the model already understands.

SWE-bench captures this kind of work in benchmark form: an agent receives a real GitHub issue and must explore its repository and produce a patch. Training for such tasks requires more than code completion. The model must learn repository-scale context, iterative tool use, and long-horizon decision-making.

### What Actually Drives Progress in Agent Training

Agentic RLVR can look like an algorithmic revolution, but its gains still depend heavily on data and systems engineering. The policy needs relevant mid-training data, realistic tasks, executable environments, reliable checkers, and trajectories at the right difficulty. No optimizer can compensate for a task distribution that is trivial, impossible, contaminated by leaked answers, or disconnected from deployment.

The emerging design principles are practical:

- Use objective outcomes where they genuinely exist, but audit what the checker fails to measure.
- Prefer simpler optimization pipelines when they preserve performance and reduce infrastructure burden.
- Treat chain-of-thought length as an explicit cost and incentive, not merely a model behavior.
- Focus RL compute on tasks near the model's current capability frontier.
- Build agent knowledge during mid-training rather than expecting late-stage RL to create it from scratch.
- Train specialists when reward functions conflict, then distill their capabilities into a generalist.
- Assume that a capable agent will discover every accessible shortcut in its environment.

These principles connect algorithm design, data selection, and environment security. Improving any one component without the others produces fragile gains.

## 5. From Contrastive Alignment to Omni Models: How Vision-Language Systems Learn to See

Large language models operate on tokens, but most of the world does not arrive as text. It arrives as images, audio, and video: continuous signals filled with spatial detail, temporal structure, and far more raw information than a text sequence of comparable length. Building a multimodal model therefore begins with a translation problem. How can a system turn non-text data into representations that a transformer can understand without discarding the information that matters?

Modern vision-language models answer this question in stages. CLIP and SigLIP learn semantic visual representations by aligning images with captions. Systems such as LLaVA and Qwen-VL connect those representations to a language model through a trainable adapter. More advanced designs improve resolution, spatial awareness, video processing, and fusion with the language model. Fully unified architectures such as Chameleon go one step further and represent images as discrete tokens, but that architectural elegance introduces serious problems of entropy, detail loss, and training stability.

Together, these systems reveal a central lesson of multimodal AI: understanding and generation are related capabilities, but they do not necessarily benefit from the same representation or training objective.

### Multimodality Begins with a Tokenization Problem

Text enters a language model as discrete tokens. A tokenizer maps words or subwords to entries in a fixed vocabulary, and an embedding table turns each entry into a vector. The transformer then processes the resulting sequence.

An image has no natural equivalent to a word. It is a dense grid of pixel values, and treating every pixel as an independent token would create an enormous sequence while preserving little semantic structure. Vision systems instead convert an image into a shorter sequence of continuous vectors. Each vector represents a region of the image and encodes features such as shapes, objects, textures, or higher-level concepts.

This creates two broad approaches to multimodality:

- **Continuous visual tokens:** A vision encoder produces vectors that are projected into the embedding space of a language model.
- **Discrete visual tokens:** A quantizer maps image regions to entries in a finite visual vocabulary so that a model can predict them like text tokens.

The first approach dominates visual understanding. The second offers an appealing route to native image generation, but it must compress rich visual data through a discrete bottleneck.

The long-term “North Star” is an omni model: a single system capable of ingesting and producing arbitrary combinations of text, images, audio, and video. The path toward that goal begins with learning what an image means.

### CLIP Learns Visual Meaning from Language

Before large-scale vision-language pre-training, computer vision relied heavily on manually labeled datasets such as ImageNet. Human annotators assigned each image to a predefined category, giving the model reliable supervision but limiting the breadth of concepts it could learn.

CLIP, introduced by OpenAI in 2021, replaced that narrow label space with natural language. It trained on roughly 400 million noisy image-text pairs collected from the web. Instead of asking the model to classify an image into one fixed category, CLIP asked it to identify which caption belonged with which image.

#### A dual-encoder architecture

CLIP contains two independent encoders:

1. An **image encoder** converts an image into a vector.
2. A **text encoder** converts a caption into a vector in the same embedding space.

The image encoder can be a Vision Transformer, or ViT. A ViT divides an image into a grid of patches, flattens each patch, adds positional information, and passes the resulting sequence through a transformer encoder. This process produces a representation that can be compared directly with the text representation.

For a batch of $N$ images and $N$ captions, CLIP computes the similarity of every image with every caption. The result is an $N \times N$ matrix. The diagonal contains the genuine image-caption pairs; the off-diagonal entries contain mismatched pairs.

Conceptually, the objective is:

$$
\text{Loss} = \text{CrossEntropy}(\text{Softmax}(\mathbf{I} \cdot \mathbf{T}^\top / \tau), \text{Labels})
$$

In this expression, $\mathbf{I}$ and $\mathbf{T}$ are the $N \times D$ image- and text-embedding matrices, $\tau$ is a temperature that scales their dot products, and the identity-matrix labels mark the genuine diagonal pairings.

The model treats caption matching as an $N$-way classification problem. For each image, it should assign the highest similarity to the corresponding caption. Training pulls matched images and texts together in the embedding space while pushing mismatched pairs apart.

This simple objective created remarkably general visual representations. Because natural-language captions can describe far more concepts than a fixed class list, CLIP learned a broad semantic space and demonstrated strong zero-shot recognition. Zero-shot CLIP even outperformed ResNet systems trained on more than a million manually labeled ImageNet examples. A user could describe a new category in text and compare that description with an image without training a new classifier for the category.

#### Why text provides unusually powerful supervision

Contrastive vision systems can also learn by comparing two augmentations of the same image. For example, a model can learn that a cropped or rotated dog is still the same dog. That teaches useful invariance, but the supervision remains tied to pixels.

Language adds a semantic layer. A caption can distinguish a golden retriever from a poodle, describe an action, identify a location, or express a relationship between objects. The image encoder must therefore learn features that correspond to human concepts rather than merely recognize whether two pixel arrangements came from the same source.

CLIP also exposed a subtle tradeoff. Training the model to predict the exact caption sequence produced weaker image representations than contrastive matching. Exact generation forces the model to spend capacity on word order, grammar, and other linguistic details. Contrastive learning can instead treat the caption as a compact semantic target and focus on the concepts visible in the image.

### SigLIP Removes CLIP’s Global Batch Bottleneck

CLIP’s effectiveness came with a systems problem. The softmax compares each example with every candidate in the batch, so large batches provide many useful negative examples. In practice, this encouraged batch sizes in the tens of thousands.

Large global batches are expensive to distribute. When the similarity matrix is split across many accelerators, the devices must communicate because every entry contributes to the shared softmax denominator. The learning objective therefore couples the examples together and creates a synchronization bottleneck.

SigLIP replaces the batch-wide multiclass decision with independent binary decisions. For every image-text pair, the model asks a simpler question: do these two items match?

Its objective is:

$$
\text{Loss} = \sum_{i,j} \log \sigma(y_{i,j} \cdot (\mathbf{I}_i \cdot \mathbf{T}_j / \tau))
$$

Here, $\sigma$ is the sigmoid function, and $y_{i,j}$ is 1 for a matching image-text pair and -1 otherwise.

Each pair can now be evaluated independently. The $N \times N$ comparison matrix can be divided into blocks and processed on different devices without synchronizing a global softmax. This makes training easier to parallelize, more stable at smaller batch sizes, and less dependent on enormous collections of in-batch negatives.

The conceptual shift is small but important. CLIP asks the model to choose the one correct caption from a batch. SigLIP asks it to make many independent true-or-false judgments. Both create a shared semantic space, but the second objective maps much more naturally onto distributed hardware.

### From a Visual Encoder to a Visual Assistant

CLIP and SigLIP can determine whether an image and a description are semantically aligned, but they are not conversational assistants. They do not naturally explain an image, answer a complex question about it, or follow a visual instruction. A vision-language model must connect the visual representation to the generative and reasoning capabilities of a large language model.

LLaVA demonstrated an influential recipe: combine a pre-trained vision encoder with a pre-trained language model and learn a small bridge between them. Its original formulation paired CLIP’s visual representations with the Vicuna language model.

#### The adapter as a learned translator

The vision encoder outputs a sequence of continuous patch vectors. The language model also processes vectors, but its inputs occupy an embedding space learned from text. Even when the dimensions happen to match, the two encoders do not assign the same meaning to corresponding directions in that space.

An adapter, also called a projector, learns the translation. It may be a linear projection, a multilayer perceptron, or a cross-attention module. In the simplest LLaVA formulation, a trainable matrix $W$ maps the vision encoder’s output into the dimensional space expected by the language model.

After projection, the visual vectors can be inserted into the language model’s input sequence. The model processes them alongside ordinary word embeddings and generates a textual response through its existing next-token prediction mechanism.

This modular architecture avoids the cost of training a complete multimodal system from scratch. The vision encoder already recognizes visual concepts, and the language model already knows how to reason and generate text. Training focuses on making their internal representations compatible.

#### Alignment before instruction tuning

VLM training commonly proceeds in two stages:

1. **Feature alignment:** Freeze both the vision encoder and the language model, then train only the adapter on a large collection of image-caption pairs. The projector learns to turn visual features into vectors that behave like meaningful language-model inputs.
2. **Visual instruction tuning:** Keep the vision encoder frozen while training the adapter and the language model on curated conversations about images. This stage teaches the model to answer questions, follow visual instructions, explain scenes, and perform more complex reasoning.

The two stages solve different problems. Alignment establishes a shared representational interface. Instruction tuning teaches behavioral patterns on top of that interface.

Early open-source VLM projects often generated instruction data synthetically. LLaVA, for example, used text metadata such as captions and bounding boxes from existing datasets and asked GPT-4 to write detailed conversations about the corresponding images. GPT-4 did not need direct access to the pixels; the metadata supplied enough structure to create richer training dialogues than a simple caption alone.

This bootstrapping strategy let open systems acquire conversational behavior without the cost of manually writing every visual question and answer.

### Resolution Determines What a Model Can See

A standard vision encoder often resizes every image to a small square such as $224 \times 224$. That can work well for recognizing large objects, but it destroys fine detail. A photograph of a document may contain perfectly legible text at its original resolution, yet become an unreadable blur after aggressive downsampling.

AnyRes processing addresses this problem without replacing the underlying encoder. Instead of squeezing a high-resolution or unusually shaped image into one small square, the system divides it into tiles that match the encoder’s native input size. It processes each tile independently and concatenates the resulting visual tokens.

This changes the length of the visual sequence rather than the resolution of each encoder input. A transformer can naturally accept different sequence lengths, so a high-resolution document can contribute many visual tokens while a simple image contributes fewer.

AnyRes is especially important for:

- Optical character recognition and document understanding
- Charts, diagrams, and screenshots with small labels
- Wide or tall images with unusual aspect ratios
- Scenes in which small objects carry essential information

The technique illustrates a recurring multimodal tradeoff. Preserving more detail usually means producing more tokens, and more tokens increase compute and memory costs. Better perception therefore depends not only on a stronger encoder but also on a deliberate token-budget strategy.

Visual prompting offers a complementary way to control attention. A user can draw a circle, arrow, or bounding box directly onto an image and ask about the marked region. The annotation becomes part of the visual input, allowing the model to use an ordinary instruction while the image itself specifies the object of interest.

### Spatial and Temporal Position Need Their Own Structure

A text sequence has one obvious order: token 1 precedes token 2. Images and videos require richer coordinates. An image patch has horizontal and vertical position, while a video frame adds time.

Qwen-VL extends rotary positional embeddings into a multimodal form known as M-RoPE. Rather than assigning only a one-dimensional sequence index, M-RoPE tracks coordinates across time, width, and height. These structured positions help the model preserve relationships such as “above,” “to the left of,” and “earlier in the video.” They also support tasks such as predicting bounding boxes or reasoning about where an object appears.

Later refinements interleave the positional dimensions rather than allocating separate frequency ranges to time, width, and height. This lets each axis experience both low- and high-frequency rotations and avoids imbalances that can weaken spatial-temporal modeling.

Video creates an additional grounding challenge: the model must connect an event to a moment. Explicit timestamp tokens such as `<0s>` and `<2s>` can be inserted into the multimodal sequence, giving the language model concrete temporal anchors for describing changes and ordering events.

These mechanisms can also produce compositional generalization across modalities. A model trained to interpret charts in single images and trained separately to reason across multiple images may generalize to comparisons across several charts, even when that exact combination did not appear in the training set. The visual interface supplies the content, while the language model contributes reusable reasoning patterns.

### Deeper Fusion Extends the Adapter Recipe

The simplest VLM inserts projected visual tokens only at the input of the language model. More advanced systems such as Qwen-3 push this approach toward context lengths of up to 256K tokens and can inject visual information at several depths.

A DeepStack-style adapter, used in Qwen-3 and DeepSeek designs, adds vision embeddings directly into the residual streams of multiple language-model layers. This gives later layers access to visual features without requiring all image information to survive unchanged from the beginning of the sequence. Deep fusion preserves the modularity of an encoder-plus-language-model design while making their interaction more direct.

This architecture remains asymmetric in parameter count. The vision encoder may contain fewer than a billion parameters, while the language model may contain tens of billions. The vision component performs much of the local perceptual work: finding edges, shapes, text regions, and objects. The larger language model performs the more general reasoning needed to explain how those elements relate or what they imply.

Long videos stress this architecture because they can produce enormous token sequences. If every token contributes equally to the training loss, a few long video examples may dominate the gradients and overwhelm shorter images or text-only examples. Square-root loss normalization reduces this imbalance by dividing an example’s loss by the square root of its token length. Long examples still receive more weight, but not in direct proportion to every token they contain.

Combined with high-resolution tiling, structured position encodings, timestamps, and deeper visual injection, this makes the adapter-based design far more capable than its simple origins suggest.

### Chameleon Pursues Native Discrete Multimodality

Adapter-based VLMs have an important limitation: they naturally accept images but still generate text. Their language-model head predicts discrete vocabulary entries, not continuous visual vectors. Image generation therefore requires a separate output mechanism.

Meta’s Chameleon explored a more unified alternative. It converted images into discrete visual tokens and trained a standard autoregressive transformer over a mixed vocabulary of text and image tokens. In principle, the same next-token predictor could read and generate arbitrarily interleaved modalities.

#### How a VQ-VAE creates image tokens

Chameleon uses a Vector Quantized Variational Autoencoder, or VQ-VAE, to discretize an image. The encoder first converts image regions into continuous vectors. Each vector is then replaced by the nearest entry in a learned codebook. The selected codebook index becomes a visual token, much like the vocabulary ID of a text subword.

In the described configuration, a $512 \times 512$ image becomes 1,024 tokens selected from a visual vocabulary of 8,000 codes. Once this conversion is complete, the transformer can process an image with the same next-token objective used for language. It can also generate visual tokens autoregressively and pass them through the VQ-VAE decoder to reconstruct an image.

The design is architecturally elegant. It replaces modality-specific interfaces with one vocabulary, one sequence, and one training objective. A conversation can interleave text and images without switching to a fundamentally different model.

### Why Discrete Image Tokens Are Difficult to Scale

The elegance of a unified token stream hides two fundamental problems.

#### Text and images have different entropy

Text is highly structured. In a sentence such as “The sky is...,” only a small set of next words is plausible. Discrete image tokens are much less predictable. Many slightly different colors, textures, and pixel arrangements can form an equally valid cloud or patch of sky.

This entropy mismatch makes joint autoregressive training unstable. The model must learn predictable symbolic sequences and high-variance visual sequences with the same parameters and objective. In Chameleon-style training, this can cause parameter norms to grow rapidly, requiring additional regularization such as z-loss to avoid collapse.

The difficulty is not merely that images use more tokens. Each token also asks the model to predict fine-grained visual variation that may have no single correct answer.

#### Quantization destroys fine detail

A VQ-VAE is a lossy compressor. Every image region must be rounded to one of a limited number of codebook entries. That bottleneck discards subtle information before the transformer sees it.

The lost details may be inconsequential for recognizing a large object, but they are essential for reading small text, interpreting a dense document, or preserving exact visual structure. Increasing the codebook or the token count can reduce the loss, but it also makes modeling and generation more expensive.

Continuous vision encoders avoid hard quantization and therefore retain richer semantic features for understanding. Diffusion models, meanwhile, are especially effective at generating high-frequency continuous detail. These alternatives have reduced the practical appeal of forcing both perception and generation through the same discrete visual vocabulary.

### Understanding and Generation Favor Different Architectures

The current direction of multimodal systems is best understood as an asymmetric pipeline:

- **For visual input**, use a continuous encoder such as CLIP or SigLIP, preserve detail through high-resolution processing, and map the resulting features into a language model with adapters or deeper fusion.
- **For visual output**, route the model’s intent or representation to a diffusion-based generator that specializes in reconstructing fine visual detail.

This arrangement may look less theoretically pure than a single autoregressive model over a universal vocabulary, but it respects the different statistical demands of the tasks. Understanding benefits from abstraction: the system should identify the objects, relationships, and concepts that matter while ignoring irrelevant pixel variation. Generation demands reconstruction: the system must create plausible color, texture, geometry, and other high-frequency details.

An image encoder compresses pixels into meaning. An image generator expands meaning back into pixels. Those operations move in opposite directions, so forcing them through the same bottleneck can compromise both.

The resulting system can still present a seamless omni-model interface. Users do not need to know whether an image was processed by a continuous encoder or generated by a diffusion decoder. Architectural modularity behind the interface does not prevent unified multimodal behavior.

## 6. From Token Serving to Looped Transformers: Redesigning the LLM Stack for Efficient Intelligence

The cost of artificial intelligence does not end when a model finishes training. Once millions of users begin sending prompts, every generated token becomes a systems problem: requests must be scheduled, model weights moved through memory, attention state preserved, and GPU work coordinated without wasting expensive hardware. Small inefficiencies that seem harmless in a research prototype become enormous at production scale.

This pressure is changing the entire large language model stack. Inference systems now separate prompt processing from token generation because the two phases stress hardware in fundamentally different ways. GPU engineers fuse entire transformer layers into megakernels to eliminate launch overhead and idle time. Model architects are also reconsidering recurrence, using looped transformers to trade additional computation for greater capability without increasing the parameter footprint.

These developments point to a common principle: progress no longer comes from scaling model size alone. Efficient intelligence increasingly depends on co-designing the serving system, GPU software, and neural architecture around the physical constraints of computation and memory.

### Inference Is the Engine That Turns Compute Into Tokens

Training produces a model, but an inference engine turns that model into a usable service. It schedules requests, manages memory, determines whether previous work can be reused, launches machine-learning kernels, and streams generated tokens back to users. At large scale, the quality of this engine can matter almost as much as the model itself.

The central challenge is that a language-model request contains two computationally different workloads: **prefill** and **decode**.

During prefill, the model reads the prompt. A document containing 10,000 tokens can be processed largely in parallel, much like a forward pass during training. This phase performs substantial matrix computation and is therefore compute-bound.

During decode, the model generates new tokens autoregressively, one at a time. Producing each token requires the system to load and use the model's weights again, even though the amount of arithmetic for that individual step is relatively small. Decode is therefore dominated by memory bandwidth rather than raw floating-point throughput.

| Phase   | Primary task               | Execution pattern                        | Main bottleneck    |
| :------ | :------------------------- | :--------------------------------------- | :----------------- |
| Prefill | Read and encode the prompt | Many prompt tokens processed in parallel | Compute throughput |
| Decode  | Generate the response      | One new token produced at a time         | Memory bandwidth   |

An intuitive analogy is that prefill resembles reading a whole book at once, while decode resembles writing it one character at a time. The first workload can saturate a GPU's parallel arithmetic units. The second repeatedly moves a huge model through memory to perform comparatively little computation.

### Why Prefill and Decode Are Becoming Separate Services

When prefill and decode share the same workers, their incompatible resource demands interfere with each other. A large incoming prompt can occupy compute resources and delay conversations that are already generating tokens. Meanwhile, hardware selected for high arithmetic throughput may still perform poorly when decode is limited by memory movement.

Disaggregated serving addresses this mismatch by assigning prefill and decode to different machines or GPU pools. Prefill workers can be optimized for parallel computation, while decode workers can be designed around memory capacity and bandwidth. The system transfers the request state between them after the prompt has been processed.

This division is beginning to influence hardware design itself. Decode-oriented accelerators can devote more on-chip memory to reducing weight movement, while prefill-oriented hardware can prioritize dense matrix computation. The workload is no longer merely adapting to available chips; it is helping determine what those chips should become.

### The KV Cache Turns Serving Into a Memory-Management Problem

Autoregressive generation would be even more expensive if every new token required recomputing attention over all previous tokens. The **key-value cache**, or KV cache, avoids that repetition by storing the key and value matrices produced for earlier tokens. Each decode step can reuse this state rather than reconstruct it from scratch.

The trade-off is memory consumption. Long conversations, large batches, and many simultaneous users can quickly fill GPU memory. Modern inference engines therefore manage the KV cache as a hierarchy:

1. Active state remains in fast GPU memory.
2. Less active state can be offloaded to CPU DRAM.
3. Inactive state may be moved to NVMe SSD storage.
4. When a conversation resumes, its state is restored to the faster tier.

This design resembles virtual memory in an operating system. The GPU acts like the processor, the KV cache acts like working memory, and policies such as Least Recently Used eviction determine which state should be paged out. Ideas developed for operating systems decades ago have reappeared inside modern AI serving stacks because both systems must create the illusion of abundant fast memory on top of a limited physical resource.

Scheduling has evolved in the same direction. **Continuous batching** allows requests to enter and leave a batch at token boundaries instead of forcing an entire fixed batch to finish together. A short response no longer needs to wait behind a very long generation before its resources can be reused.

**Cache-aware routing** adds another layer of coordination. Requests with a cold cache can be directed to dedicated prefill workers, while conversations with warm state continue decoding elsewhere. This prevents new, computation-heavy prompts from interrupting active generations. In the example discussed here, this kind of systems-level optimization produced a roughly 40% speedup without any change to the model itself.

### At Scale, Systems Bugs Can Look Like Model Failures

Serving trillions of tokens also exposes defects that almost never appear in small tests. An off-by-one error or uninitialized memory in a GPU kernel may surface only under a rare combination of sequence length, batch composition, and cache state.

The resulting behavior can be deceptive. A model may emit an endless sequence of Chinese characters, repeat a pattern indefinitely, or enter a loop of tool calls. From the outside, these symptoms look like hallucination or a strange property of the training data. The actual cause may be a low-level inference bug corrupting a small part of the computation.

This makes full-stack observability essential. Model behavior cannot always be diagnosed at the model layer; request scheduling, kernel correctness, memory state, and cache movement may all influence the tokens a user sees.

### Decode Leaves Expensive GPUs Waiting

Even after improving routing and memory management, autoregressive decode can underutilize the GPU itself. A conventional transformer layer executes a sequence of distinct operations: LayerNorm, QKV projections, rotary position embeddings, attention, output projections, and multilayer perceptrons. Frameworks such as PyTorch traditionally launch a separate GPU kernel for each operation.

That modular structure is convenient, but decode operations are often so small that kernel launch overhead competes with—or exceeds—the time spent doing useful mathematics. A GPU execution trace consequently contains substantial white space. Streaming multiprocessors sit idle while they wait for the next kernel to launch, for a dependency to resolve, or for the slowest item in a batch to finish.

The problem is especially visible on hardware such as an H100 with 132 streaming multiprocessors. If those processors are not calculating or moving data, their theoretical performance is irrelevant. The system has purchased compute that its software cannot keep busy.

### Megakernels Treat the GPU as a Distributed System

A **megakernel** attacks this inefficiency by fusing many transformer operations—potentially an entire layer—into one carefully orchestrated GPU kernel. Instead of returning control to the host between LayerNorm, matrix multiplication, attention, and the MLP, the fused kernel manages dependencies and intermediate state internally.

This changes the mental model of GPU execution. Rather than treating the device as one processor that steps through a list of operations, megakernel designers treat its streaming multiprocessors as participants in a small distributed system. Different groups coordinate data loading, arithmetic, and dependency management while the kernel remains active.

The fused schedule can overlap tasks that a conventional execution graph performs sequentially. For example, some processors can begin loading the large KV cache while others are still completing the QKV projection. Intermediate results can remain in registers or shared memory instead of being written to global memory and loaded again by the next kernel.

The payoff can be dramatic. Megakernel decoding can reach 72% memory-bandwidth utilization, close to the practical physical limit of the hardware. Frameworks such as ThunderKittens exist to make this unusually low-level style of CUDA programming more manageable.

### Extreme Performance Comes With Extreme Specialization

Megakernels reveal both the opportunity and the weakness of hand-optimized GPU software. Fusing an entire layer can remove launch overhead, reduce memory traffic, and keep hardware busy, but the resulting code may depend on a specific combination of: `GPU architecture`, `Model architecture`, `Tensor dimensions`, `Batch size` and `Memory layout`.

A kernel optimized for one configuration may lose its advantage—or fail entirely—when the batch size or model shape changes. Producing it can consume as much as a year of work from an expert engineer, and a new hardware generation may force much of that effort to be repeated.

This tension suggests that the long-term goal is not simply to hand-write more megakernels. It is to build compilers and programming systems capable of generating fused, hardware-specific schedules automatically. FlashAttention demonstrated how operation fusion could transform the attention block; megakernels extend the same idea toward an entire transformer layer.

### Looped Transformers Add a Third Scaling Axis

Systems and kernel optimization make an existing model cheaper to serve. Looped transformers ask a more architectural question: can a model perform more computation without storing more unique parameters?

A standard transformer moves tokens through a sequence of distinct layers. A looped transformer instead reuses the same layer, or block of layers, multiple times. If a block is applied 12 times, the model performs additional computation on its hidden state without requiring 12 independent copies of the block's weights.

This design is attractive because parameter count determines much of a model's memory footprint. Reusing parameters can increase the amount of reasoning applied to each token while keeping VRAM requirements relatively stable. Recurrence therefore adds a third dimension to compute-optimal scaling: `Number of parameters`, `Amount of training data` and `Number of recurrent loops`.

The promise is substantial, but early looped transformers were notoriously unstable. Small learning-rate changes could cause loss spikes, NaN gradients, and complete training collapse.

### Reusing a Layer Also Reuses Its Instability

The residual stream provides a useful way to understand this failure. A simplified looped-transformer update can be written as:

$$
\mathbf{x}_{t+1} = \mathbf{A} \mathbf{x}_t + \mathbf{B} \mathbf{u}_t + \text{NonLinear}(\mathbf{x}_t)
$$

Here, $\mathbf{x}_t$ is the residual-stream state at loop step $t$; $\mathbf{A}$ governs how that state evolves; $\mathbf{B}\mathbf{u}_t$ controls how the original input is retained; and $\text{NonLinear}(\mathbf{x}_t)$ represents transformer operations such as attention, MLPs, GELU, and Softmax.

In an ordinary transformer, each layer has different weights, so the residual stream encounters a different transformation at every depth. In a looped transformer, the same transition is applied repeatedly. The linearized dynamics therefore contain repeated powers such as $\mathbf{A}^T$.

If a transformation increases the activation magnitude by a factor of 1.1, applying it 16 times produces growth proportional to $1.1^{16}$. More generally, when the spectral radius of $\mathbf{A}$ is $>1$, repeated application can make the state explode. Excessive contraction can create the opposite problem by driving activations and gradients toward zero.

The instability is not an incidental training inconvenience. It follows directly from reusing the same dynamics over and over.

### Parcae Stabilizes Recurrence Through Spectral Control

Parcae approaches the looped transformer as a dynamical system. Rather than treating loss spikes as a problem to solve only through optimizer tuning, it analyzes the matrices that govern the residual stream using state-space model theory.

The architecture constrains $\mathbf{A}$ as a negative diagonal matrix whose spectral radius remains $< 1$. This restriction prevents repeated application from amplifying activations without bound. No matter how many times the block loops, the linear component decays instead of exploding.

That architectural constraint stabilizes the training curve and makes recurrence a usable scaling mechanism. The result illustrates the value of theory in neural-network design: a mathematical property of the transition operator can explain an empirical failure that would otherwise look like random optimizer fragility.

### Three-Dimensional Scaling Changes Compute Optimality

Traditional scaling laws describe a balance between model parameters and training data. A larger dataset generally requires a larger model to absorb its information efficiently. Looped transformers introduce recurrence as another way to spend a fixed compute budget.

Parcae's scaling analysis suggests that when parameter count remains fixed and training data increases, the number of recurrent loops should also increase to preserve compute optimality. In this view, a model can scale not only outward through more weights but also inward through repeated computation over the same state.

This reframes the economics of model design. A model with fewer unique parameters may consume less memory at inference time while using additional FLOPs to refine each token representation. Such a trade is increasingly attractive when memory movement, rather than arithmetic, is the dominant serving bottleneck.

Recurrence does not come for free. Additional loops increase latency and total computation, and stable training requires careful architectural constraints. But it creates a design space that parameter-only scaling ignores: intelligence can grow through the depth of computation even when the number of stored weights does not.

### The Full Stack Is Becoming One Optimization Problem

Inference disaggregation, megakernels, and looped transformers operate at different layers, yet they respond to the same physical reality. Computation is abundant only when software can schedule it effectively; fast arithmetic is useful only when memory can supply data; and larger parameter counts are valuable only when they can be stored and served economically.

The connections are direct:

- Disaggregated serving maps compute-bound prefill and memory-bound decode onto different resources.
- KV-cache hierarchies and cache-aware routing keep limited fast memory focused on active work.
- Megakernels reduce software overhead and approach the hardware's usable memory-bandwidth limit.
- Looped transformers reuse parameters, exchanging extra computation for a smaller memory footprint.
- Spectral constraints make that repeated computation stable enough to scale.

These are not isolated optimizations. A recurrent architecture changes the amount and pattern of inference computation. A fused kernel changes which batch sizes and model shapes are efficient. A cache-routing policy changes how much useful work a GPU can sustain. Decisions at one layer reshape the best design at every other layer.
