# Modern LLM Systems: Architecture, Kernels, Training, Serving, and Evaluation

Modern LLM systems are shaped by the interaction of Transformer architecture, numerical stability, GPU memory behavior, distributed training, scaling laws, inference serving, and evaluation design. The modern Transformer still depends on residual streams, attention, feed-forward networks, positional information, and softmax prediction, but practical models rely on refinements such as pre-normalization, RMSNorm, SwiGLU, RoPE, QK normalization, logit soft-capping, and Grouped Query Attention to improve stability, throughput, and KV-cache efficiency.

Long-context and high-capacity models respond to the limits of dense quadratic attention and dense parameter activation through selective computation. Linear attention, Mamba-style recurrences, Gated Delta Net, sparse attention, retrieval systems, and Mixture-of-Experts architectures reduce unnecessary token interactions or parameter use. These methods increase scale, but they also introduce routing, load-balancing, communication, expert-specialization, and selection-quality challenges.

GPU and distributed-training efficiency depend less on raw FLOPs than on data movement. Strong kernels use tiling, fusion, online softmax, coalesced access, and careful memory reuse across registers, shared memory, and HBM, while the broader compiler stack spans PyTorch, `torch.compile`, TorchInductor, Triton, CUTLASS, cuBLAS, PTX, and hardware scheduling. At the cluster scale, data parallelism, ZeRO/FSDP, activation checkpointing, gradient accumulation, tensor/pipeline/context/expert parallelism, and communication overlap must be carefully mapped to the underlying hardware topology.

Scaling laws help predict large training runs from smaller experiments, but their conclusions depend on data quality, token budget, model size, optimizer choice, context length, architecture, and downstream objectives. Perplexity remains useful, yet deployment quality also depends on coding ability, tool use, safety, latency, cost, and workflow-specific success. Inference has its own bottlenecks: prefill can be compute-friendly, while autoregressive decoding is often memory-bound because each generated token loads weights and KV-cache entries.

Evaluation must match the decision being made. Base-model training benefits from held-out perplexity, academic comparison uses exam and reasoning benchmarks, chat systems rely on preference evaluations, agents require scaffold-aware system tests, and safety work needs refusal, policy, and jailbreak robustness measurements. Strong LLM engineering therefore optimizes the full system rather than a single metric: the architecture must train stably, kernels must target measured bottlenecks, parallelism must fit topology, inference must preserve correctness under resource pressure, and benchmarks must support concrete deployment decisions.

## 1. Modern Transformer Architecture

The Transformer is still the dominant architecture for LLMs, but the block used in frontier and open-source models has evolved far beyond the original 2017 design. Modern models keep the broad pattern of residual streams, attention, feed-forward networks, positional information, and softmax prediction. The important changes are in the details: pre-normalization, RMSNorm, gated feed-forward networks, RoPE, attention stabilization, Grouped Query Attention, and careful shape choices that map well to hardware.

These refinements are not cosmetic. Deep models train only when gradient flow remains stable. Large models serve only when memory traffic stays under control. Long-context models work only when positional encoding and attention do not break outside the training range. Modern Transformer engineering is therefore a mix of mathematical design and systems pressure.

### Residual Streams and Normalization

The residual stream is the main information path through a Transformer. Each block reads from it, computes an update, and writes the update back. A stable architecture keeps this path close to an identity map, so gradients can flow backward through many layers without repeated distortion.

The original Transformer used post-normalization:

$$
x_{l+1} = \text{Norm}(x_l + F(x_l))
$$

This places normalization directly in the residual path. During backpropagation, every layer rescales the gradient. At small scale this can work, but at depth it makes optimization sensitive and often requires long warmup.

Modern LLMs typically use pre-normalization:

$$
x_{l+1} = x_l + F(\text{Norm}(x_l))
$$

Here, the residual stream remains a clean identity path. Normalization happens only on the branch entering attention or the feed-forward block. This makes very deep networks easier to train because the shortcut from late layers to early layers remains mathematically direct.

LayerNorm stabilizes activations by subtracting the mean and dividing by standard deviation:

$$
\text{LN}(x) = \frac{x - \mu}{\sigma} \odot \gamma + \beta
$$

RMSNorm removes mean subtraction and additive bias:

$$
\text{RMSNorm}(x) = \frac{x}{\text{RMS}(x)} \odot \gamma \quad \text{where} \quad \text{RMS}(x) = \sqrt{\frac{1}{d} \sum_{i=1}^d x_i^2 + \epsilon}
$$

The simplification matters because normalization is memory-bound. It reads activations, computes statistics, and writes results back, but does not provide enough dense matrix multiplication to fully occupy tensor cores. RMSNorm keeps the stabilizing scale normalization while reducing memory work. For the same reason, many LLMs remove additive bias terms from dense linear layers: the quality benefit is usually small, while every extra operation matters at scale.

### Gated Feed-Forward Blocks

The feed-forward network is usually the largest parameter consumer in a dense Transformer layer. Early models used ReLU or GeLU:

$$
\text{FFN}_{\text{ReLU}}(x) = \max(0, x W_1) W_2
$$

Modern models often use Gated Linear Units, especially SwiGLU. A gated block adds a second projection and multiplies the two branches:

$$
\text{GLU}_{\text{gated}}(x) = (x W_1 \otimes x V) W_2
$$

SwiGLU uses Swish or SiLU in the gate:

$$
\text{SwiGLU}(x) = (\text{Swish}(x W_1) \otimes x V) W_2
$$

A minimal implementation is:

<details><summary>Code</summary>

```python
import torch
import torch.nn as nn
import torch.nn.functional as F

class SwiGLU(nn.Module):
    def __init__(self, d_model: int, d_ff: int):
        super().__init__()
        self.w1 = nn.Linear(d_model, d_ff, bias=False)
        self.v = nn.Linear(d_model, d_ff, bias=False)
        self.w2 = nn.Linear(d_ff, d_model, bias=False)

    def forward(self, x: torch.Tensor) -> torch.Tensor:
        gate = F.silu(self.w1(x))
        value = self.v(x)
        return self.w2(gate * value)
```

</details>

The parameter accounting explains why SwiGLU models usually use a smaller hidden dimension than classic FFNs. A traditional expansion to $4d_{\text{model}}$ uses:

$$
P_{\text{trad}} = 2 \times d_{\text{model}} \times 4d_{\text{model}} = 8d_{\text{model}}^2
$$

A gated FFN uses three matrices:

$$
P_{\text{gated}} = 3 \times d_{\text{model}} \times d_{\text{ff}} = 3d_{\text{model}}d_{\text{ff}}
$$

Matching parameter count gives:

$$
d_{\text{ff}} = \frac{8}{3}d_{\text{model}} \approx 2.67d_{\text{model}}
$$

This makes comparisons meaningful: the gain comes from the gating structure, not from silently increasing model size.

### Position Encoding with RoPE

Self-attention is permutation invariant unless position is injected somewhere. Sinusoidal embeddings, learned absolute embeddings, and relative position biases all work, but Rotary Position Embeddings became a standard choice because they encode relative distance while preserving the efficient $QK^T$ attention factorization.

RoPE aims for:

$$
\langle f(q, m), f(k, n) \rangle = g(q, k, m - n)
$$

The dot product between a query at position $m$ and a key at position $n$ should depend on content and relative offset, not absolute position. RoPE achieves this by rotating query and key coordinates according to position. In two dimensions:

$$
R_{m,\theta} \begin{pmatrix} x_1 \\ x_2 \end{pmatrix} =
\begin{pmatrix} \cos(m\theta) & -\sin(m\theta) \\ \sin(m\theta) & \cos(m\theta) \end{pmatrix}
\begin{pmatrix} x_1 \\ x_2 \end{pmatrix}
$$

Because rotations are orthogonal:

$$
\langle R_m u, R_n v \rangle = u^T R_m^T R_n v = u^T R_{n-m} v
$$

The remaining term depends on relative distance. High-frequency dimensions encode local order; low-frequency dimensions rotate slowly and help represent longer-range relationships. Long-context extensions often change the frequency schedule, increase the base, or interpolate positions to avoid unstable extrapolation.

A vectorized implementation avoids building explicit rotation matrices:

<details><summary>Code</summary>

```python
def apply_rotary_emb(x: torch.Tensor, cos: torch.Tensor, sin: torch.Tensor) -> torch.Tensor:
    # x shape: [Batch, Heads, Seq_len, Head_dim]
    x1 = x[..., :x.shape[-1] // 2]
    x2 = x[..., x.shape[-1] // 2:]
    return torch.cat([x1 * cos - x2 * sin, x2 * cos + x1 * sin], dim=-1)
```

</details>

### Stabilizing Softmax

Large-scale training failures often appear around softmax. There are two main softmax sites: the vocabulary distribution and the attention matrix. The output softmax has a shift invariance: adding a constant to every logit does not change probabilities, but it changes the partition function:

$$
Z = \sum_{i=1}^V e^{u_i}
$$

The z-loss penalizes drift in the log partition:

$$
L_z = \lambda (\log Z)^2
$$

This encourages logits to stay numerically controlled without changing the modeling objective too aggressively.

Attention logits can also become too large. QK normalization applies normalization to queries and keys before the dot product:

<details><summary>Code</summary>

```python
class QKNormAttention(nn.Module):
    def __init__(self, d_model, n_heads):
        super().__init__()
        self.n_heads = n_heads
        self.d_head = d_model // n_heads
        self.q_proj = nn.Linear(d_model, d_model, bias=False)
        self.k_proj = nn.Linear(d_model, d_model, bias=False)
        self.q_norm = nn.RMSNorm(self.d_head)
        self.k_norm = nn.RMSNorm(self.d_head)

    def forward(self, x):
        q = self.q_proj(x).view(-1, self.n_heads, x.shape[1], self.d_head)
        k = self.k_proj(x).view(-1, self.n_heads, x.shape[1], self.d_head)
        q = self.q_norm(q)
        k = self.k_norm(k)
        scores = torch.matmul(q, k.transpose(-2, -1)) / math.sqrt(self.d_head)
        return F.softmax(scores, dim=-1)
```

</details>

Logit soft-capping directly bounds values:

$$
\text{logits}_{\text{capped}} = C \tanh\left(\frac{\text{logits}}{C}\right)
$$

This constrains logits to $[-C, C]$. It is strong medicine: useful for stability, but potentially limiting if the model needs very sharp attention.

### Efficient Attention at Inference

Training and inference stress hardware differently. Training processes many tokens in parallel, so arithmetic intensity is high. Autoregressive inference generates one token at a time and repeatedly loads model weights plus cached keys and values. It is often memory-bound.

A useful approximation for inference arithmetic intensity is:

$$
I_{\text{infer}} \approx \frac{N_{\text{tokens}}}{d_{\text{model}}} + \frac{1}{B}
$$

Here, $N_{\text{tokens}}$ is active context length, $d_{\text{model}}$ is width, and $B$ is batch size. Small batches and wide models produce low computation per byte moved.

The KV cache is central. During generation, each layer stores previous keys and values so the model does not recompute them. The cache grows with batch size, sequence length, layers, heads, and head dimension. Grouped Query Attention reduces this pressure by letting many query heads share fewer key-value heads. It preserves more capacity than Multi-Query Attention while greatly reducing memory traffic relative to full Multi-Head Attention.

Modern systems also combine global attention with local sliding windows or other sparse patterns. The goal is not only to reduce FLOPs, but to keep memory traffic compatible with long-context serving.

### Block Layouts and Hardware Shape

Modern Transformer blocks also differ in how they order attention and feed-forward computation. The most common design is serial: attention reads the normalized residual stream, writes an update, then the feed-forward block reads the updated stream and writes another update. This gives the FFN access to information already mixed by attention.

Some models use parallel blocks, where attention and FFN both read the same normalized input and their outputs are added together in one residual update.

The attraction is systems efficiency. Parallel branches can expose fusion and scheduling opportunities, and they shorten the dependency chain inside a layer. The cost is representational: attention and the FFN no longer condition on each other within that same layer. As compiler support for standard serial blocks has improved, serial blocks have remained the safer default.

Model shape is another systems decision. Width, depth, number of heads, FFN expansion, and vocabulary size all affect both quality and hardware mapping. A very deep narrow model may have good parameter efficiency but can be hard to pipeline without bubbles. A wider model creates large matrices that tensor parallelism can shard efficiently. Empirically, many strong models live in broad basins rather than at one exact aspect ratio, but hardware pushes designs toward shapes that align with GPU matmul tiles and distributed sharding.

A common rough target keeps model width much larger than layer count, often around a width-to-depth ratio of 100. This is not a law. It is a reminder that architecture is not chosen only by validation loss. It must also fit tensor parallel groups, activation memory, optimizer state, checkpointing strategy, and inference latency.

### Architectural Stability as a Budget

It is useful to think of stability as a budget. Every component can either preserve the budget or spend it. Pre-norm preserves gradient flow. RMSNorm reduces memory traffic while keeping activation scale controlled. RoPE preserves relative position structure. QK normalization and soft-capping prevent attention logits from exploding. Conservative initialization and learning-rate warmup reduce early training shocks.

The danger is that stability interventions can also limit expressiveness. Too much logit capping can make attention less selective. Too much regularization can slow learning. Too small an FFN can reduce capacity. Too aggressive long-context interpolation can preserve syntax but damage retrieval. Modern model design is therefore not just a list of improvements; it is a balancing act between stable optimization and sufficient freedom.

This is why architectural changes should be tested at multiple scales. A trick that improves a small model may disappear at large scale, and a method that is neutral at small scale may prevent rare catastrophic failures at large scale. Large runs are dominated by tail risks: one unstable layer, data spike, optimizer mismatch, or numerical overflow can waste enormous compute. The purpose of the modern Transformer block is to make those failures less likely while staying friendly to kernels and distributed execution.

## 2. Beyond Quadratic Attention and Dense Compute

Full self-attention scales quadratically with sequence length. Flash Attention improves memory behavior and constant factors, but it does not remove the $n \times n$ interaction pattern. At very long contexts, architecture must change.

The main responses fall into three groups. Linear and recurrent methods replace dense attention with state updates. Sparse methods keep exact attention but compute it only over selected tokens. Mixture-of-Experts methods attack a different bottleneck: they increase total parameters without activating every parameter for every token.

### The Quadratic Bottleneck

Scaled dot-product attention is:

$$
\text{Attention}(Q, K, V) = \text{softmax}\!\left(\frac{QK^\top}{\sqrt{d_k}}\right) V
$$

Its cost is:

$$
\text{Cost} \sim O(n^2 \cdot d_k)
$$

The $QK^\top$ term creates an $n \times n$ score matrix. The feed-forward block scales linearly in sequence length, so the attention-to-FFN ratio is approximately:

$$
\frac{\text{Cost}_{\text{Attention}}}{\text{Cost}_{\text{FFN}}} \sim \frac{n^2 d_k}{n \cdot d_{ff}} = \frac{n \cdot d_k}{d_{ff}}
$$

As context grows, attention eventually dominates.

### Linear Attention

Linear attention removes the softmax or replaces it with a feature map that permits reassociation. Without softmax:

$$
\text{Out} = Q(K^\top V)
$$

Instead of computing all pairwise query-key interactions first, the model computes the global summary $K^\top V$ and then applies queries. The complexity becomes:

$$
O(nd_kd_v + nd_qd_v)
$$

For autoregressive generation, the state can be updated recurrently:

$$
S_t = S_{t-1} + k_t^\top v_t
$$

$$
o_t = q_t S_t
$$

For example:

<details><summary>Code</summary>

```python
def linear_attention_decode(q_seq, k_seq, v_seq):
    S = torch.zeros(k_seq.size(-1), v_seq.size(-1), device=q_seq.device)
    outputs = []
    for q_t, k_t, v_t in zip(q_seq, k_seq, v_seq):
        S = S + torch.outer(k_t, v_t)
        outputs.append(q_t @ S)
    return torch.stack(outputs)
```

</details>

The advantage is linear context scaling and a constant-size recurrent state. The challenge is selectivity. Softmax attention can focus sharply on a few tokens. Linear summaries mix information, so modern variants add gates, decay, or more structured state updates.

### Mamba-2 and Gated Delta Net

State-space and recurrent models generalize the linear state idea. Mamba-style models use input-dependent dynamics so the model can decide what to retain and what to forget. A simplified state update is:

$$
h_t = A_t h_{t-1} + B_t x_t
$$

$$
y_t = C_t h_t
$$

The important property is that recurrence can be parallelized with scan algorithms during training, while remaining efficient during generation. This gives the model an attention-like long-context path without materializing an $n^2$ matrix.

Gated Delta Net makes the memory operation more explicit: erase, forget, and write. A compressed form is:

$$
S_t = \alpha_t S_{t-1} + \beta_t k_t^\top v_t
$$

Here, $\alpha_t$ controls retention and $\beta_t$ controls write strength. The model no longer passively accumulates everything. It learns when to preserve memory and when to overwrite it.

These recurrent alternatives are attractive for long context, but they change model behavior. Attention exposes direct token-token interaction. Recurrent state compresses history, which can help efficiency but may lose exact retrieval unless the state is designed carefully.

### Sparse Attention

Sparse attention keeps exact softmax attention over a selected subset. The idea is to avoid attending to every token while preserving the semantics of attention for the chosen tokens.

DeepSeek-style sparse attention can be understood as a two-stage system. A cheap indexer selects candidate keys, then exact attention runs over that subset:

<details><summary>Code</summary>

```python
def sparse_attention(q, k, v, indexer, top_k):
    # q: [n, d], k: [n, d], v: [n, d_v]
    low_scores = indexer(q, k)
    selected = low_scores.topk(top_k, dim=-1).indices
    out = []
    for i in range(q.size(0)):
        k_i = k[selected[i]]
        v_i = v[selected[i]]
        scores = q[i] @ k_i.T / math.sqrt(q.size(-1))
        weights = torch.softmax(scores, dim=-1)
        out.append(weights @ v_i)
    return torch.stack(out)
```

</details>

This shifts the problem from dense matrix multiplication to retrieval quality. If the selector misses relevant tokens, exact attention over the selected subset cannot recover. Sparse attention therefore depends on good indexing, routing, or locality assumptions.

### Mixture-of-Experts Scaling

Mixture-of-Experts increases total parameters while keeping active compute relatively low. Instead of applying one dense FFN to every token, an MoE layer routes each token to a small number of experts. Total parameters scale with the number of experts, while active per-token compute scales mainly with the number of selected experts. This decouples total capacity from per-token compute. A model can store far more knowledge and specialization than a dense model with similar active FLOPs.

The router usually computes expert probabilities:

$$
p(e \mid x) = \text{softmax}(W_r x)_e
$$

Then selects the top experts:

$$
\mathcal{E}(x) = \text{TopK}_{e}(p(e \mid x))
$$

The output is a weighted sum:

$$
y = \sum_{e \in \mathcal{E}(x)} p(e \mid x) f_e(x)
$$

For example:

<details><summary>Code</summary>

```python
def moe_layer(x, router, experts, k=2):
    probs = torch.softmax(router(x), dim=-1)
    top_p, top_e = probs.topk(k, dim=-1)
    y = torch.zeros_like(x)
    for rank in range(k):
        expert_ids = top_e[:, rank]
        weights = top_p[:, rank]
        for e in expert_ids.unique():
            mask = expert_ids == e
            y[mask] += weights[mask, None] * experts[e](x[mask])
    return y
```

</details>

MoE models introduce new failure modes. Without load balancing, tokens may collapse onto a small set of experts. A common load-balancing objective penalizes mismatch between router probability and token usage:

$$
L_{\text{balance}} = E \sum_{e=1}^{E} f_e p_e
$$

where $f_e$ is the fraction of tokens routed to expert $e$ and $p_e$ is the average router probability for that expert.

MoE also changes systems behavior. Expert parallelism requires all-to-all token dispatch:

<details><summary>Text</summary>

```text
# MoE layer, conceptually
# 1. Router chooses expert ids for each token
# 2. all_to_all dispatch sends tokens to expert ranks
# 3. Each rank runs local experts
# 4. all_to_all combine returns outputs to origin ranks
```

</details>

This communication can dominate if routing is imbalanced or the topology is weak. Fine-grained experts, shared experts, expert replication, and capacity controls are all attempts to improve quality while keeping the all-to-all manageable.

### Training MoEs Without Collapse

MoE training is harder than dense training because the router is both a modeling component and a load balancer. If the router sends too many tokens to a few experts, those experts learn faster and become more attractive, which makes the imbalance worse. This positive feedback can leave many experts undertrained.

Capacity factors limit how many tokens each expert can process:

$$
C_e = \left\lceil \frac{\text{capacity factor} \cdot T \cdot k}{E} \right\rceil
$$

where $T$ is token count, $k$ is top-k routing, and $E$ is number of experts. If more than $C_e$ tokens route to expert $e$, some tokens are dropped, rerouted, or handled by a fallback path. Dropping tokens saves compute but can hurt learning; rerouting improves coverage but changes the router objective.

Router z-loss and entropy regularization are also common. The router must be confident enough to specialize but not so confident that it collapses. A useful target is high specialization per token with balanced aggregate traffic across experts.

Shared experts help by giving every token access to a dense common pathway. Fine-grained experts increase routing flexibility by using more smaller experts. Expert replication places copies of popular experts on multiple ranks to reduce hot spots. Upcycling initializes an MoE from a dense checkpoint by copying dense FFN weights into experts, which can reduce the cost and instability of training from scratch.

MoE also changes evaluation. A model with more total parameters but the same active FLOPs may improve knowledge and specialization, but it may not improve every task uniformly. Router decisions can be domain-sensitive, and underused experts may behave poorly on rare languages or specialized data. For this reason, MoE training needs per-expert telemetry: token counts, entropy, dropped-token rates, gradient norms, and domain distribution.

### Sparse Computation as a Shared Pattern

Linear attention, recurrent state models, sparse attention, and MoE look different, but they share a design pressure: avoid spending full compute on every possible interaction. Attention sparsifies over tokens. MoE sparsifies over parameters. Recurrent models compress history into state. The practical question is always what information can be skipped without damaging the target behavior.

Dense Transformers are attractive because they are simple and predictable: every token can attend to every previous token, and every token passes through the same parameters. Sparse systems trade that simplicity for scale. They need routing, indexing, gating, or memory policies. Their success depends on whether those policies are cheaper than dense compute and accurate enough not to discard important information.

### Retrieval, Memory, and Exactness

Long-context methods differ in what they promise. Full attention gives exact access to every previous token, modulo finite precision and softmax behavior. Sparse attention gives exact access only to selected tokens. Linear and recurrent models give compressed access through a state. Retrieval-augmented systems move some memory outside the model and retrieve chunks through an index.

These choices are not interchangeable. Exact retrieval matters for tasks such as copying a key from a long document, resolving a citation, or using a code definition many files away. Compressed memory may be enough for topic tracking, style consistency, or broad summarization. Sparse attention is strong when relevance is local or indexable. External retrieval is strong when the needed information can be searched cheaply and inserted into context.

A useful design question is whether the task needs exact recall, compressed state, or retrieved evidence. Million-token context is expensive if the task only needs a few retrieved facts. Conversely, retrieval can fail when the model must integrate many small dependencies spread across the full context. The best systems often combine methods: local attention for nearby syntax, sparse or global attention for anchors, recurrence for broad memory, and retrieval for external knowledge.

## 3. GPU Kernels and the Compiler Stack

LLM training and inference are constrained by GPU memory hierarchy as much as by arithmetic. Tensor cores are fast, but data must reach them. HBM is large but slower than on-chip memory. Registers and shared memory are fast but small. Good kernels arrange computation so data is reused before it returns to HBM.

The basic performance question is arithmetic intensity:

$$
I = \frac{\text{FLOPs}}{\text{Bytes moved}}
$$

If $I$ is low, the kernel is memory-bound. If $I$ is high enough, it may become compute-bound. Many Transformer operations are dominated by memory movement unless fused or tiled.

### The GPU Mental Model

GPU programs run many threads grouped into blocks or warps. Each streaming multiprocessor has registers, shared memory, schedulers, and access to global HBM. The fastest programs:

- Use coalesced memory access.
- Reuse data in registers or shared memory.
- Avoid unnecessary reads and writes to HBM.
- Keep enough work resident to hide latency.
- Use tensor cores for matrix-heavy operations.

Occupancy matters, but it is not the whole story. A kernel with high occupancy can still be slow if it repeatedly moves data through HBM. A kernel with lower occupancy can be faster if it reuses data effectively.

### Benchmark Before Optimizing

GPU optimization begins with measurement. The useful question is not "is this code vectorized?" but "what is the bottleneck?" A simple benchmark should report time, effective bandwidth, and achieved FLOPs:

<details><summary>Code</summary>

```python
def bandwidth_gb_s(num_bytes, seconds):
    return num_bytes / seconds / 1e9

def tflops(num_flops, seconds):
    return num_flops / seconds / 1e12
```

</details>

If a kernel moves many bytes per operation, optimization should reduce memory traffic. If it performs large matmuls, optimization should improve tiling, tensor-core use, and launch overhead.

### Fusion

Fusion changes performance because intermediate tensors are expensive. Suppose a model applies several elementwise operations:

$$
y = \text{GeLU}(xW + b)
$$

If each operation is separate, the GPU writes an intermediate tensor to HBM and reads it back for the next operation. A fused kernel keeps intermediate values in registers and writes only the final result.

For an elementwise chain, unfused memory traffic may scale like:

$$
\text{Bytes}_{\text{unfused}} \approx 2K \times \text{sizeof(float)}
$$

where $K$ is the number of stages. A fused version approaches:

$$
\text{Bytes}_{\text{fused}} = 2 \times \text{sizeof(float)}
$$

one read and one write per element. This is why compiler stacks such as `torch.compile`, TorchInductor, and Triton matter: they turn high-level tensor programs into fused kernels when possible.

### Triton's Block-Level Model

Triton exposes a block-programming model. Instead of writing one CUDA thread at a time, the programmer writes operations over blocks of elements. The compiler maps those blocks to GPU execution.

A row-wise softmax illustrates the pattern. For a row $x$, stable softmax is:

$$
\text{softmax}(x_i) = \frac{e^{x_i - m}}{\sum_j e^{x_j - m}}, \quad m = \max_j x_j
$$

A fused implementation loads a row, computes the max, exponentiates, reduces the sum, divides, and writes the result once. The key is to avoid materializing intermediate tensors.

<details><summary>Code</summary>

```python
def stable_softmax_row(x):
    m = x.max()
    z = torch.exp(x - m)
    return z / z.sum()
```

</details>

For rows larger than one block, reductions require multiple passes or hierarchical reduction. The same pattern appears in attention: compute local statistics, merge them safely, and avoid storing the full score matrix.

### Matmul and Tiling

Naive matrix multiplication repeatedly loads elements:

<details><summary>Text</summary>

```python
# For each (m, n), for each k:
# load A[m, k], load B[k, n], accumulate
```

</details>

Tiled matmul loads blocks of $A$ and $B$, reuses them from shared memory or registers, and accumulates a block of $C$. The arithmetic is the same, but data movement is different.

For attention, the best-known example is Flash Attention. It tiles $Q$, $K$, and $V$ so attention can be computed without materializing the full $n \times n$ matrix. It maintains online softmax statistics and writes only the output. The asymptotic FLOPs remain quadratic, but memory traffic drops dramatically, which is exactly what matters on modern GPUs.

### Online Softmax and Flash Attention

Flash Attention works because softmax can be computed online while streaming through blocks of keys and values. For a vector $x$, stable softmax uses:

$$
m = \max_i x_i, \qquad l = \sum_i e^{x_i - m}
$$

When a new block arrives with local maximum $m_b$ and local denominator $l_b$, the global maximum becomes:

$$
m_{\text{new}} = \max(m_{\text{old}}, m_b)
$$

The denominator can be updated by rescaling old and new terms:

$$
l_{\text{new}} =
e^{m_{\text{old}} - m_{\text{new}}} l_{\text{old}} +
e^{m_b - m_{\text{new}}} l_b
$$

The output accumulator is updated with the same rescaling. This lets a kernel stream over blocks of $K$ and $V$, maintain exact softmax statistics, and avoid writing the attention matrix to HBM.

Conceptually:

<details><summary>Code</summary>

```python
def online_attention(q, k_blocks, v_blocks):
    m = -torch.inf
    l = 0.0
    acc = 0.0
    for k, v in zip(k_blocks, v_blocks):
        scores = q @ k.T
        m_block = scores.max()
        p = torch.exp(scores - m_block)
        l_block = p.sum()
        m_new = torch.maximum(m, m_block)
        acc = acc * torch.exp(m - m_new) + (p @ v) * torch.exp(m_block - m_new)
        l = l * torch.exp(m - m_new) + l_block * torch.exp(m_block - m_new)
        m = m_new
    return acc / l
```

</details>

The real kernel is tiled across many queries and uses vectorized memory movement, but the logic is the same. This is a good example of systems-aware algorithm design: the mathematical result is exact attention, but the data movement pattern changes completely.

### Reductions and Large Rows

Reductions are deceptively important. Softmax, normalization, loss computation, sampling, top-k, and many router operations all require max or sum reductions. When a row fits in one block, the kernel can reduce locally. When it does not, the operation becomes multi-stage:

1. Compute partial reductions per block.
2. Reduce the partials.
3. Rescale or normalize the original elements.

This is why sequence length and vocabulary size affect kernel design. A vocabulary softmax over more than 100,000 tokens has different reduction behavior from a small row-wise normalization. A long-context attention row may exceed the convenient block size and require more complex tiling.

The same issue appears in MoE routing. A top-k router over many experts needs efficient selection, not a full sort. If $E$ is large and $k$ is small, top-k kernels should avoid unnecessary work. Kernel design is full of these distinctions. Two operations can look identical in high-level PyTorch while having very different memory behavior, launch overhead, and reduction structure.

### The Stack in Practice

The practical stack is layered:

- PyTorch expresses model math and gives a reference.
- `torch.compile` and TorchInductor fuse graphs and emit lower-level kernels.
- Triton expresses block-level GPU algorithms.
- CUTLASS and cuBLAS provide tuned matmul implementations.
- PTX and hardware scheduling decide what actually runs.

The same rules repeat across softmax, normalization, matmul, attention, and MoE dispatch: reduce HBM traffic, tile for reuse, fuse when possible, align memory access, and benchmark real shapes instead of trusting intuition.

### When Custom Kernels Are Worth It

Not every operation deserves a custom kernel. cuBLAS, cuDNN, CUTLASS, and vendor libraries are already excellent for standard matmuls and convolutions. Custom kernels are most valuable when an operation combines several steps that would otherwise materialize intermediates, or when the shape is unusual enough that generic kernels waste memory bandwidth.

Good candidates include:

- Fused bias, activation, and projection epilogues.
- Fused normalization plus residual addition.
- Attention variants with custom masks or sparse layouts.
- MoE dispatch, combine, and grouped expert matmuls.
- Quantized matmuls with custom dequantization.
- Sampling kernels that combine logits processing, top-k/top-p, and random selection.

The risk is maintenance. A custom kernel must be correct across dtypes, shapes, architectures, and edge cases. It can break silently when model shape changes. A pragmatic workflow starts with a correct PyTorch reference, adds tests against random inputs and edge cases, benchmarks real production shapes, and only then replaces the hot path.

### Numerical Precision and Dtypes

Kernel performance is tied to dtype. FP32 is stable but expensive. FP16 and BF16 reduce memory traffic and use tensor cores efficiently. FP8 can improve throughput and memory use further, but requires careful scaling. Quantized inference formats such as INT8 and INT4 reduce bandwidth, but need dequantization and can introduce quality loss.

The numerical question is where precision matters. Accumulators often need higher precision than inputs:

$$
C_{ij} = \sum_k A_{ik}B_{kj}
$$

Even if $A$ and $B$ are FP16 or FP8, accumulating in FP32 or a wider internal format can prevent large rounding errors. Softmax also needs stable max subtraction. Normalization needs enough precision for variance or RMS estimates. Optimizer states often remain in higher precision because small update errors can accumulate over billions of tokens.

Mixed precision training therefore uses a policy, not one dtype everywhere. Parameters, gradients, optimizer states, activations, communication buffers, and accumulators may all use different formats. The policy must be compatible with kernels, hardware, checkpointing, and distributed collectives. A dtype that is fast in one kernel can become expensive if it forces casts, unfused dequantization, or unsupported communication paths.

### Profiling the Real Bottleneck

A good profiler trace explains where wall-clock time goes. Common categories are matmul, attention, normalization, communication, optimizer step, data loading, and idle gaps. The next optimization should target the largest real bottleneck, not the most interesting kernel.

For example, optimizing attention is pointless if the run is blocked on data loading. Rewriting a matmul is pointless if cuBLAS is already near peak. Reducing all-reduce time may not change step time if it is fully overlapped. Kernel engineering is most effective when paired with end-to-end profiling.

## 4. Distributed Training and Parallelism

Once a model no longer fits on one accelerator, training becomes a communication problem. The goal is to keep expensive GPUs computing while moving the minimum necessary data through a tiered network. On one GPU, "far away" means HBM instead of registers. Across a cluster, "far away" may mean another GPU, another node, or another pod.

### Communication Hierarchy

A rough hierarchy is:

| Level                   | Medium            | Role                             |
| :---------------------- | :---------------- | :------------------------------- |
| Registers/shared memory | On-chip           | Fast local reuse                 |
| HBM                     | Per GPU           | Large local tensor storage       |
| NVLink/NVSwitch         | In node           | Fast GPU-to-GPU communication    |
| InfiniBand/Ethernet     | Across nodes      | Slower distributed communication |
| Storage                 | Disk/object store | Checkpoints and datasets         |

Different parallelism strategies stress different links. Tensor parallelism communicates every layer and strongly prefers fast intranode links. Data parallelism communicates gradients once per step and can tolerate slower internode links if overlapped. Pipeline parallelism sends activations between stages and is sensitive to bubbles. Expert parallelism uses all-to-all routing and depends heavily on balanced traffic.

### Collectives

Distributed training is built from collective operations:

- `all_reduce`: combine tensors from all ranks and return the full result to all ranks.
- `reduce_scatter`: reduce tensors and scatter shards.
- `all_gather`: gather shards into a full tensor.
- `all_to_all`: exchange distinct chunks between ranks.
- `broadcast`: send one tensor to all ranks.

All-reduce can be decomposed:

$$
\text{all-reduce} = \text{reduce-scatter} + \text{all-gather}
$$

This identity is central to ZeRO, FSDP, tensor parallelism, and many optimizer-state sharding schemes.

### Data Parallelism

Data parallelism replicates the model on every GPU and splits the batch. Each rank computes local gradients, then gradients are averaged:

$$
g = \frac{1}{N} \sum_{r=1}^N g_r
$$

It is simple and efficient when the model fits on one GPU and the global batch can grow. But it does not reduce model memory. Every rank stores parameters, gradients, and optimizer state.

For Adam-like optimizers, memory is dominated by replicated state:

$$
\text{Memory} \approx P_{\text{params}} + P_{\text{grads}} + 2P_{\text{optimizer}}
$$

Data parallelism also runs into the critical batch size. Beyond some batch size, adding more data-parallel workers reduces training time poorly because optimization no longer benefits from larger batches.

### ZeRO and FSDP

ZeRO and Fully Sharded Data Parallel shard model state across ranks. Instead of every GPU holding all parameters, gradients, and optimizer states, each rank owns a shard.

The core pattern is:

<details><summary>Code</summary>

```python
# FSDP layer loop, conceptually
all_gather(weight_shards)      # materialize full layer weights
activation = layer(x)          # forward
discard_full_weights()

# backward
all_gather(weight_shards)
grad = layer_backward(...)
reduce_scatter(grad)           # return gradient shards
update_local_shard()
```

</details>

This saves memory at the cost of communication. It works well when communication can be overlapped with compute and when layers are large enough to amortize collective overhead.

### Tensor Parallelism

Tensor parallelism splits individual matrix multiplications across GPUs. For an MLP projection:

$$
y = xW
$$

a column split partitions $W$:

$$
W = [W_1, W_2, \dots, W_p]
$$

Each rank computes part of the output:

$$
y_i = xW_i
$$

The parts are then gathered or reduced depending on the next operation. Megatron-style tensor parallelism carefully pairs column and row splits so communication occurs at predictable points.

Tensor parallelism reduces per-GPU parameter and activation pressure, but it communicates inside every layer. It is therefore best inside a node with NVLink or NVSwitch.

### Pipeline Parallelism

Pipeline parallelism splits model depth. Rank 0 holds early layers, rank 1 holds later layers, and so on. Microbatches flow through the pipeline.

The problem is bubbles: some stages wait while others work. If there are $p$ pipeline stages and $m$ microbatches, the bubble fraction is roughly:

$$
\text{Bubble} \approx \frac{p - 1}{m + p - 1}
$$

More microbatches reduce bubbles but increase activation memory or require recomputation. Pipeline parallelism is most useful when the model is too deep to fit otherwise or when tensor/FSDP strategies alone are insufficient.

### Sequence, Context, and Expert Parallelism

Sequence parallelism shards sequence-dependent activations to reduce memory pressure. It is often paired with tensor parallelism because some operations, such as layernorm or dropout, are naturally sequence-local.

Context parallelism splits long sequences across devices. Attention then requires communication because tokens on one rank may need keys and values from another. The communication pattern depends on the attention algorithm: full attention, ring attention, block-sparse attention, or local/global hybrids.

Expert parallelism assigns MoE experts to different ranks. Tokens are routed to the ranks that host their experts:

<details><summary>Code</summary>

```python
# Expert parallel layer, conceptually
expert_ids = router(tokens)
dispatch = all_to_all(tokens, expert_ids)
local_out = run_local_experts(dispatch)
output = all_to_all(local_out, original_token_ids)
```

</details>

The challenge is load balance. If one expert receives too many tokens, its rank becomes the bottleneck.

### Composing Parallelism

Frontier training usually composes multiple axes:

| Strategy             | Shards      | Main communication         | Preferred topology         |
| :------------------- | :---------- | :------------------------- | :------------------------- |
| Data parallelism     | Batch       | Gradient all-reduce        | Across nodes acceptable    |
| FSDP/ZeRO            | Model state | All-gather, reduce-scatter | Good overlap needed        |
| Tensor parallelism   | Width       | Per-layer collectives      | NVLink/NVSwitch            |
| Pipeline parallelism | Depth       | Activation send/receive    | Moderate links acceptable  |
| Context parallelism  | Sequence    | Attention communication    | Depends on attention       |
| Expert parallelism   | Experts     | All-to-all                 | Strong network and balance |

The design is a placement problem. Fast links should carry frequent communication. Slow links should carry infrequent or overlapped communication. Activation checkpointing trades extra compute for lower memory. Gradient accumulation increases effective batch size without increasing communication frequency. The right plan depends on model width, depth, sequence length, MoE structure, batch size, and network topology.

### Effective Bandwidth and Overlap

Raw network bandwidth is not the same as effective training bandwidth. A collective may underperform because of small message sizes, topology mismatches, contention, kernel launch overhead, or poor overlap with compute. Training systems therefore measure effective bandwidth:

$$
\text{BW}_{\text{effective}} = \frac{\text{bytes communicated}}{\text{time observed}}
$$

This value should be measured for the actual collectives and tensor sizes used by the model. A cluster can look fast on a synthetic all-reduce benchmark and still bottleneck on all-to-all MoE dispatch or small per-layer tensor-parallel reductions.

Overlap is the main defense. In FSDP, the system can prefetch the next layer's weights while the current layer computes. In data parallelism, gradient buckets can be reduced while earlier gradients are still being computed. In pipeline parallelism, microbatch scheduling overlaps stages. Good overlap turns communication into a background cost; poor overlap exposes it directly on the critical path.

Conceptually:

<details><summary>Code</summary>

```python
for layer in layers:
    prefetch(next_layer.weight_shard)
    y = layer(x)
    reduce_previous_grad_bucket_if_ready()
```

</details>

The code is simple as an idea and complex in practice. Real systems must manage CUDA streams, memory pressure, dependency ordering, and failure recovery.

### Activation Checkpointing

Activations often dominate memory. During training, the backward pass needs intermediate activations from the forward pass. Activation checkpointing stores only selected activations and recomputes the rest during backward.

Checkpointing lowers activation memory by spending extra compute during backward recomputation. This is usually a good trade when memory is the bottleneck and tensor cores would otherwise be underused. It is less attractive when compute is already the bottleneck. Selective checkpointing is better than all-or-nothing checkpointing: attention, FFN, normalization, and MoE layers have different memory and compute profiles.

Checkpointing also interacts with pipeline parallelism and FSDP. Recomputing a layer may require all-gathering its weights again unless the system carefully schedules retention and release. The memory savings are real, but they can increase communication if implemented naively.

### Production Training Patterns

A common large-model layout is:

- Tensor parallelism inside each high-bandwidth node.
- FSDP or ZeRO across nodes to shard model state.
- Pipeline parallelism only when model depth or memory requires it.
- Context parallelism for very long sequences.
- Expert parallelism for MoE layers, aligned with network topology.

For dense models, the primary challenge is usually parameter, optimizer, and activation memory. For MoE models, it is often all-to-all communication and load balance. For long-context models, attention communication and KV-like activation memory become more important.

The best parallel plan is usually discovered by profiling. Theoretical memory formulas narrow the options, but the final decision depends on observed step time, bubble fraction, collective timing, recomputation overhead, and hardware reliability. Large training runs also need operational engineering: checkpoint cadence, restart time, data loader throughput, determinism requirements, and monitoring for silent divergence.

### Checkpointing and Fault Tolerance

Large training runs fail. Machines disappear, links degrade, filesystems stall, and jobs get preempted. Checkpointing is therefore part of the training algorithm from a systems perspective. A checkpoint must capture model weights, optimizer state, scheduler state, random number generator state, data loader position, and sometimes distributed-sharding metadata.

The checkpoint interval trades wasted compute against storage and pause time. Frequent checkpoints reduce lost work but can slow training or overload storage. Infrequent checkpoints improve steady-state throughput but increase recovery cost. Sharded checkpoints reduce per-rank memory pressure and write bandwidth, but they complicate restoration if the new job uses a different parallel layout.

Fault tolerance also affects evaluation and reproducibility. If a run restarts with a different data order or nondeterministic kernels, exact reproducibility may be impossible. Many production systems accept approximate reproducibility but preserve enough metadata to audit training: code version, data snapshot, checkpoint hash, hyperparameters, environment, and cluster layout.

### Data Pipeline Throughput

A model can only train as fast as data arrives. The data pipeline must tokenize, shuffle, pack, and deliver batches without starving accelerators. This becomes harder with multi-domain mixtures, long sequences, document boundaries, and online filtering.

Sequence packing is especially important. If examples have variable length and are padded naively, compute is wasted:

$$
\text{Padding waste} = \frac{\text{padded tokens} - \text{real tokens}}{\text{padded tokens}}
$$

Packing multiple documents into fixed-length sequences improves utilization but creates boundary and masking decisions. The data loader must also preserve mixture weights across workers and restarts. At large scale, input pipeline bugs can look like model problems: loss spikes, domain regressions, duplicated data, or poor downstream transfer.

## 5. Scaling Laws and Practical Training Recipes

Scaling laws turn small experiments into predictions about large training runs. They are not magic, and they are not substitutes for judgment, but they are essential because frontier runs are too expensive to tune by trial and error.

### Power Laws

Many training curves look approximately linear on log-log axes. A common model is:

$$
L(N) = L_\infty + aN^{-\alpha}
$$

where $N$ may represent parameter count, dataset size, or compute. More generally:

$$
L(C) = L_\infty + aC^{-\alpha}
$$

This captures diminishing returns: each multiplicative increase in compute yields a smaller absolute improvement.

Power laws appear because learning is distributed across many factors with heavy-tailed difficulty. Easy patterns are learned early; rarer and more complex patterns require more data and compute.

### Compute-Optimal Scaling

Kaplan-style scaling emphasized large models trained on relatively fewer tokens. Chinchilla shifted the conclusion: for a fixed compute budget, many models were undertrained. The compute-optimal recipe used more tokens and smaller models than earlier practice suggested.

If compute is roughly:

$$
C \approx 6ND
$$

where $N$ is parameters and $D$ is training tokens, the objective is:

$$
(N^\*, D^\*) = \arg\min_{N,D: 6ND=C} L(N,D)
$$

The lesson is not that one fixed token-to-parameter ratio is eternal. The lesson is that parameters and data must be scaled jointly. Data quality, duplication, curriculum, context length, architecture, optimizer, and target benchmark all affect the optimum.

### Data Scaling

More data is not automatically better. Pretraining data differs in quality, deduplication, domain mix, language coverage, code quality, reasoning density, and contamination risk. A model trained on lower-quality tokens may need more compute for the same downstream behavior.

A useful abstraction is effective data: tokens should be weighted by quality, domain relevance, uniqueness, and downstream usefulness rather than counted uniformly. In practice, those weights are not directly observable. They are inferred from ablations, validation loss, benchmark transfer, and downstream evals.

Long-context data also matters. Extending context length by interpolation alone can help, but models need training examples that actually use long-range dependencies. Otherwise long windows become expensive storage rather than useful reasoning context.

### Batch Size, Learning Rate, and WSD

Training throughput improves with larger batches until optimization reaches a critical batch size. Below that point, more batch improves hardware use and reduces gradient noise. Above it, returns diminish.

A common scaling relation is:

$$
\eta \propto \sqrt{B}
$$

or sometimes:

$$
\eta \propto B
$$

depending on regime, optimizer, and schedule. These rules are starting points, not guarantees.

Warmup-stable-decay schedules are common in modern recipes. The schedule has three phases:

1. Warmup raises the learning rate safely.
2. Stable training holds a high learning rate for most compute.
3. Decay reduces the learning rate near the end to improve final loss.

The WSD structure is useful because it separates exploration and convergence. It also makes it easier to extend training runs: the stable phase can be lengthened before decay.

### Hyperparameter Transfer

Small runs are useful only if their hyperparameters transfer. Practical scaling recipes run grids over smaller models and shorter budgets, then fit how optimal learning rate, batch size, weight decay, and schedule parameters change with scale.

A typical process is:

<details><summary>Code</summary>

```python
# Step 1: tune learning rate and batch size on small runs
for eta in eta_grid:
    for batch in batch_grid:
        loss = train_small(model_size, eta, batch)

# Step 2: tune weight decay after eta and batch are reasonable
for wd in wd_grid:
    loss = train_small(model_size, eta_best, batch_best, wd)

# Step 3: fit scaling trends and extrapolate cautiously
```

</details>

The risk is extrapolation. A hyperparameter that works at 1B parameters may fail at 100B if architecture, data, optimizer, or hardware regime changes.

### Muon and Optimizer Scaling

AdamW remains the default optimizer for many LLMs, but alternatives such as Muon try to improve matrix-parameter updates. Muon applies momentum and approximate orthogonalization to matrix-shaped parameters, while vector parameters such as normalization scales typically use AdamW.

Conceptually:

<details><summary>Code</summary>

```python
# Matrix parameter block
M_t = beta * M_{t-1} + (1 - beta) * G_t
U_t = newton_schultz_orthogonalize(M_t)
W_t = W_{t-1} - eta * U_t

# Vector parameters
# use AdamW separately
```

</details>

The motivation is to control update geometry. But optimizer comparisons are easy to get wrong. Each optimizer needs its own tuned learning rate, batch size, weight decay, and schedule before comparing final loss.

### muP

Maximal update parametrization, or muP, aims to make feature updates stable across width. Standard parametrizations can change the effective learning dynamics when width changes, so hyperparameters tuned on small models may not transfer.

The muP goal is:

$$
\Delta h_{\text{wide}} \approx \Delta h_{\text{small}}
$$

under width scaling. If this holds, small models become better predictors of large-model hyperparameters. In practice, muP is one tool in a larger scaling workflow. It helps most when architecture families are fixed and the goal is width extrapolation.

### A Practical Scaling Playbook

A serious training plan usually follows this loop:

1. Define the target: base loss, chat quality, code ability, reasoning, long context, latency, or cost.
2. Fix the architecture family and data mixture enough for experiments to transfer.
3. Run small scaling sweeps over model size, tokens, learning rate, batch size, schedule, and weight decay.
4. Fit trends and identify compute-optimal regions.
5. Validate with intermediate runs before committing to the largest run.
6. Track downstream evals, not only perplexity.
7. Preserve enough telemetry to diagnose instability, data problems, and optimizer failures.

Scaling laws reduce uncertainty. They do not remove it.

### Historical Lessons from Kaplan and Chinchilla

The Kaplan scaling laws showed that loss followed smooth trends over model size, dataset size, and compute. They encouraged the view that larger models trained on more compute would predictably improve. The later Chinchilla result changed the practical recipe by showing that many large models were data-starved. For a fixed compute budget, a smaller model trained on more tokens could outperform a larger model trained on fewer tokens.

The disagreement was not simply a contradiction. It reflected different experimental regimes, data assumptions, and compute allocations. Scaling laws are conditional statements: they hold over the range and setup used to fit them. Change the data quality, tokenizer, architecture, optimizer, context length, or benchmark objective, and the fitted optimum can move.

This is why modern teams treat scaling laws as part of an empirical system rather than a single universal formula. They fit internal curves on their own data mixture, architecture family, and training stack. Public laws provide priors; private experiments provide decision evidence.

### Perplexity Is Not the Whole Objective

Perplexity is useful because it is smooth and cheap, but it does not fully capture model value. A model can improve validation loss while barely improving coding, tool use, mathematical reasoning, or instruction following. Conversely, post-training can dramatically improve user-facing behavior while leaving base perplexity almost unchanged.

A broader training objective includes:

- Base-model loss on clean held-out data.
- Domain validation loss for code, math, multilingual text, or long-context data.
- Downstream benchmark performance.
- Post-training compatibility.
- Inference cost and latency.
- Safety and refusal behavior.

This creates a multi-objective problem where base quality, reasoning, coding ability, serving cost, latency, and safety risk all trade off against each other. The weights are product and deployment choices. A research model, a coding assistant, and a mobile on-device model should not optimize the same utility function.

### Open-Source Recipes as Infrastructure

Recent open-source model families have made scaling practices more standardized. Qwen-style recipes emphasize strong data pipelines, long-context extension, multilingual coverage, and careful post-training. LLaMA-style recipes show the importance of large clean datasets, staged context extension, and benchmark-driven iteration. DeepSeek-style recipes highlight aggressive systems optimization, MoE scaling, and fitted hyperparameters. Other models explore hybrid attention, state-space layers, or alternative optimizers.

The lesson is that scaling is now infrastructure. It includes:

- Data filtering and deduplication.
- Tokenizer and vocabulary choices.
- Architecture templates.
- Hyperparameter scaling rules.
- Distributed training recipes.
- Evaluation harnesses.
- Inference kernels.
- Post-training pipelines.

Model quality is not produced by one trick. It is produced by the alignment of these components.

### Separating Data and Model Effects

One common mistake is to attribute improvements to model size when they actually come from data, or to data when they come from architecture. Clean experiments vary one axis at a time. In practice, perfect isolation is hard because changes interact. A better optimizer may enable a larger learning rate. Better data may shift the compute-optimal model size. MoE may benefit more from diverse domains than a dense model. Still, ablation discipline matters. Without it, scaling decisions become storytelling.

A useful experiment matrix includes small, medium, and large models trained on controlled data mixtures; fixed-token and fixed-compute comparisons; repeated seeds for small runs; and downstream evals measured throughout training. This is expensive, but far cheaper than discovering a failed assumption at frontier scale.

### Learning Curves as Diagnostics

Training curves are diagnostic tools, not just progress indicators. A smooth loss curve with the expected slope suggests that data, optimizer, and scale are aligned. A curve that bends early may indicate data exhaustion, learning-rate decay too soon, batch size too large, or insufficient model capacity. Sudden spikes can indicate bad data batches, numerical instability, communication errors, or optimizer overflow.

Different metrics move at different speeds. Training loss reacts quickly. Validation loss reacts with delay. Downstream benchmarks may be noisy and step-like. Safety and instruction-following behavior may change mostly during post-training. A good monitoring setup tracks all of them without overreacting to any single noisy point.

One useful comparison is predicted loss versus observed loss:

$$
\Delta L = L_{\text{observed}} - L_{\text{predicted}}
$$

If $\Delta L$ stays near zero, the run follows the fitted scaling trend. If it drifts, something changed: data distribution, implementation, optimizer dynamics, hardware errors, or the validity range of the scaling law.

### From Pretraining to Deployment Quality

Pretraining produces a base model. Deployment usually needs additional stages: instruction tuning, preference optimization, tool-use training, safety tuning, domain adaptation, and inference optimization. These stages can change the ranking between base models. A base model with slightly worse perplexity may become a better assistant after post-training if it has stronger reasoning traces or cleaner data. A model with excellent chat quality may be too slow or expensive for the target product.

This reinforces the systems view. Scaling decisions should be made with the final product in mind. If the deployment requires low latency, architecture and quantization tolerance matter early. If the deployment requires long-context retrieval, pretraining should include long-document structure. If the deployment requires code editing, evaluation should include repository-level tasks, not just token loss on code.

## 6. Inference Serving and Evaluation

Inference has a different bottleneck from training. Training can process many tokens in parallel. Generation is sequential: each new token depends on previous tokens. This turns serving into a memory and scheduling problem.

Evaluation asks what "good" means. For LLMs, that question is not singular. A base model, chatbot, coding agent, safety filter, and cybersecurity assistant require different evidence.

### Prefill and Decode

LLM inference has two phases:

- Prefill: process the input prompt and build the KV cache.
- Decode: generate new tokens one at a time using the cache.

Prefill resembles training. It processes many tokens in parallel and can use large matmuls efficiently. Decode is usually memory-bound because each step loads model weights and KV cache entries for a small amount of computation.

The naive approach recomputes attention over the full prefix at every step. KV caching avoids that:

<details><summary>Code</summary>

```python
# Prefill
for layer in layers:
    k, v = layer.project_kv(prompt_tokens)
    cache[layer].append(k, v)

# Decode
for step in range(max_new_tokens):
    for layer in layers:
        q = layer.project_q(current_token)
        k_cache, v_cache = cache[layer]
        current_token = attend(q, k_cache, v_cache)
    cache[layer].append(new_k, new_v)
```

</details>

With a cache, each step attends to stored keys and values instead of recomputing them.

### KV Cache Size

KV cache memory scales as:

$$
\text{KV bytes} = 2 \cdot B \cdot T \cdot L \cdot H_{\text{kv}} \cdot d_h \cdot \text{bytes}
$$

where $B$ is batch size, $T$ is sequence length, $L$ is layer count, $H_{\text{kv}}$ is the number of key-value heads, and $d_h$ is head dimension.

This formula explains why long-context serving is difficult. Even if model weights fit comfortably, the cache can dominate memory. GQA reduces $H_{\text{kv}}$. Quantized KV caches reduce bytes per element. Sliding-window or sparse attention reduces effective $T$. PagedAttention improves memory allocation and sharing.

### Arithmetic Intensity in Decode

Decode is often memory-bound because each generated token performs relatively little computation per byte loaded. For a dense model with $P$ parameters, each token may require streaming a large fraction of the weights. If weights are in FP16, weight traffic is approximately:

$$
\text{Bytes}_{\text{weights}} \approx 2P
$$

The FLOPs per token are also proportional to $P$, so the compute-to-memory ratio is limited by dtype and batch size. Larger batches reuse weights across more tokens, but they also increase queueing delay and KV cache memory. Serving is therefore a scheduling problem as much as a kernel problem.

Prefill has higher arithmetic intensity because prompt tokens are processed together. A server may be compute-bound during prefill and memory-bound during decode. This split motivates separate optimization paths: large efficient attention kernels for prefill, and cache-friendly scheduling plus weight/KV compression for decode.

### PagedAttention and Cache Management

KV cache allocation is difficult because requests have variable lengths. A naive allocator reserves contiguous memory for the maximum possible sequence length, wasting memory when outputs are shorter. PagedAttention treats the KV cache like virtual memory. It stores cache blocks in pages and maps logical token positions to physical blocks.

This enables:

- Efficient handling of variable-length requests.
- Sharing prefixes across requests.
- Avoiding large contiguous allocations.
- Better memory utilization under continuous batching.

The abstraction is:

<details><summary>Code</summary>

```python
logical_block = sequence_id, block_index
physical_block = page_table[logical_block]
kv = kv_cache[physical_block]
```

</details>

This is systems plumbing, but it directly affects model throughput. If cache fragmentation wastes memory, batch size falls. If batch size falls, decode uses the GPU poorly.

### Latency and Throughput

Latency is time per request. Throughput is tokens per second across requests. Serving systems trade them against each other.

Small batches minimize latency but waste GPU bandwidth. Large batches improve throughput but increase waiting time. Continuous batching addresses this by admitting new requests as old ones finish, keeping the GPU full without forcing every request into the same static batch.

The scheduler must manage:

- Prompt length variation.
- Output length uncertainty.
- KV cache memory.
- Priority classes.
- Streaming tokens.
- Cancellation.
- Speculative decoding.

At production scale, the scheduler can matter as much as the model kernel.

### Prefix Caching and Routing

Many applications reuse prompt prefixes: system prompts, tool instructions, templates, retrieved context headers, or conversation history. Prefix caching stores the KV cache for shared prefixes so future requests can skip prefill for those tokens.

The benefit depends on hit rate, prefix length, and the cost of prefill for those tokens. Prefix caching works best when prompts are standardized. It works poorly when every request has unique context.

Large deployments also route requests across replicas. Routing decisions consider model availability, cache locality, current batch composition, expected output length, latency class, and memory headroom. A request may be sent to a slightly busier replica if that replica already has the relevant prefix cached.

This means serving quality depends on more than the model binary. The same weights can have different latency and cost profiles under different schedulers, cache policies, batching strategies, and hardware.

### Quantization and Pruning

Quantization reduces parameter traffic:

$$
\text{Bytes}_{\text{weights}} = P \cdot \text{bits} / 8
$$

Moving from FP16 to INT8 roughly halves weight bandwidth. Moving to 4-bit can reduce it further, though quality and kernel support become more delicate.

Weight-only quantization is especially useful for decode because generation repeatedly streams weights. Activation quantization and KV quantization can help too, but they introduce more numerical risk.

Pruning removes parameters or structures. Unstructured sparsity is hard to accelerate unless hardware and kernels support it. Structured pruning is easier to serve but can damage quality if not aligned with model behavior.

### Speculative Decoding

Speculative decoding uses a small draft model to propose multiple tokens, then the target model verifies them. If accepted, the system gets several tokens for one target-model pass.

The method can be lossless with respect to the target distribution. If the draft distribution is $p$ and target distribution is $q$, a proposed token is accepted with probability:

$$
\min\left(1, \frac{q(x)}{p(x)}\right)
$$

When the draft model is close to the target, many tokens are accepted and speed improves. When it is poor, verification rejects too often and overhead dominates.

A conceptual loop is:

<details><summary>Code</summary>

```python
while not done:
    draft_tokens = draft_model.generate(prefix, k)
    target_probs = target_model.score(prefix, draft_tokens)
    accepted = accept_reject(draft_tokens, target_probs)
    prefix.extend(accepted)
```

</details>

Speculative decoding is most useful when target-model forward passes are expensive and the draft model is much cheaper.

### Putting Serving Techniques Together

High-performance serving stacks combine many techniques:

- Flash Attention or paged attention kernels.
- GQA or MQA to reduce KV heads.
- KV cache paging and reuse.
- Continuous batching.
- Quantized weights and sometimes quantized KV cache.
- Speculative decoding.
- Prefix caching for repeated prompts.
- Routing across model replicas.
- Admission control based on memory and latency targets.

No single technique dominates all workloads. A chat assistant, code agent, batch summarizer, and long-context retrieval system have different prompt lengths, output lengths, latency needs, and cache behavior.

### Serving Metrics

Useful serving metrics include:

- Time to first token.
- Inter-token latency.
- End-to-end latency.
- Tokens per second per GPU.
- Requests per second.
- KV cache utilization.
- Batch size distribution.
- Prefix cache hit rate.
- Cost per million input and output tokens.

These metrics should be reported by workload. A benchmark with short prompts and short outputs says little about long-context agents. A throughput test with static batching says little about interactive chat. Production serving requires replaying realistic traces or carefully modeling the request distribution.

### Reliability and Degradation

Serving systems need graceful degradation. When traffic spikes, the system may reduce max output length, lower batch admission, route to smaller models, disable expensive reasoning modes, or reject low-priority requests. These policies affect user experience and should be designed explicitly rather than emerging from out-of-memory failures.

The core resource constraints are HBM capacity, request latency SLOs, and tokens-per-second capacity. When one constraint is violated, the scheduler must choose a trade-off. It can reduce throughput to preserve latency, increase latency to preserve throughput, or shed load. For agentic systems, it may also reduce tool retries or reasoning budget.

Reliability also includes numerical and content consistency. Quantized models need regression tests against quality loss. Speculative decoding needs tests that acceptance logic preserves the target distribution. Prefix caching needs isolation between users and prompts. A serving optimization that leaks cache state or changes sampling semantics is not an optimization; it is a correctness bug.

### Perplexity

Perplexity evaluates probability modeling:

$$
\text{PPL}(D) = \exp\left(-\frac{1}{|D|}\sum_{t=1}^{|D|}\log p(x_t \mid x_{\lt t})\right)
$$

Lower perplexity means the model assigns higher probability to held-out text. It is useful for base-model training because it is dense, stable, and cheap to measure.

But perplexity is not enough. It may not predict instruction following, tool use, factuality, safety, or long-horizon agent behavior. It can also improve while downstream quality stalls if the validation distribution is mismatched.

Perplexity also depends on tokenizer and data formatting. Two models with different tokenizers may have perplexities that are not directly comparable unless normalized carefully. Even within one tokenizer, validation set choice matters. A model optimized for code may not shine on general web text; a multilingual model may look weaker on English-only validation while being more useful globally.

### Exam Benchmarks

Exam-style benchmarks provide clear grading. They ask questions with known answers:

$$
\text{Accuracy} = \frac{1}{N}\sum_{i=1}^{N}\mathbb{1}[\hat{y}_i = y_i]
$$

They are useful because they are reproducible and easy to compare. They are limited because they can be saturated, contaminated, sensitive to prompting, and disconnected from real workflows.

Multiple-choice exams are especially fragile. A model may exploit answer patterns, wording artifacts, or memorized examples. Strong benchmark practice reports prompts, decoding settings, contamination checks, and confidence intervals.

Exam scores also hide calibration. A model that answers 80 percent correctly with well-calibrated uncertainty may be more useful than a model that answers 82 percent correctly but is confidently wrong on critical items. For high-stakes use, evaluation should include abstention, confidence, and error severity.

### Chat and Preference Benchmarks

Chat models are often evaluated by pairwise preference, where human raters or judge models compare two responses. Arena-style systems aggregate many comparisons into ratings. This is closer to user preference than exact-match exams, but it introduces new problems: judge bias, length bias, demographic uncertainty, prompt distribution drift, and hidden system prompts.

Debiasing can adjust for response length or judge tendencies, but it cannot fully solve validity. A chat benchmark should be treated as evidence about a particular user distribution, not a universal measure of intelligence.

Preference data is also shaped by interface. Users may prefer concise answers in one product and detailed answers in another. They may reward confidence even when it masks uncertainty. They may prefer answers that look polished over answers that expose caveats. This is why pairwise preference should be supplemented with task rubrics, factuality checks, and domain expert review.

### Agentic Benchmarks

Agent benchmarks evaluate systems that act over time: coding agents, web agents, terminal agents, tool-using assistants, and research agents. The score is a function of the model plus scaffold, so two systems using the same base model can perform very differently. Tool access, retrieval, prompting, planning loops, file editing, test running, and error recovery all change outcomes.

A coding benchmark should specify the unit of evaluation:

<details><summary>Code</summary>

```python
score = swe_bench(
    lm="model-weights-or-api",
    scaffold="agent-framework-version",
    tools=["shell", "editor", "tests"],
    split="verified",
)
```

</details>

Without scaffold details, the score is hard to interpret.

Agent benchmarks need trace inspection. A final pass/fail score can hide brittle behavior: excessive tool calls, lucky test passing, hidden timeouts, destructive edits, or incorrect reasoning that happens to satisfy the benchmark. For coding agents, unit tests are necessary but insufficient; a patch can pass visible tests and still be the wrong fix. Private repositories and human review remain important because public tasks become training and tuning targets.

### ARC, Reasoning, and Test-Time Compute

ARC-style tasks try to reduce reliance on memorized knowledge and emphasize abstraction. They attempt to make reasoning dominate over stored facts. Reasoning models improve partly by spending more inference compute, which changes evaluation. A model is no longer just a set of weights; it is also an inference procedure with a compute budget. Reports should state whether the model used one pass, chain-of-thought sampling, search, tool use, verifier reranking, or another test-time strategy.

### Safety Benchmarks

Safety evaluation measures refusal, harmful compliance, jailbreak resistance, policy adherence, and contextual risk. A simple refusal metric is:

$$
\text{SafeRate} = \frac{1}{|\mathcal{H}|} \sum_{h \in \mathcal{H}} \mathbb{1}\left[ \text{Refuse}\big(\text{LM}(h)\big) \right]
$$

This is useful but incomplete. A model can refuse too much, refuse too little, or behave differently under multi-turn pressure. Safety is also multidimensional. A model may reduce hallucination risk as capability improves while increasing misuse risk. Jailbreak evaluation is adversarial: attackers search for a suffix or prompt transformation that induces harmful compliance. Safety scores therefore depend on attacker strength, policy definitions, domain, and deployment context.

### Validity and Contamination

A benchmark can be cleanly implemented and still invalid for the intended decision. Ecological validity asks whether the benchmark distribution matches deployment.

Train-test contamination is another threat. Modern models train on enormous corpora, so benchmark items, solutions, paraphrases, or derivative pages may have appeared in training. Fresh data helps but does not prove cleanliness; a new page can contain old copied content.

One route is private evaluation with data that was never published or leaked. Another is exposure testing: if a model strongly prefers the canonical ordering of benchmark questions over random permutations, that can suggest exposure.

No method is perfect. Serious evaluation combines contamination checks, private data, fresh tasks, output inspection, and deployment-specific tests.

### Cost-Aware Evaluation

Modern models can trade inference compute for quality. A reasoning model may use longer internal traces, more samples, search, verifier reranking, or tool calls. Evaluation should therefore report cost, latency, and risk alongside quality.

A slower model with higher accuracy may be better for offline theorem proving and worse for autocomplete. A cheaper model may be better for high-volume classification even if a larger model wins benchmarks. Cost-aware evaluation is especially important for agents because tool calls, retries, and long context can dominate the bill.

The unit of evaluation should match the buying or deployment decision. If the user will deploy a full agent, evaluate the full agent. If the user wants to choose base weights for fine-tuning, evaluate the base model. If the user wants to compare algorithms, control the data, compute, and scaffold.

### Choosing the Right Evaluation

The right evaluation depends on the decision:

| Goal                         | Better evaluation choice                                    |
| :--------------------------- | :---------------------------------------------------------- |
| Train a base model           | Held-out perplexity, private validation sets                |
| Compare academic capability  | Exams, ARC, reasoning suites                                |
| Pick a chatbot               | Pairwise preference plus task-specific rubrics              |
| Deploy a coding agent        | SWE-bench-like tasks, private repos, trace audits           |
| Evaluate cybersecurity tools | Capability tests plus dual-use policy review                |
| Assess safety                | Refusal tests, policy violation rates, jailbreak robustness |
| Buy a model for a workflow   | Private use-case eval with cost and latency included        |

The key is to report what is being evaluated: method, model, or system.

| Object | Fixed                       | Varies                       | Example                 |
| :----- | :-------------------------- | :--------------------------- | :---------------------- |
| Method | Train/test split and budget | Algorithm                    | Classic ML comparison   |
| Model  | Often unclear               | Weights, data, compute       | Foundation model report |
| System | Almost everything           | LM, scaffold, tools, prompts | Agent leaderboard       |

For modern LLMs, a score usually reflects many moving parts. An evaluation report should specify the dataset, split, prompt or scaffold, tools, judge, cost, latency, and purpose.

### A Minimal Evaluation Report

A useful LLM evaluation report should include:

- The model or system version.
- The exact benchmark and split.
- Prompt template, system prompt, and decoding settings.
- Tool access and scaffold details.
- Number of samples and confidence intervals.
- Judge model or human-rater protocol.
- Cost, latency, and inference budget.
- Contamination or freshness checks.
- Known failure modes from manual inspection.

This may look bureaucratic, but it prevents misleading comparisons. Without these details, two scores can differ because of prompt format, tool permissions, retries, context length, judge bias, or sampling temperature rather than model capability.

The final question for any benchmark is not "what is the score?" It is "what decision does this score support?" If the score does not support a concrete decision, it is at best descriptive. If it supports the wrong decision, it is actively harmful.
